## 1. 终端在整体架构中的定位

在“在线收敛、离线有界”的总体原则下，终端不是后端微服务的附属显示设备，而是**离线业务期间余额记账的权威执行节点**和**门禁策略的本地决策节点**。后端方案将两条不可后补的架构约束——消费离线的幂等键 `{terminal_id}:{local_seq_no}`、门禁快照的**最大离线有效期**——钉在了服务边界上，而这两个约束的**实际执行主体都是终端**。终端的工程目录、运行时选型和补传纪律，直接决定这两条约束能否落地。

因此，终端应用在工程结构中作为与 `services/` 并列的一等单元存在：

```
project-root/
├── terminals/
│   ├── onecard-terminal-consumption/     # 消费终端应用
│   ├── onecard-terminal-access/          # 门禁终端应用
│   ├── onecard-terminal-common/          # 公共库：本地账本、补传队列、国密SDK封装
│   └── docs/                             # 终端部署、升级、运维文档
├── services/                             # 8 个后端微服务
├── apis/                                 # 跨服务 Feign 契约
├── gateway/
└── ...
```

`terminals/` 独立成工程而非塞入 `services/`，原因是终端的构建目标（APK / 固件 / 边缘容器）、运行时（OpenHarmony / 轻量信创 Linux）、本地数据库与硬件依赖（PSAM、生物识别模组）与后端 Maven 聚合工程完全不同。公共能力沉淀到 `onecard-terminal-common`，消费与门禁共享底层驱动和国密封装，但**事务语义层严禁共用**。


## 2. 物理与操作系统架构

### 2.1 终端形态与 OS 选型

2026年Q4的一卡通终端选型，信创合规与金融级安全是两条硬约束。OpenHarmony 已成为消费/门禁终端信创路线的主流底座之一：联迪商用 LANDIQ8-T 智能收银终端已于 2026 年通过 **OpenHarmony 官方兼容性认证**，基于“鲲鹏 + 鸿蒙”根技术完成金融支付场景的适配。OpenHarmony 金融数字化服务终端兼容性规范已明确覆盖 **PSAM 卡、刷脸模块、指纹模块、安全执行环境、远程 OTA 升级、TMS 接入**等终端必备能力。对于算力需求较低的轻量消费机和水控器，可采用 OpenHarmony 轻量系统或信创轻量 Linux；门禁控制器若已运行 Linux 且外设驱动成熟，可保留轻量信创 Linux 并叠加安全加固层。

| 终端类型 | 推荐 OS | 理由 |
|---|---|---|
| 消费终端（食堂/商超） | **OpenHarmony 5.0+**（标准系统） | 已获金融终端兼容性认证路径；PSAM/刷脸/打印/扫码外设规范成熟 |
| 门禁终端（人脸/刷卡） | **OpenHarmony 5.0+** 或 **加固轻量 Linux** | 人脸模组和 PSAM 验签在 OpenHarmony 上有标准接口；存量 Linux 控制器可保留 |
| 圈存/自助终端 | **OpenHarmony 5.0+** 或 **信创 Linux（麒麟/统信轻量版）** | 交互复杂，需完整 Web/UI 框架；信创 OS 可与后端复用适配成果 |

**关键纪律**：无论选哪种 OS，终端必须支持 **Secure Boot 和安全启动链**，确保只有签名固件/应用可执行；生物识别模板（人脸特征值）**不得以明文或可逆形式存储**，应加密后存入安全存储区，原始人脸图像不在终端持久化。

### 2.2 硬件安全根

终端必须内置**国密二级（或以上）安全芯片 / PSAM 模块**作为硬件信任根。主流 PSAM 模块符合 **GM/T 0016、GM/T 0019**，支持 **SM1/SM2/SM3/SM4 全套国密算法**，具备密钥不可导出、防篡改、拆机自保护等特性。安全芯片承担三项终端侧核心职责：

- **设备身份**：每台终端持有唯一 SM2 证书，私钥生成并封闭于安全芯片内部，平台侧通过挑战-应答完成双向身份认证，阻断伪终端接入；
- **交易密码运算**：消费流水的 SM3 完整性指纹、交易报文的 SM4 会话加密、门禁策略快照的 SM2 验签，全部在安全芯片内闭环；
- **密钥生命周期**：行业密钥或终端密钥更新时，通过更换 PSAM 卡或安全芯片内的密钥分区完成，**密钥不以任何形式出现在普通应用内存或本地文件中**。


## 3. 消费终端：本地权威 + 幂等补传

### 3.1 分层架构

消费终端应用分为五层，补传队列与本地账本严格分离：

| 层级 | 职责 | 关键设计 |
|---|---|---|
| **硬件抽象层** | 读卡器、刷脸模组、PSAM、打印机、通信模组统一驱动接口 | 屏蔽不同终端形态差异 |
| **本地账本层** | SQLite（WAL 模式）+ 追加写事件日志 | **落盘先于提示**；本地流水号单调递增 |
| **补传队列层** | 持久化待传队列，消费流水独立 topic | **不与人证核验、通行事件共用队列** |
| **安全服务层** | SM2/SM3/SM4 运算、证书管理、PSAM 调用 | 密钥不出安全芯片 |
| **业务应用层** | 消费受理、规则执行（补贴/限额/时段）、人机交互 | 识别成功 ≠ 记账成功 |

### 3.2 本地账本纪律

消费终端本地账本是离线期间余额的唯一权威，必须满足三条硬性要求：

**落盘先于提示。** 识别成功（刷卡/刷脸/扫码）不等于记账成功。终端必须先完成本地账本写入并 `fsync`，之后才向用户显示“扣款成功”。提示先于落盘是窗口纠纷最常见的根因。SQLite 必须启用 **WAL 模式**，每次本地写入使用显式事务，确保设备突然断电时已确认的交易不丢失。在 WAL 之外，建议维护一个**追加写的事件日志**（append-only journal），作为 SQLite 主库之外的独立权威记录，用于断电恢复后的校验和对账，避免 WAL checkpoint 异常导致账本不一致。

**幂等键由终端生成。** 幂等键格式为：

```
{terminal_id}:{local_seq_no}
```

`local_seq_no` 是终端本地**单调递增序号**，不是时间戳。使用时间戳在时钟回拨时会产生碰撞键，导致两笔不同交易被云端误判为同一笔。无论补传重试多少次、经过多少次网络抖动，`onecard-transaction-service` 以该键做唯一性检查，云端只入账一次。

**补传只写交易，不写主数据。** 离线补传通道的职责边界是交易流水。人员信息、账户状态、门禁权限等主数据**不得通过消费补传通道回传**，避免补传通道演变成第二条主数据写入路径。这条纪律与门禁补传的边界一致，在消费侧同样适用。

### 3.3 补传队列与语义隔离

消费流水的补传队列**不得与人证核验、通行事件共用同一 MQTT 主题和同一重试 backoff**。食堂高峰的消费补传若被其他流量挤占，窗口扣款确认延迟会直接引发纠纷。消费流水队列的配置要求：

| 维度 | 要求 |
|---|---|
| 通信协议 | MQTT（QoS 1 或以上）或 HTTP，经 `onecard-device-service` 统一接入 |
| Topic | **独立 topic**，不与通行/人证共用 |
| 消费优先级 | 最高，独立消费者组与线程池 |
| 补传顺序 | 按 `local_seq_no` 升序串行补传 |
| 服务端响应 | `SUCCESS` / `NEED_REVIEW`；`NEED_REVIEW` 不阻断受理，但进入人工队列 |
| 风控 | 补传交易**必须经过** `onecard-risk-service`，不因离线绕过 |

### 3.4 离线容量与降级

消费终端本地离线记录容量建议 **≥10,000 条**（覆盖食堂峰值场景下的典型断网时长）。本地账本接近容量阈值时，终端应拒绝新交易并明确提示，而非静默覆盖或丢弃。本地余额文件须由 WAL + 校验机制保护，防止损坏导致透支或负余额；服务端补传风控作为第二道防线，对超额、超频交易标记 `NEED_REVIEW`。


## 4. 门禁终端：策略快照 + 有界自主

### 4.1 与消费终端的事务语义隔离

门禁离线与消费离线的语义根本不同，**不得共用同一套补传重试机制**：

| 维度 | 消费离线 | 门禁离线 |
|---|---|---|
| 事务语义 | 记账恰好一次 | 状态机事件（继电器动作） |
| 补传顺序 | 必须幂等，按序号保序 | **可乱序**，按时间戳排序即可 |
| 补传合并 | 不可合并 | 可合并相同门状态重复事件 |
| 失败后果 | 资金差错 | 拒绝通过，门保持锁定 |

门禁补传队列使用**独立 topic**，优先级低于消费流水，不与消费队列共用 backoff。

### 4.2 策略快照的完整性与有效期

`onecard-access-service` 在设备在线时生成策略快照，经 `onecard-device-service` 下发至门禁控制器。快照内容必须包含：该门组授权人员标识列表、有效时段规则、版本号、签发时间、**最大离线有效期**。完整性由 **SM2 签名**保障，设备端在载入本地决策引擎前必须验签通过。

**有界自主是门禁离线安全的核心。** 超过最大离线有效期后，控制器必须执行 **fail-closed**（拒绝所有常规凭证）或仅允许应急凭证通行，**不得无限期信任陈旧白名单**。离线自治的前提是时间窗口可控；无限期信任本地快照意味着一次长期的权限撤销可能在断网设备上完全失效。最大离线有效期应在选型阶段由业务安全策略确定，并在终端固件中作为**强制逻辑**实现，而非可选配置。

### 4.3 恢复连接后的同步顺序

门禁终端恢复连接后的操作顺序是确定的，**不可调换**：

1. **先校准时钟**：通过 SNTP 或平台时间源校准本地时钟；
2. **再拉取最新策略快照并验签**：快照的完整性和有效期判断依赖正确时钟；
3. **最后按时间戳补传通行记录**：通行事件可乱序、可按时间戳排序，不要求幂等。

如果时钟校准晚于快照拉取，快照的有效期判断可能在错误时钟下失效；如果补传早于快照更新，可能在旧快照下产生错误的放行决策。

### 4.4 生物识别与本地决策

人脸/指纹识别在终端侧运行，用于判断“**是谁**”，但“**能不能进**”由本地策略快照决定。识别成功的人脸特征值必须与快照中的授权列表和时段规则匹配，匹配通过才驱动继电器。人脸模板以加密形式存储于安全区，原始人脸图像不在终端持久化。门禁终端同样不承载人员主数据的新增或修改，**通行记录只上送、不反向改写主数据**。


## 5. 终端安全体系（国密闭环与等保/密评衔接）

终端侧的安全能力必须形成完整闭环，而非依赖平台侧外挂。等保三级和密评要求密码保障系统**同步规划、同步建设、同步运行**，密评基本合格口径为**得分 ≥ 60 且无高风险项**，等保三级及以上系统每年至少开展一次密评。

| 安全能力 | 终端侧实现 | 算法/标准 |
|---|---|---|
| 设备身份认证 | PSAM/安全芯片内的唯一 SM2 证书，挑战-应答 | SM2，GM/T 0016/0019 |
| 交易报文加密 | 每笔交易 SM4 会话密钥加密，密钥由安全芯片协商 | SM4 |
| 流水完整性 | 每笔消费生成 SM3 数字指纹，篡改可即时发现 | SM3 |
| 门禁快照验签 | 设备端用安全芯片内公钥验签后载入 | SM2 |
| 本地存储加密 | 卡号、身份证号等敏感字段 SM4 加密后落盘；人脸模板加密存储 | SM4 |
| 安全启动 | Secure Boot，仅签名固件/应用可执行 | 芯片级信任根 |
| 密钥保护 | 密钥在安全芯片内生成、存储、运算，**不可导出** | PSAM 硬件 |
| 审计 | 终端本地记录关键操作日志（登录、参数变更、补传状态），按等保要求留存并可上送 | — |

终端证书体系和密钥管理方案应在**选型阶段**纳入密评方案，而非测评前补救。PSAM 卡的行业密钥更新通过换卡完成，终端整机无需更换，降低密钥轮换的运维成本。


## 6. OTA 升级与设备影子

### 6.1 OTA 升级纪律

终端固件/应用升级必须满足：

- **签名校验**：升级包在终端侧用内置公钥验证签名，**不通过则拒绝安装**，防止恶意固件写入；
- **灰度发布**：按终端型号、区域或白名单分批推送，首批比例建议 ≤20%，验证稳定后再扩大范围；
- **回滚能力**：保留上一可用版本，升级失败或异常时自动回滚；
- **断电续传**：升级包分片传输，支持断点续传，避免弱网环境下重复下载。

### 6.2 设备影子：只同步状态，不承载决策数据

设备影子保存“期望状态”与“上报状态”的差异，用于**状态同步**（在线状态、固件版本、配置差异等），经 MQTT `$sys/{pid}/{did}/shadow/update` 和 `get` 主题与平台交互。**设备影子不得替代终端侧离线决策数据**：门禁策略快照必须完整缓存在终端本地，消费账本必须完整落盘于终端本地，影子只保存差异，不承载交易流水或策略快照。


## 7. 与后端微服务的契约边界

终端应用通过 `apis/*-api` 中的契约模块与后端交互，**禁止直接调用账户/交易服务的内部实现**。

| 交互场景 | 接口/通道 | 关键约束 |
|---|---|---|
| 消费离线补传 | `POST /api/transaction/offline-transactions`（经 device-service） | 载荷含 `terminal_id:local_seq_no` 幂等键；响应 `SUCCESS` / `NEED_REVIEW` |
| 门禁快照拉取 | 经 `onecard-device-service` 通道 | 终端验签后载入；快照完整缓存，不走影子 |
| 通行记录补传 | 独立 MQTT topic / HTTP | 可乱序，按时间戳排序；不与消费共用队列 |
| 设备影子同步 | MQTT shadow topic | 仅状态类信息，不含交易/策略数据 |
| 风控标记 | 补传响应或异步回执 | `NEED_REVIEW` 进入人工复核，不静默入账 |


## 8. 终端工程规范与实施要点

### 8.1 工程目录

```
terminals/
├── onecard-terminal-common/          # 本地账本抽象、补传队列、国密SDK封装、WAL工具
├── onecard-terminal-consumption/
│   ├── app/                          # 消费业务应用
│   ├── ledger/                       # SQLite WAL + append-only journal
│   ├── sync/                         # 消费补传队列（独立 topic）
│   └── security/                     # PSAM/SM2/SM3/SM4 调用封装
├── onecard-terminal-access/
│   ├── app/                          # 门禁业务应用
│   ├── snapshot/                     # 策略快照验签与本地决策引擎
│   ├── sync/                         # 通行补传队列（独立 topic，可乱序）
│   └── biometrics/                   # 人脸/指纹本地识别与模板安全存储
└── docs/
```

### 8.2 关键实施纪律

1. **幂等键第一天落定**：`{terminal_id}:{local_seq_no}` 在终端接口和本地账本 schema 设计的第一天钉死；`local_seq_no` 必须单调递增，**禁止时间戳**。
2. **消费与门禁补传物理隔离**：两套队列、两套 topic、两套 backoff，消费流水队列优先级最高。
3. **落盘先于提示**：本地 `fsync` 成功是显示“扣款成功”的前置条件；SQLite WAL + append-only journal 双保险。
4. **门禁快照有界**：最大离线有效期 + 超期 fail-closed 写入固件强制逻辑，不可作为可选配置。
5. **国密在终端闭环**：SM2 设备证书、SM4 传输/存储加密、SM3 完整性校验全部经 PSAM 安全芯片完成，密钥不出芯片。
6. **OTA 签名不可绕过**：升级包验签失败即拒绝，灰度与回滚作为固件基本能力。
7. **设备影子不承载决策**：快照和账本必须完整端侧缓存，影子只同步状态差异。

终端方案的成功标准不是“功能齐全”，而是**在后端网络不可达时，消费记账不丢、不重、不乱序，门禁决策在有效期内自主、超期后 fail-closed**。这两个标准一旦在终端工程中得到满足，后端方案中的幂等约束和有界自主原则才真正闭环。
