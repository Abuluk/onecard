# 一卡通平台基础开发方案（信创 + 等保三级）

**版本**：2.0  
**日期**：2026-11-02  
**定位**：本方案面向同时满足**信息技术应用创新（信创）** 与**网络安全等级保护第三级（等保三级）** 的一卡通平台建设/改造项目。一卡通承载身份认证、消费交易、门禁通行、清分清算等核心业务，属于“重要业务系统”，须同时通过信创适配验证与等保三级测评（并衔接密评）。本方案以《项目说明》确定的技术基线为工程事实，以《一卡通系统微服务架构设计文档》确定的服务边界与离线语义为业务约束，围绕**技术栈、安全架构、微服务工程规范、离线业务适配、实施路径**五个维度展开。


## 一、方案定位与双合规基线

### 1.1 两条刚性约束

- **信创约束**：从芯片、操作系统、数据库、缓存、消息、微服务运行时到应用层，形成可验证的国产化链路，不接受“局部替换、核心仍依赖非信创组件”的组合。
- **等保三级约束**：遵循“一个中心、三重防护”——安全管理中心统一管控，安全通信网络、安全区域边界、安全计算环境三层纵深防御。

两条约束的交集是：**信创组件自身必须具备等保三级所需的安全能力**（数据库审计与国密、操作系统访问控制、消息中间件传输加密），而非“信创了再外挂安全”。

### 1.2 与项目基线的对齐关系

本方案不再另起技术栈，而是以《项目说明》的既有基线为准：JDK 25、Spring Boot 4.1.x、Spring Cloud 2025.1.x（Oakwood）、Spring Cloud Alibaba 2025.1.0.0、Nacos、Spring Cloud Gateway、OpenFeign、Sentinel、Seata、RocketMQ、MyBatis-Plus、Valkey、OceanBase、Flyway，可观测性采用 Categraf + 夜莺 N9E + GreptimeDB。信创适配的工作重心，是把这条开源基线**在信创 OS + 国产 JDK + 国产数据库上完成端到端验证**，并对无法直接满足等保项的能力做组件级补强，而不是替换成另一套栈。

> **版本对齐风险**：Spring Cloud Alibaba 2025.1.0.0 正式 BOM 声明适配 Boot 4.0.x + Cloud 2025.1.x；对 Boot 4.1 的兼容分支已就绪但正式 BOM 尚未发布。选型阶段必须锁定“Boot 4.1.x + Cloud 2025.1.x + Alibaba 兼容分支/正式 BOM”这一组合的联合验证结果，避免“各自在册、组合不通”。


## 二、总体架构

### 2.1 分层架构

采用**微服务 + 容器化**，分五层：

| 层级 | 选型方向（对齐项目基线） | 等保三级对应 |
|---|---|---|
| **硬件/芯片层** | 海光 C86、鲲鹏 ARM、龙芯（均须在信创名录内） | 物理环境安全、设备冗余 |
| **操作系统层** | 银河麒麟高级服务器 V10/V11、统信 UOS 服务器版 | 安全计算环境（主机加固、漏洞管理） |
| **数据层** | **OceanBase**（核心关系库，支持国密、审计、三权分立）；**Valkey**（信创适配发行版）作缓存 | 数据完整性、保密性、备份恢复 |
| **微服务运行时/中间件层** | **国产 JDK**（毕昇/Dragonwell 等完成 JDK 25 适配的发行版）+ Spring Boot 内嵌容器；Nacos、Gateway、RocketMQ、Seata、Sentinel 均须完成信创 OS + 国产 JDK 兼容验证 | 安全通信、边界防护 |
| **应用层** | Spring Boot 4.1.x / Spring Cloud 2025.1.x 微服务，MyBatis-Plus 持久层，Flyway 迁移 | 身份鉴别、访问控制、安全审计 |

> **关于传统应用服务器中间件**：在 Spring Cloud 微服务架构下，服务以可执行 JAR + 内嵌容器部署，东方通 TongWeb / 宝兰德 BES 不再是部署必需项。信创适配的重心转移到“**国产 JDK + 信创 OS + 内嵌容器**”链路。若项目合规口径强制要求国产应用服务器，可将服务打包为 WAR 部署至 TongWeb/BES，但须额外完成其与 Spring Boot 4.1.x 的兼容验证，并作为独立选型项评估，不纳入默认基线。

### 2.2 微服务拓扑与边界

共 8 个业务服务，`gateway/` 为独立 API 入口（不计入业务服务）。边界纪律是架构基线的一部分，开发方案必须逐条落地：

| 服务 | 职责 | 边界纪律（开发约束） | 离线职责 |
|---|---|---|---|
| **onecard-account-service** | 账户与卡务：余额、状态、冻结/解冻、介质生命周期 | **在线资金唯一权威源**；余额变更只能在此事务边界内发生 | 离线补传流水的最终入账与日终对账 |
| **onecard-transaction-service** | 消费、充值入账的编排与流水记录 | 发起交易、**幂等受理离线补传**；**不持有余额写权限** | 离线消费补传的幂等校验（键：`terminal_id:local_seq_no`） |
| **onecard-payment-adapter-service** | 微信/支付宝/银联/NFC 圈存适配、路由、签名验签、回调 | 防腐层，隔离外部渠道；与 `gateway/` 语义彻底区分 | 无 |
| **onecard-clearing-service** | 日终对账、商户清分、差错处理、结算报表 | **不参与实时链路**；内部按能力域拆分（见 §6.5） | 离线终端流水与在线交易一并纳入对账输入 |
| **onecard-notification-service** | 短信、Push、微信模板消息统一出口 | 横向支撑，无资金逻辑 | 无 |
| **onecard-risk-service** | 限额、频次、黑名单、异常模式拦截 | **实时前置服务**，同步嵌入交易链路 | 离线补传交易同样经过风控，不因“离线”绕过 |
| **onecard-access-service** | 门禁权限模型、**离线策略快照**生成与签发、通行审计 | 不处理人员主数据、不处理资金、不与控制器长连接 | 快照签名与**最大离线有效期**管理；通行记录接收 |
| **onecard-device-service** | 多协议通道（TCP/HTTP/MQTT）、**设备影子**、在线状态、批量下发与回传调度 | **只负责可靠送到与可靠取回**，不参与权限或扣款决策 | 回传队列**按业务语义隔离**，消费流水优先级最高 |

`gateway/` 只做统一鉴权、全局限流和基础路由，**不得出现直连账户/交易数据库的 `mapper/` 与 `entity/`**；所有资金与门禁业务请求经网关路由至对应服务。跨服务共享对象放 `apis/*-api`，禁止直接依赖其他服务的内部实现模块；业务服务不直接共享数据库表。

### 2.3 在线/离线的总体原则

架构必须同时满足“**在线时资金强一致，离线时业务不中断**”，总体原则是“**在线收敛、离线有界**”：

1. **在线资金的唯一权威源是账户服务**，余额扣减的强一致性收敛在 `onecard-account-service` 的事务边界内；交易服务只编排、不写余额。
2. **离线余额的权威下放至终端，但本地权威不等于本地免责**：断网期间终端本地记账是扣款成功与否的唯一依据；联网后终端流水作为**待验证输入**进入账户服务对账链路，而非默认信任。
3. **门禁离线与消费离线的事务语义根本不同，不得共用补传重试机制**：门禁离线是“放行缓存”（可乱序、可合并），消费离线是“记账恰好一次”（必须幂等、建议保序、失败立即可见）。


## 三、信创技术栈选型（对齐项目基线）

### 3.1 技术基线

以《项目说明》为准，锁定以下组合并逐项完成信创适配验证：

| 类别 | 选型 | 信创/等保验证要点 |
|---|---|---|
| JDK | **JDK 25**（Boot 4.x 最低 17，官方推荐生产用 25 LTS），选用国产 JDK 发行版（毕昇/Dragonwell 等已完成目标版本适配者） | 与 Boot 4.1/Cloud 2025.1 兼容；JVM 安全基线 |
| 框架 | **Spring Boot 4.1.x + Spring Cloud 2025.1.x（Oakwood）** | 版本列车对齐；禁止跨列车混用 |
| 微服务套件 | **Spring Cloud Alibaba 2025.1.0.0**（注意对 Boot 4.1 的兼容分支状态） | Nacos/Sentinel/Seata 联合验证 |
| 注册/配置 | **Nacos** | 信创 OS + 国产 JDK 运行验证；配置加密 |
| 网关 | **Spring Cloud Gateway** | 统一鉴权、全局限流、`response-timeout` 显式配置 |
| 服务调用 | **OpenFeign** | 必须配 `fallback`/`fallbackFactory` 与超时 |
| 熔断限流 | **Sentinel** | 规则持久化到 Nacos，禁止仅存内存 |
| 分布式事务 | **Seata** | 与 OceanBase 的事务模式联合压测；注意 AT 模式对国产库的适配 |
| 消息 | **RocketMQ** | 传输加密；消费幂等；离线补传削峰 |
| 持久层 | **MyBatis-Plus** | 禁止 `SELECT *`；批量操作走批量接口 |
| 缓存 | **Valkey**（信创适配发行版） | 敏感数据不明文入缓存；连接池与超时显式配置 |
| 数据库 | **OceanBase** | 国密 SM2/SM3/SM4、细粒度审计、三权分立；Oracle/MySQL 语法兼容度评估 |
| 迁移 | **Flyway** | 迁移脚本入库管理，禁止手改线上库 |
| 可观测 | **Categraf + 夜莺 N9E + GreptimeDB** | 指标入库、告警可触发；配置落盘 |

### 3.2 关键组件选型要点

**数据库（OceanBase）**：一卡通核心数据特征是“高并发短事务 + 批量清结算 + 强一致性”。选型须重点验证三点：（1）**Oracle/MySQL 语法兼容度**，降低 MyBatis-Plus 映射改造量；（2）**迁移工具链完整性**，覆盖评估、转换、同步、校验全流程，并与 Flyway 的版本化迁移衔接；（3）**等保三级内置能力**，包括 SM2/SM3/SM4 国密支持、细粒度审计、三权分立（系统管理员/安全管理员/审计管理员）。分布式事务能力须在选型阶段用 Seata + OceanBase 完成压测，不能只信厂商单方声明。

**缓存（Valkey）**：选用信创名录内的 Valkey 发行版或基于 Valkey 的兼容产品；敏感字段（卡号、身份证号）不得明文入缓存，应用层先用 SM4 加密再写入；连接池、超时、最大连接数显式配置，禁止依赖默认值。

**微服务运行时**：国产 JDK 与 Spring Boot 4.1.x、Spring Cloud 2025.1.x、Alibaba 兼容分支必须做**联合适配验证**。Spring Boot 内嵌容器在信创 OS 上的线程模型、文件句柄、时区/时钟行为须纳入实验室用例。

**CPU 与操作系统**：优先选择已获**安全可靠测评等级**的产品（如银河麒麟高级服务器 V11 SP1 已获评安全可靠Ⅱ级；鲲鹏 920、海光 C86-4G、龙芯 3C5000L 均在信创名录内）。必须确认目标版本与 OceanBase、国产 JDK、RocketMQ、Nacos 的**兼容矩阵**，避免“在册但不兼容”。


## 四、等保三级安全设计

### 4.1 安全通信网络

核心控制项：**冗余架构 + 传输加密 + 流量审计**。核心链路与关键设备双机热备/多副本（K8s 多副本 + 反亲和），避免单点故障；跨越不可信区域的通信启用加密传输；全流量审计覆盖 IPv4 与 IPv6。

终端到平台的通信是一卡通安全的关键。刷卡终端、人脸识别设备、圈存机分布在物理环境不可控区域，须落实：

- 终端与平台之间使用**国密 SM4** 对交易报文做会话加密，每笔交易使用不同会话密钥；
- 平台侧部署**双向认证**，终端证书基于 **SM2** 签发，防止伪终端接入；
- 设备通信网关实施**白名单 + 协议深度解析**，阻断异常指令；
- RocketMQ、Nacos 等组件间通信启用传输加密；消息体中的敏感字段在应用层再做 SM4 加密，形成“通道加密 + 载荷加密”双层。

### 4.2 安全区域边界

平台划分为**核心交易区、管理服务区、终端接入区、外联区**四个安全域，域间通过下一代防火墙实施访问控制，关键边界部署 IPS 与 WAF。

针对一卡通特有风险，边界防护须额外关注：

- **清分清算接口**：与银行、第三方支付、财务系统的对接是资金安全关键节点，须实施**接口级鉴权 + 交易签名 + 重放攻击防护**（时间戳 + nonce + 签名）；
- **终端接入边界**：门禁控制器、水控器、消费机等大量物联网终端通过专网或 VPN 接入，边界处部署**物联网协议深度检测**，而非仅做 IP 层过滤；
- **网关边界**：Spring Cloud Gateway 统一鉴权与全局限流，服务内不重复实现鉴权；网关路由显式配置 `response-timeout`，禁止依赖默认值。

### 4.3 安全计算环境（应用安全）

这是等保三级控制项最密集、与一卡通业务耦合最深的部分。

**身份鉴别**：管理员和特权用户采用**双因素认证**（口令 + 动态令牌或 USB Key）。一卡通涉及资金操作，对财务清算岗位额外叠加**操作密码二次确认**。登录失败处理、会话超时自动退出、口令复杂度与定期更换必须落地。禁止默认口令上线，默认账号必须重命名或删除。

**访问控制**：基于 RBAC 实施最小权限。消费扣款、余额调整、清分规则变更等敏感操作与普通查询严格分离，实施**职责分离**（制单与审核不能为同一人）。服务间调用以 Nacos 服务发现 + 网关统一鉴权为准，禁止硬编码地址；`onecard-transaction-service` 在代码与库权限两个层面均不得持有账户余额写权限。

**安全审计**：审计覆盖每个用户，记录用户标识、事件类型、时间、结果等关键要素，审计日志**留存不少于 6 个月**（部分行业实践要求 180 天以上）。一卡通场景下列事件必须进入审计范围：账户开户/销户、余额变动、消费撤销/冲正、清分规则修改、管理员登录与权限变更、终端设备注册/注销、离线补传的 `NEED_REVIEW` 标记与人工复核结论。审计记录写入**只追加的审计存储**或独立审计库，防止非授权删除和修改；OceanBase 的审计能力与独立审计库形成双保险。

### 4.4 数据安全与密码应用（密评衔接）

等保三级系统涉及身份信息、消费记录、行为轨迹等敏感数据，须实施加密、脱敏、备份与审计的完整链条；等保三级通常触发密评要求，密评与等保须**同步规划、同步建设、同步运行**。

国密算法在一卡通中的分工：

- **SM2（非对称）**：终端证书签发、数字签名与验签、身份认证令牌、门禁策略快照签名；
- **SM3（杂凑）**：交易流水完整性校验，为每笔消费生成“数字指纹”；
- **SM4（对称）**：敏感字段加密存储（卡号、身份证号）、传输通道加密、会话密钥加密、缓存敏感字段加密、消息体敏感字段加密。

密评量化口径通常要求**得分 ≥ 60 且无高风险项**，等保三级及以上系统每年至少开展一次密评。方案设计阶段就把密码应用纳入架构：终端证书体系、快照签名验签链路、密钥管理（建议独立 KMS 或密码机）在选型阶段一并确定，而非测评前补救。

### 4.5 安全管理中心

部署**日志审计平台 + 堡垒机 + 态势感知**的集中管控组合，并与项目可观测性栈衔接：

- **堡垒机**：管控所有运维操作并全程审计；数据库直连、清分脚本执行、配置变更必须经过堡垒机，禁止绕过；
- **日志审计平台**：汇聚网络设备、安全设备、主机、数据库、应用的全量日志，留存 ≥ 6 个月；应用侧 SLF4J 日志中的关键链路带 `traceId`（由网关/MDC 透传，不自行生成），敏感信息（手机号、身份证、密码、token）禁止打印；
- **态势感知**：异常行为实时告警与联动处置；与夜莺 N9E 告警引擎分工明确——N9E 负责指标类告警，态势感知负责安全事件类告警，二者告警通过统一通道汇聚，避免“两套告警各说各话”。


## 五、微服务工程规范（落地约束）

本节把《项目说明》中的工程纪律固化为开发方案的验收项，评审与 CI 逐条检查。

### 5.1 工程结构与依赖纪律

- 模块结构严格按 `common / gateway / apis / services / sql / docs / docker / deploy/monitoring / scripts / tools / tests/performance / deploy/k8s` 组织；
- 跨服务共享对象只放 `apis/*-api`，禁止直接依赖其他服务的内部实现模块；`gateway/` 不含业务 `mapper/entity`；业务服务不直接共享数据库表；
- 禁止编辑 `target/` 与自动生成代码（MapStruct 实现、代码生成器输出）；
- 每个服务引入 `spring-boot-starter-actuator` 与 `micrometer-registry-prometheus`，`/actuator/health` 纳入数据库、Valkey、Nacos 等关键依赖健康指示器。

### 5.2 编码与 DTO 规范

- 类名 PascalCase、方法/变量 camelCase、常量 UPPER_SNAKE_CASE；
- 使用 `record` 或显式 DTO 承载请求/响应，**禁止把 `entity` 暴露给接口**；
- 依赖注入优先构造器注入，禁止字段注入；Lombok 统一 `@RequiredArgsConstructor` + `@Slf4j`；
- 时间统一 `java.time`（`LocalDateTime`/`Instant`），禁止 `java.util.Date`；金额统一 `BigDecimal`，禁止 `double`/`float`；
- 同一用途只允许一个 DTO，禁止 `XxxDTO`/`XxxDto`/`XxxRequest` 别名类混用；入参 `XxxDTO`（写）/`XxxQuery`（查），出参 `XxxVO`；禁止用 `@JsonAlias`/`@JsonProperty` 堆别名，兼容走网关适配层或接口版本；
- 禁止空 catch、禁止捕获 `Exception` 吞掉不处理；Controller 不写业务逻辑。

### 5.3 接口与可用性

- 统一返回体 `Result<T>`、统一异常 `BizException` + `@RestControllerAdvice`；入参校验用 `jakarta.validation` + `@Validated`，禁止手写大量 if 判空；
- 接口路径统一 `/api/<服务名>/<资源>`，动词用 HTTP 方法表达；分页用统一 `PageQuery`/`PageResult`；
- Feign 客户端必须显式配置 `fallback`/`fallbackFactory` 与 `connectTimeout`/`readTimeout`，降级返回统一 `Result` 失败结构，禁止异常穿透；
- 写接口必须支持幂等：由调用方传幂等键或业务天然幂等，幂等逻辑落在 Service 层并在接口文档注明。**离线消费补传的幂等键 `{terminal_id}:{local_seq_no}` 必须在接口设计第一天落定**，这是不可后补的架构约束；
- 接口变更兼容优先：新增字段允许，删除/改类型/改语义走 `/v2/...` 或新接口；对外 DTO 变更同步更新 `apis/*-api` 并跑通调用方编译；
- 上线前提供接口冒烟用例，冒烟不过不允许发布。

### 5.4 数据库与迁移

- 表名、字段名 snake_case，禁止保留字；每张表必须有主键、`create_time`、`update_time`；
- 禁止 `SELECT *`，查询字段显式列出；禁止循环中执行 SQL，批量走 `foreach`/批量接口；分页查询必须有明确排序字段；
- 表结构变更用 **Flyway** 迁移脚本管理，按服务放在 `sql/`，禁止手改线上库；
- 账户与交易在第一阶段**同库同事务**部署（见 §7），但代码层仍保持服务边界，不为图方便跨服务直连表。

### 5.5 可观测性

- Actuator 仅暴露 `health,info,prometheus`，**禁止 `*`**（会暴露 `env`、`heapdump`、`shutdown` 等敏感端点）；
- 应用侧不挂 Java agent，JVM/HTTP/连接池/线程池指标由 Actuator Prometheus 端点提供，Categraf `input.prometheus` 抓取，`labels` 必填 `application`（值为服务名），供夜莺按应用区分大盘；
- 夜莺时序库配置为 **GreptimeDB**，写入走 `[[Pushgw.Writers]]`，查询侧数据源选 “Prometheus like”；写入端点固定 `http://greptimedb:4000/v1/prometheus/write`，查询数据源 `http://greptimedb:4000/v1/prometheus`，改端口须同步 compose、夜莺配置、数据源三处；
- 告警规则从夜莺「集成中心」SpringBoot 模板导入后默认停用，先确认指标入库再逐条启用；新增服务必须同时提交 Categraf 采集配置、夜莺 `application` 标签值、该服务告警规则，**只加服务不加采集配置视为未完成**；
- 监控栈统一由 `deploy/monitoring/docker-compose.yml` 编排（n9e/categraf/greptimedb 同一 compose），夜莺数据源、告警规则、大盘以 JSON 落盘到 `deploy/monitoring/n9e/`，**禁止只在 UI 改而不落盘**；
- 新增自定义 Micrometer 指标时，指标名与标签同步登记到夜莺告警规则/大盘，避免口径分裂。

### 5.6 测试要求

分层测试，每层只测自己该测的：

- **Service 层**：JUnit 5 + Mockito，隔离 Mapper 与 Feign；每个 public 方法覆盖正常路径 + 边界值 + 一个异常路径；
- **Controller 层**：`@WebMvcTest` + `MockMvc`，校验参数绑定、`@Validated` 生效、全局异常处理返回结构，不启动完整容器；
- **Feign 客户端**：WireMock/MockWebServer 模拟下游，断言请求路径、方法、请求体、超时与降级逻辑，禁止单测发起真实远程调用；
- **集成测试**：`@SpringBootTest` + Testcontainers（OceanBase/Valkey/Nacos 按需），只覆盖跨层关键链路；
- **接口冒烟**：每服务提供 `XxxApiSmokeTest`，启动容器后依次请求核心接口 + `/actuator/health`，断言 HTTP 200 且 `Result.code` 成功，作为 CI 必过项；
- **性能冒烟**：`tests/performance/` 下 k6 脚本使用 ESM，地址从 `__ENV.BASE_URL` 读取，`options.thresholds` 至少包含 `http_req_failed: ['rate<0.01']`、关键接口 `http_req_duration: ['p(95)<500']`、`checks: ['rate>0.99']`；**只写 `check()` 不配阈值视为无效**（checks 不影响退出码，阈值才影响）；数据准备与清理必须幂等；
- 修改 `common`/`api` 后运行全量测试确认无回归；禁止为通过测试放宽断言、禁止删除已有测试让流水线变绿；CI 禁止 `-DskipTests`。


## 六、一卡通核心业务适配

### 6.1 在线资金强一致

消费扣款、余额更新、流水记录须在同一事务中完成。第一阶段 `onecard-account-service` 与 `onecard-transaction-service` **同库同事务部署**，由账户服务在自身事务边界内完成余额变更，交易服务只编排与记录流水，**不持有余额写权限**（代码层与库权限双重约束）。Seata 用于跨服务编排场景（如支付适配回调入账），但资金核心链路优先走本地事务，减少分布式事务面。选型阶段须用 OceanBase + Seata 完成高并发压测，性能基线可参考国产库在同类场景的实测数据，但**以本项目压测结果为准**。

### 6.2 消费离线：本地权威 + 幂等补传

**权威点声明**：离线期间消费余额权威在终端本地，此决策写入架构基线，不作为部署期可选项。

**幂等键**：`{terminal_id}:{local_seq_no}`，`local_seq_no` 是终端本地单调递增序号，**不是时间戳**（时间戳在时钟回拨时会产生碰撞键）。同一笔离线交易无论重传多少次，`onecard-transaction-service` 以该键做唯一性检查，云端只入账一次。

**关键纪律**：

- **落盘先于提示**：终端识别成功不等于记账成功，必须先将交易写入本地持久化存储（SQLite/Realm/LevelDB + WAL），落盘成功后才显示“扣款成功”；提示先于落盘是窗口纠纷的常见根因；
- **补传只写交易，不写主数据**：人员信息、账户状态、门禁权限等主数据不得通过消费补传通道回传，避免补传通道演变成第二条主数据写入路径；
- **补传后必须经过风控**：离线期间无法实时执行的限额、频次、超额检查，在补传时由 `onecard-risk-service` 同步执行；风控不通过不阻断补传受理，但将交易标记为 `NEED_REVIEW` 进入人工复核队列，**不得静默入账**；
- 终端侧须防范**时钟回拨**（补传顺序错乱、幂等键冲突）与**余额文件损坏**（透支/负余额），由本地账本 WAL + 服务端补传风控兜底，不假设终端永不故障。

### 6.3 门禁离线：策略快照 + 有界自主

**策略快照**：`onecard-access-service` 在设备在线时生成并签名快照，经 `onecard-device-service` 下发至门禁控制器。快照内容包括该门组授权人员标识列表、有效时段规则、版本号、签发时间、**最大离线有效期**。完整性与防篡改由国密体系保障：PSAM 安全模块 + SM2/SM3/SM4 用于签名和加密，设备端验签通过后才载入本地决策引擎。快照必须在设备本地完整缓存，不能依赖云端临时下发，否则断网瞬间决策即失效；设备影子只保存状态差异，**不能替代端侧离线决策数据**。

**有界离线**：超过最大离线有效期后，控制器必须执行 **fail-closed**（拒绝常规凭证）或仅允许应急凭证通行，不得无限期信任陈旧白名单。恢复连接后的同步顺序确定：**先校准时钟 → 再拉取最新快照（验签）→ 最后按序补传通行记录**；时钟校准必须先于快照拉取，否则有效期判断可能在错误时钟下失效。

**补传语义**：通行事件可乱序、可按时间戳排序、可合并相同门状态的重复事件；与消费流水的“幂等 + 保序”根本不同，**禁止共用同一套补传重试机制**。

### 6.4 设备接入：通道统一、语义隔离

`onecard-device-service` 只负责协议适配与可靠投递，不参与“能不能进门”“扣没扣钱”的业务决策。三套回传队列**不得共用同一 MQTT 主题与同一重试 backoff**：

| 队列 | 载荷 | 重试策略 | 失败可见性 | 优先级 |
|---|---|---|---|---|
| **消费流水** | 金额、幂等键、本地流水号 | 必须幂等，按终端保序 | 窗口立刻感知 | 最高 |
| **人证核验** | 会话、证摘要、比对分 | 可延迟 | 前台可改人工 | 中 |
| **通行事件** | 门、人、结果 | 可合并相同门状态 | 闸机口排队感知较低 | 低 |

若消费流水与人证核验、通行日志共用同一 MQTT 主题和同一 backoff，食堂高峰消费补传会被人证与通行流量挤成超时，窗口端扣款确认延迟直接引发纠纷。通道层可统一接入，但**持久化保证与重试优先级必须按队列隔离**；RocketMQ 按队列拆分 topic/消费者组，消费流水队列配置独立线程池与更高消费并发。

### 6.5 清结算内部粒度

`onecard-clearing-service` 保持清结算业务域归属，内部不得建成“什么都在做的批处理单体”，按能力域组织为三个职责单一的组件/子部署单元：

| 子能力 | 职责 | 幂等/一致性约束 |
|---|---|---|
| **轧差/清算** | 按清算对象汇总交易、计算应收应付净额 | 输入为已确认交易流水，不直接读写账户余额 |
| **余额一致性校验/对账** | 将离线终端流水、在线交易、渠道回调三者交叉核对 | 差异分类：重复、缺失、金额不符，分别进入自动冲正或人工队列 |
| **幂等账务落库** | 将清算结果幂等写入账务 | 幂等键基于 `business_id + seq_no`，幂等窗口覆盖最长对账周期 |

**报表与分析类查询不得跑在清结算联机库上**，只读副本或数仓是唯一承载位置。**对账输入必须从第一天起就包含离线补传流水**——离线补传的缺失会在第一笔网络抖动重试时暴露为账实不平，无法靠后期对账修补。


## 七、实施路径

**第一阶段：选型与实验室验证（1—2 个月）** 。锁定“国产 JDK 25 + 信创 OS + OceanBase + Valkey + Nacos/Gateway/RocketMQ/Seata/Sentinel + Boot 4.1.x/Cloud 2025.1.x/Alibaba 兼容分支”的具体版本组合，完成功能、性能、兼容、安全四类用例，要求厂商提供**目标组合的联合适配报告**与压测数据。重点验证 OceanBase 语法兼容度、Flyway 迁移链路、Seata 与 OceanBase 的事务适配、国产 JDK 与 Boot 4.1 的运行时行为。同时完成等保三级差距分析，把安全能力纳入采购要求而非后补。

**第二阶段：主链路（账户 + 交易 + 风控 + 设备 + 门禁）** 。`account-service` 与 `transaction-service` 同库同事务部署，`risk-service` 独立轻量启动，`device-service` 与 `access-service` 随门禁场景就位。**离线消费幂等键 `{terminal_id}:{local_seq_no}` 必须在接口设计第一天落定**；门禁**策略快照最大离线有效期**与 fail-closed 规则同步确定。同步开展密评方案设计（终端证书、快照签名、密钥管理）。

**第三阶段：支付适配与通知**。`payment-adapter-service` 独立部署，`notification-service` 轻量上线；两者不参与离线主链路，可在主链路稳定后并行推进。同步完成支付渠道接口的签名验签与重放防护。

**第四阶段：清结算拆分与双轨测评（2 个月）** 。`clearing-service` 在交易量积累后按 §6.5 三项子能力逐步拆分；日终对账可先以批处理任务运行，但对账输入从第一天包含离线补传流水。信创环境与原环境双轨并行、增量同步保数据一致；试运行稳定后启动等保三级测评与密评，确保测评前技术控制项与管理控制项全部闭环。


## 八、关键风险提示

信创与等保三级双重约束下，最大的实施风险不是单一组件功能缺失，而是 **“适配链条断裂”** ——某个层级（如中间件）看似在信创名录中，但与上下层组件兼容性未经联合验证，上线后出现会话丢失、连接池异常或性能骤降。应对策略：

1. **坚持目标组合的联合适配报告**：Nacos/RocketMQ/Seata 与国产 JDK、OceanBase、信创 OS 的联合验证，不接受各组件独立出具的兼容声明；
2. **实验室端到端压测**：高并发消费、批量清分、离线补传洪峰、门禁快照批量下发四类场景必须压测；
3. **版本列车对齐**：Boot 4.1.x + Cloud 2025.1.x + Alibaba 兼容分支的组合风险单独跟踪，正式 BOM 发布前不锁定为生产基线；
4. **安全能力前置**：OceanBase 国密/审计/三权分立、终端 SM2 证书体系、快照签名链路在选型阶段确定，密评与等保同步规划；
5. **离线语义不可后补**：消费幂等键与门禁快照最大有效期是架构级约束，缺失后无法靠对账修复第一笔网络抖动带来的账实不平——评审时作为一票否决项检查。
