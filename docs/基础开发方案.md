# 一卡通平台基础开发方案（信创适配与安全控制草案）

**版本**：2.0  
**日期**：2026-11-02  
**定位**：本方案是信创适配、安全建设与一卡通业务实现的工程草案。系统定级、等保/密评适用性、产品认证状态及测评口径尚待专业评估；文中三级控制项仅为候选设计参考，不代表系统已定级为三级或已满足测评要求。本文不要求填写个人或部门责任方，也不替代正式合规结论或厂商目标组合认证。当前 Maven 版本只代表可构建的工程基线，目标运行组件以阶段 0 联合验证结果为准。服务边界和执行顺序分别以《微服务划分》和《开发阶段规划》为准。


## 一、方案定位与候选合规/安全基线（适用性待确认）

### 1.1 候选建设目标（适用性待确认）

- **信创方向**：若项目最终要求信创适配，从芯片、操作系统、数据库、缓存、消息、微服务运行时到应用层形成可验证的目标组合；具体目录、产品、版本和适用要求待项目确认。
- **安全控制方向**：若最终确认适用等保三级或相关测评要求，再以正式定级和专业评估结果确定控制范围；本草案中的控制项不构成适用性结论。

若上述目标适用，产品能力、密码应用、审计及边界控制需要在目标环境联合验证；品牌或单组件声明不能代替目标组合验证。

### 1.2 与项目基线的对齐关系

本方案以《项目说明》列出的目标组件为候选基线：JDK 25、Spring Boot 4.0.0、Spring Cloud 2025.1.0、Spring Cloud Alibaba 2025.1.0.0、Nacos、Gateway、OpenFeign、Sentinel、Seata、RocketMQ、MyBatis-Plus、Valkey、OceanBase、Flyway，以及 Categraf + 夜莺 N9E + GreptimeDB。框架版本按 Alibaba 官方版本表对齐；除工程构建和当前监控栈外，这些组件尚未全部接入本地服务骨架。生产适用性须以目标环境联合验证结果为准。

> **版本对齐**：根 POM 已按 Spring Cloud Alibaba 官方版本表采用 Spring Boot 4.0.0、Spring Cloud 2025.1.0 和 Alibaba 2025.1.0.0。该对应关系和本地复测结果见阶段 0 组件矩阵；它不等同于生产环境适配结论。


## 二、总体架构

### 2.1 分层架构

采用**微服务 + 容器化**，分五层：

| 层级 | 选型方向（对齐项目基线） | 候选安全控制映射（适用性待确认） |
|---|---|---|
| **硬件/芯片层** | 海光 C86、鲲鹏 ARM、龙芯（均须在信创名录内） | 物理环境安全、设备冗余 |
| **操作系统层** | 银河麒麟高级服务器 V10/V11、统信 UOS 服务器版 | 安全计算环境（主机加固、漏洞管理） |
| **数据层** | **OceanBase**（核心关系库，支持国密、审计、三权分立）；**Valkey**（信创适配发行版）作缓存 | 数据完整性、保密性、备份恢复 |
| **微服务运行时/中间件层** | 国产 JDK 发行版与 Spring Boot 内嵌容器为候选；Nacos、Gateway、RocketMQ、Sentinel 及可能采用的 Seata，在目标 OS/JDK 具备后联合验证 | 安全通信、边界防护 |
| **应用层** | Spring Boot 4.0.x / Spring Cloud 2025.1.x 微服务，MyBatis-Plus 持久层，Flyway 迁移 | 身份鉴别、访问控制、安全审计 |

> **关于传统应用服务器中间件**：在 Spring Cloud 微服务架构下，服务以可执行 JAR + 内嵌容器部署，东方通 TongWeb / 宝兰德 BES 不再是部署必需项。信创适配的重心转移到“**国产 JDK + 信创 OS + 内嵌容器**”链路。若项目合规口径强制要求国产应用服务器，可将服务打包为 WAR 部署至 TongWeb/BES，但须额外完成其与 Spring Boot 4.0.x 的兼容验证，并作为独立选型项评估，不纳入默认基线。

### 2.2 微服务拓扑与边界

共 8 个业务服务，`gateway/` 为独立 API 入口（不计入业务服务）。边界纪律是架构基线的一部分，开发方案必须逐条落地：

| 服务 | 职责 | 边界纪律（开发约束） | 离线职责 |
|---|---|---|---|
| **onecard-account-service** | 账户与卡务：余额、状态、冻结/解冻、介质生命周期 | **在线资金唯一权威源**；余额及账户账本变更只能在此服务本地事务内发生 | 校验并执行已确认的离线入账；不承担跨来源日终对账 |
| **onecard-transaction-service** | 消费、充值入账的编排与流水记录 | 发起交易、**幂等受理离线补传**；**不持有余额写权限**，不共享账户库表 | 离线消费补传的幂等校验（键：`terminal_id:local_seq_no`）及受理状态维护 |
| **onecard-payment-adapter-service** | 微信/支付宝/银联/NFC 圈存适配、路由、签名验签、回调 | 防腐层，隔离外部渠道；与 `gateway/` 语义彻底区分 | 无 |
| **onecard-clearing-service** | 跨来源日终对账、商户清分、差错处理、结算报表 | **不参与实时链路**；内部按能力域拆分（见 §6.5），不直接写账户余额 | 离线终端流水与在线交易一并纳入对账输入 |
| **onecard-notification-service** | 短信、Push、微信模板消息统一出口 | 横向支撑，无资金逻辑 | 无 |
| **onecard-risk-service** | 限额、频次、黑名单、异常模式拦截 | **实时前置服务**，同步嵌入交易链路 | 离线补传交易同样经过风控，不因“离线”绕过 |
| **onecard-access-service** | 门禁权限模型、**离线策略快照**生成与签发、通行审计 | 不处理人员主数据、不处理资金、不与控制器长连接 | 快照签名与**最大离线有效期**管理；通行记录接收 |
| **onecard-device-service** | 多协议通道（TCP/HTTP/MQTT）、**设备影子**、在线状态、批量下发与回传调度 | **只负责可靠送到与可靠取回**，不参与权限或扣款决策 | 回传队列**按业务语义隔离**，消费流水优先级最高 |

`gateway/` 只做统一鉴权、全局限流和基础路由，**不得出现直连账户/交易数据库的 `mapper/` 与 `entity/`**；所有资金与门禁业务请求经网关路由至对应服务。跨服务共享对象放 `apis/*-api`，禁止直接依赖其他服务的内部实现模块；业务服务不直接共享数据库表。

### 2.3 在线/离线的总体原则

消费终端以在线交易为常态，意外断线时才按策略切到终端本地支付。目标是在在线时资金强一致、断线期间有界可用；离线支付是故障切换，不是日常支付的并行选项。

1. **在线资金的唯一权威源是账户服务**，余额扣减的强一致性收敛在 `onecard-account-service` 的事务边界内；交易服务只编排、不写余额。
2. **离线余额只在断线故障切换期间由终端承载**：终端需通过经批准的断线检测条件后才可本地扣款。余额不足、卡冻结、风控拒绝等业务拒绝不得触发离线绕过；联网后终端流水作为**待验证输入**进入平台入账与对账流程。账户服务负责账本与入账完整性，清结算服务负责跨来源日终对账。
3. **门禁离线与消费离线的事务语义根本不同，不得共用补传重试机制**：门禁审计事件允许乱序到达但须完整保留，只有设备状态快照可合并；消费流水采用至少一次投递、服务端幂等去重，实现业务效果只入账一次，并按终端序号保序。网络不提供端到端恰好一次投递保证。


## 三、信创技术栈候选选型（项目基线待联合验证）

### 3.1 候选技术基线

以《项目说明》为准，锁定以下组合并逐项完成信创适配验证：

| 类别 | 选型 | 信创/等保验证要点 |
|---|---|---|
| JDK | **JDK 25**（Boot 4.x 最低 17，官方推荐生产用 25 LTS），选用国产 JDK 发行版（毕昇/Dragonwell 等已完成目标版本适配者） | 与当前 Boot 4.0/Cloud 2025.1 基线兼容；JVM 安全基线 |
| 框架 | **Spring Boot 4.0.x + Spring Cloud 2025.1.x（Oakwood）** | 与 Alibaba 2025.1.0.0 官方对应；禁止跨列车混用 |
| 微服务套件 | Spring Cloud Alibaba 2025.1.0.0（当前构建基线；官方版本依据待供应商补充） | Nacos/Sentinel 联合验证；仅在阶段 0 决定采用 Seata 后验证 Seata |
| 注册/配置 | **Nacos** | 信创 OS + 国产 JDK 运行验证；配置加密 |
| 网关 | **Spring Cloud Gateway** | 统一鉴权、全局限流、`response-timeout` 显式配置 |
| 服务调用 | **OpenFeign** | 必须配 `fallback`/`fallbackFactory` 与超时 |
| 熔断限流 | **Sentinel** | 规则持久化到 Nacos，禁止仅存内存 |
| 分布式事务 | **Seata（候选；是否需要待阶段 0 决策）** | 如选择 Seata，再与 OceanBase 联合验证具体事务模式；不预设必须引入 |
| 消息 | **RocketMQ** | 传输加密；消费幂等；离线补传削峰 |
| 持久层 | **MyBatis-Plus** | 禁止 `SELECT *`；批量操作走批量接口 |
| 缓存 | **Valkey**（信创适配发行版） | 敏感数据不明文入缓存；连接池与超时显式配置 |
| 数据库 | **OceanBase** | 国密 SM2/SM3/SM4、细粒度审计、三权分立；Oracle/MySQL 语法兼容度评估 |
| 迁移 | **Flyway** | 迁移脚本入库管理，禁止手改线上库 |
| 可观测 | **Categraf + 夜莺 N9E + GreptimeDB** | 指标入库、告警可触发；配置落盘 |

### 3.2 关键组件选型要点

**数据库（OceanBase）**：一卡通核心数据特征是“高并发短事务 + 批量清结算 + 强一致性”。选型须重点验证三点：（1）**Oracle/MySQL 语法兼容度**，降低 MyBatis-Plus 映射改造量；（2）**迁移工具链完整性**，覆盖评估、转换、同步、校验全流程，并与 Flyway 的版本化迁移衔接；（3）若经评审确认适用相关等级/密码要求，再核验目标产品的 SM2/SM3/SM4、审计和职责分离能力。先由阶段 0 判断跨服务资金链路是否需要分布式事务；只有选定 Seata 后，才执行 Seata + OceanBase 的联合压测，不以依赖存在推定必须采用。

**缓存（Valkey）**：Valkey 及兼容产品为候选项，目标版本、发行版和适用要求待阶段 0 确认；缓存中敏感字段的存放和加密方式按数据分类/密码评审结果决定；连接池、超时、最大连接数在选定产品后显式验证。

**微服务运行时**：国产 JDK 与 Spring Boot 4.0.x、Spring Cloud 2025.1.x、Alibaba 兼容分支必须做**联合适配验证**。Spring Boot 内嵌容器在信创 OS 上的线程模型、文件句柄、时区/时钟行为须纳入实验室用例。

**CPU 与操作系统**：按采购要求核验具体产品、型号、版本和固件的名录/测评状态；本方案不预先认定任何产品已通过认证。必须确认目标版本与数据库、国产 JDK、消息和注册配置组件的**兼容矩阵**，避免只按品牌或产品系列推定兼容。


## 四、安全控制设计要点（适用性及测评口径待确认）

### 4.1 安全通信网络

候选控制项包括冗余、跨信任边界的传输保护和必要审计。生产副本数、双机热备、Kubernetes 编排、网络设备与全流量审计范围尚未选定；须按目标业务可用性、资源和适用要求设计验证。`deploy/k8s/` 当前仅为预留目录，不代表已经选用 Kubernetes。

终端到平台的通信是一卡通安全的关键。刷卡终端、人脸识别设备、圈存机分布在物理环境不可控区域，须落实：

- 评估终端与平台间加密、设备证书/双向认证及算法套件；SM2/SM4 是待验证候选，不代表已选定设备或密码产品；
- 评估设备协议 allowlist、命令校验和网络隔离，与实际终端协议、网段和设备能力共同确定；
- 对 Nacos、消息和服务间通信核对认证/传输保护；敏感载荷保护按数据分类和密码应用评审确定，不预先锁定双层加密实现。

### 4.2 安全区域边界

核心交易、管理、设备接入和外联可作为候选安全域；具体分区、ACL、防火墙、IPS/WAF 的部署边界须等生产网络和适用要求确定后设计，不视作当前已部署拓扑。

针对一卡通特有风险，边界防护须额外关注：

- **清分清算接口**：与银行、第三方支付、财务系统的对接是资金安全关键节点，须实施**接口级鉴权 + 交易签名 + 重放攻击防护**（时间戳 + nonce + 签名）；
- **终端接入边界**：门禁控制器、水控器、消费机等大量物联网终端通过专网或 VPN 接入，边界处部署**物联网协议深度检测**，而非仅做 IP 层过滤；
- **网关边界**：Spring Cloud Gateway 负责外部请求统一鉴权与全局限流；服务间另行实施服务身份认证、授权和网络隔离，不把网关视为服务间调用的唯一安全边界。网关路由显式配置 `response-timeout`，禁止依赖默认值。

### 4.3 安全计算环境（应用安全）

如最终确认适用等保三级或其他相应测评要求，此处将是与一卡通业务耦合较深的控制区域之一；当前仍是候选设计。

**身份鉴别候选**：针对管理员/特权账户评估多因素认证、财务敏感操作复核、失败锁定和会话管理；具体强度与方式由身份源、系统分级、业务风险和现场环境评审确定。任何实际部署不得保留厂商默认凭据。

**访问控制候选**：以 RBAC/最小权限分离敏感资金写操作和普通查询；是否对特定操作实施制单/审核分离按实际岗位与制度确认。Nacos 用于服务发现和配置分发，不作为外部用户身份/授权系统；用户 API 由网关及服务资源授权共同保护，服务间调用另设服务身份和授权。`onecard-transaction-service` 在代码与库权限两个层面均不得持有账户余额写权限。

**安全审计**：审计覆盖用户和服务主体，记录主体标识、事件类型、时间、结果等关键要素。留存时长和存储方式由阶段 0 的定级/合规分析及业务要求确认；可将 6 个月作为待确认的规划值，不在本文中将其声明为通用法定时限。一卡通场景审计范围包括账户开户/销户、余额变动、消费撤销/冲正、清分规则修改、管理员登录与权限变更、终端设备注册/注销、离线补传复核及人工处理结论。审计存储须防止非授权删除和修改，具体方案在目标环境验证。

### 4.4 数据安全与密码应用（密评衔接）

系统涉及身份信息、消费记录和通行轨迹等数据，应先完成数据分类分级与密码应用需求分析。是否需要密评及其范围、周期和实施口径，由阶段 0 按适用的权威要求和专业机构意见确认，并与系统设计同步安排。

国密算法在一卡通中的分工：

- **SM2（非对称）**：终端证书签发、数字签名与验签、身份认证令牌、门禁策略快照签名；
- **SM3（杂凑）**：交易流水完整性校验，为每笔消费生成“数字指纹”；
- **SM4（对称）**：敏感字段加密存储（卡号、身份证号）、传输通道加密、会话密钥加密、缓存敏感字段加密、消息体敏感字段加密。

密评的评分规则、风险判定和复测周期以适用的现行标准及测评机构意见为准，本文不预设分数门槛或周期。终端证书体系、快照签名验签链路和密钥管理方案须在选型阶段确认，并在目标设备及密码产品上验证。

### 4.5 安全管理中心

部署**日志审计平台 + 堡垒机 + 态势感知**的集中管控组合，并与项目可观测性栈衔接：

- **堡垒机**：管控所有运维操作并全程审计；数据库直连、清分脚本执行、配置变更必须经过堡垒机，禁止绕过；
- **日志审计平台**：按阶段 0 确认的留存要求汇聚网络设备、安全设备、主机、数据库、应用日志；应用侧 SLF4J 日志中的关键链路带 `traceId`（由网关/MDC 透传，不自行生成），敏感信息（手机号、身份证、密码、token）禁止打印；
- **态势感知**：异常行为实时告警与联动处置；与夜莺 N9E 告警引擎分工明确——N9E 负责指标类告警，态势感知负责安全事件类告警，二者告警通过统一通道汇聚，避免“两套告警各说各话”。


## 五、微服务工程规范（落地约束）

本节把《项目说明》中的工程纪律固化为开发方案的验收项，评审与 CI 逐条检查。

### 5.1 工程结构与依赖纪律

- 模块结构严格按 `common / gateway / apis / services / sql / docs / docker / deploy/monitoring / scripts / tools / tests/performance / deploy/k8s` 组织；
- 跨服务共享对象只放 `apis/*-api`，禁止直接依赖其他服务的内部实现模块；`gateway/` 不含业务 `mapper/entity`；业务服务不直接共享数据库表；
- 禁止编辑 `target/` 与自动生成代码（MapStruct 实现、代码生成器输出）；
- 每个服务引入 `spring-boot-starter-actuator` 与 `micrometer-registry-prometheus`，`/actuator/health` 纳入数据库、Valkey、Nacos 等关键依赖健康指示器。

### 5.2 编码与 DTO 规范

- 类名 PascalCase、方法/变量 camelCase、常量 UPPER_SNAKE_CASE；
- 使用 `record` 或显式 DTO 承载请求/响应，**禁止把 `entity` 暴露给接口**；
- 依赖注入优先构造器注入，禁止字段注入；Lombok 统一 `@RequiredArgsConstructor` + `@Slf4j`；
- 时间统一 `java.time`（`LocalDateTime`/`Instant`），禁止 `java.util.Date`；金额统一 `BigDecimal`，禁止 `double`/`float`；
- 同一用途只允许一个 DTO，禁止 `XxxDTO`/`XxxDto`/`XxxRequest` 别名类混用；入参 `XxxDTO`（写）/`XxxQuery`（查），出参 `XxxVO`；禁止用 `@JsonAlias`/`@JsonProperty` 堆别名，兼容走网关适配层或接口版本；
- 禁止空 catch、禁止捕获 `Exception` 吞掉不处理；Controller 不写业务逻辑。

### 5.3 接口与可用性

- 统一返回体 `Result<T>`、统一异常 `BizException` + `@RestControllerAdvice`；入参校验用 `jakarta.validation` + `@Validated`，禁止手写大量 if 判空；
- 接口路径统一 `/api/<服务名>/<资源>`，动词用 HTTP 方法表达；分页用统一 `PageQuery`/`PageResult`；
- Feign 客户端必须显式配置 `fallback`/`fallbackFactory` 与 `connectTimeout`/`readTimeout`，降级返回统一 `Result` 失败结构，禁止异常穿透；
- 写接口必须支持幂等：由调用方传幂等键或业务天然幂等，幂等逻辑落在 Service 层并在接口文档注明。**离线消费补传的幂等键 `{terminal_id}:{local_seq_no}` 必须在接口设计第一天落定**，这是不可后补的架构约束；
- 接口变更兼容优先：新增字段允许，删除/改类型/改语义走 `/v2/...` 或新接口；对外 DTO 变更同步更新 `apis/*-api` 并跑通调用方编译；
- 上线前提供接口冒烟用例，冒烟不过不允许发布。

### 5.4 数据库与迁移

- 表名、字段名 snake_case，禁止保留字；每张表必须有主键、`create_time`、`update_time`；
- 禁止 `SELECT *`，查询字段显式列出；禁止循环中执行 SQL，批量走 `foreach`/批量接口；分页查询必须有明确排序字段；
- 表结构变更用 **Flyway** 迁移脚本管理，按服务放在 `sql/`，禁止手改线上库；每个服务独立拥有其 schema 和写入权限；
- 账户账本写入在账户服务本地事务内完成。交易服务通过公开契约编排，不与账户服务共享数据库表或跨服务本地事务；消息/outbox、幂等状态机或其他可靠执行机制须在阶段 0 选定并通过故障测试。

### 5.5 可观测性

- Actuator 仅暴露 `health,info,prometheus`，**禁止 `*`**（会暴露 `env`、`heapdump`、`shutdown` 等敏感端点）；
- 应用侧不挂 Java agent，JVM/HTTP/连接池/线程池指标由 Actuator Prometheus 端点提供，Categraf `input.prometheus` 抓取，`labels` 必填 `application`（值为服务名），供夜莺按应用区分大盘；
- 夜莺时序库配置为 **GreptimeDB**，写入走 `[[Pushgw.Writers]]`，查询侧数据源选 “Prometheus like”；写入端点固定 `http://greptimedb:4000/v1/prometheus/write`，查询数据源 `http://greptimedb:4000/v1/prometheus`，改端口须同步 compose、夜莺配置、数据源三处；
- 告警规则从夜莺「集成中心」SpringBoot 模板导入后默认停用，先确认指标入库再逐条启用；新增服务必须同时提交 Categraf 采集配置、夜莺 `application` 标签值、该服务告警规则，**只加服务不加采集配置视为未完成**；
- 监控栈统一由 `deploy/monitoring/docker-compose.yml` 编排（n9e/categraf/greptimedb 同一 compose），夜莺数据源、告警规则、大盘以 JSON 落盘到 `deploy/monitoring/n9e/`，**禁止只在 UI 改而不落盘**；
- 新增自定义 Micrometer 指标时，指标名与标签同步登记到夜莺告警规则/大盘，避免口径分裂。

### 5.6 测试要求

分层测试，每层只测自己该测的：

- **Service 层**：JUnit 5 + Mockito，隔离 Mapper 与 Feign；每个 public 方法覆盖正常路径 + 边界值 + 一个异常路径；
- **Controller 层**：`@WebMvcTest` + `MockMvc`，校验参数绑定、`@Validated` 生效、全局异常处理返回结构，不启动完整容器；
- **Feign 客户端**：WireMock/MockWebServer 模拟下游，断言请求路径、方法、请求体、超时与降级逻辑，禁止单测发起真实远程调用；
- **集成测试**：`@SpringBootTest` + Testcontainers（OceanBase/Valkey/Nacos 按需），只覆盖跨层关键链路；
- **接口冒烟**：每服务提供 `XxxApiSmokeTest`，启动容器后依次请求核心接口 + `/actuator/health`，断言 HTTP 200 且 `Result.code` 成功，作为 CI 必过项；
- **性能冒烟**：`tests/performance/` 下 k6 脚本使用 ESM，地址从 `__ENV.BASE_URL` 读取，`options.thresholds` 至少包含 `http_req_failed: ['rate<0.01']`、关键接口 `http_req_duration: ['p(95)<500']`、`checks: ['rate>0.99']`；**只写 `check()` 不配阈值视为无效**（checks 不影响退出码，阈值才影响）；数据准备与清理必须幂等；
- 修改 `common`/`api` 后运行全量测试确认无回归；禁止为通过测试放宽断言、禁止删除已有测试让流水线变绿；CI 禁止 `-DskipTests`。


## 六、一卡通核心业务适配

### 6.1 在线资金强一致

账户余额和对应账户账本分录必须在账户服务自身数据库事务中原子提交。交易服务只编排并维护交易状态，通过幂等契约调用账户服务；不共享数据库、不跨服务写表。交易状态与账户入账之间的可靠推进方式须在阶段 0 决定，并测试账户已提交但响应丢失、重复调用、服务重启和消息重复等场景。Seata 是否进入任何资金链路须由目标数据库联合验证和故障/性能数据决定，不能以当前依赖选型预设。

### 6.2 消费支付：在线优先 + 断线故障切换

**默认模式**：终端正常连接时通过 `transaction-service` 和 `account-service` 在线完成风控与扣款。终端本地余额/额度只用于意外断线故障切换，不作为日常支付的第二条余额权威。

**故障切换**：终端仅在链路不可用达到阶段 0 批准的阈值后切换。余额不足、卡冻结、风控拒绝等确定的业务结果保持原拒绝语义，不得进入离线支付。结果未知的在途交易保持待确认，不得转成本地成功；恢复后用原幂等键查询/重试。进入故障切换后，后续新交易可按离线策略受理，并分配各自的新本地序号和幂等键。

**幂等键**：`{terminal_id}:{local_seq_no}`，`local_seq_no` 在首次尝试受理每笔交易前由终端分配并持久化；同一交易的查询、重试和补传保持不变，进入故障切换后的每笔新交易使用新的本地序号和幂等键。它是终端本地单调递增序号，不是时间戳；投递至少一次，通过服务端幂等实现业务效果只入账一次。

**关键纪律**：

- **离线落盘先于提示**：仅在已切换到故障模式且缓存新鲜度、卡状态和已预留离线额度均满足时，终端先将流水写入本地持久化存储（SQLite/Realm/LevelDB + WAL），落盘成功后显示“离线消费已受理，联网对账中”，不得表示平台已完成记账；
- **补传只写交易，不写主数据**：人员信息、账户状态、门禁权限等主数据不得通过消费补传通道回传，避免补传通道演变成第二条主数据写入路径；
- **补传后必须经过风控**：离线期间无法实时执行的限额、频次、超额检查，在补传时由 `onecard-risk-service` 执行。风控拒绝或不可用时不得丢弃终端已确认的流水。`NEED_REVIEW` 对应的账户分录时机、可用余额影响及冲正规则须在阶段 0 明确，避免把“已受理”误当作“已入账”；
- 进入/退出阈值、连续失败数、恢复观察期和防抖策略由阶段 0 确认，避免链路抖动导致模式反复切换。恢复连接后须先同步离线流水，并完成账户入账或保留额/可用余额更新；达到恢复屏障后才允许恢复普通在线扣款，具体策略在阶段 0 决策。
- 终端侧须防范**本地序号回退、账本损坏和额度耗尽**；时钟漂移须单独监控。WAL、终端存储完整性与恢复测试以及服务端补传校验共同控制风险，不假设终端永不故障。

### 6.3 门禁离线：策略快照 + 有界自主

**范围说明**：门禁/核验为二期扩展，本节是待设备和现场验证的架构候选，不是首期实现范围，也不构成对所有门型的最终 fail-open/fail-closed 决定。二期设备选型后、开发前必须按真实门型和消防/疏散要求复核。

**策略快照**：`onecard-access-service` 在设备在线时生成并签名快照，经 `onecard-device-service` 下发至门禁控制器。快照内容包括该门组授权人员标识列表、有效时段规则、版本号、签发时间、**最大离线有效期**。完整性与防篡改由国密体系保障：PSAM 安全模块 + SM2/SM3/SM4 用于签名和加密，设备端验签通过后才载入本地决策引擎。快照必须在设备本地完整缓存，不能依赖云端临时下发，否则断网瞬间决策即失效；设备影子只保存状态差异，**不能替代端侧离线决策数据**。

**有界离线**：超过最大离线有效期后，控制器必须执行 **fail-closed**（拒绝常规凭证）或仅允许应急凭证通行，不得无限期信任陈旧白名单。控制策略必须保留消防、紧急疏散及当地法规要求的生命安全行为，具体 fail-safe/fail-secure 组合按实际门型、现场要求和设备方案验证并记录。恢复连接后的同步顺序确定：**先校准时钟 → 再拉取最新快照（验签）→ 最后按序补传通行记录**；时钟校准必须先于快照拉取，否则有效期判断可能在错误时钟下失效。

**补传语义**：通行审计事件允许乱序到达，但必须以事件 ID 幂等去重并完整保留；仅设备状态快照可以按版本合并。它与消费流水的“业务幂等 + 终端序号保序”使用不同队列和重试策略。

### 6.4 设备接入：通道统一、语义隔离

`onecard-device-service` 只负责协议适配与可靠投递，不参与“能不能进门”“扣没扣钱”的业务决策。三套回传队列**不得共用同一 MQTT 主题与同一重试 backoff**：

| 队列 | 载荷 | 重试策略 | 失败可见性 | 优先级 |
|---|---|---|---|---|
| **消费流水** | 金额、幂等键、本地流水号 | 必须幂等，按终端保序 | 窗口立刻感知 | 最高 |
| **人证核验** | 会话、证摘要、比对分 | 可延迟 | 前台可改人工 | 中 |
| **通行事件** | 门、人员标识、决策结果 | 以事件 ID 去重并完整保留；允许乱序 | 权限审计可见 | 低 |

若消费流水与核验结果、通行审计日志共用同一 MQTT 主题和同一 backoff，食堂高峰消费补传会被其他流量挤成超时，窗口端扣款确认延迟直接引发纠纷。通道层可统一接入，但**持久化保证、审计留存与重试优先级必须按队列隔离**；目标消息产品及协议须经阶段 0 验证，消费流水队列配置独立消费能力。

### 6.5 清结算内部粒度

`onecard-clearing-service` 保持清结算业务域归属，内部不得建成“什么都在做的批处理单体”，按能力域组织为三个职责单一的组件/子部署单元：

| 子能力 | 职责 | 幂等/一致性约束 |
|---|---|---|
| **轧差/清算** | 按清算对象汇总交易、计算应收应付净额 | 输入为已确认交易流水，不直接读写账户余额 |
| **交易一致性校验/对账** | 将离线终端流水、在线交易、渠道回调三者交叉核对；账户账本作为权威核对来源 | 差异分类：重复、缺失、金额不符，分别进入可审计的更正或人工队列 |
| **幂等结算结果提交** | 将清算结果通过账户服务契约提交入账，清结算服务不直接写账户账本 | 幂等键基于 `business_id + seq_no`，幂等窗口覆盖最长对账周期 |

**报表与分析类查询不得跑在清结算联机库上**，只读副本或数仓是唯一承载位置。清结算服务负责跨来源业务对账，账户服务不重复运行同一批对账任务；**对账输入必须从第一天起就包含离线补传流水**。


## 七、实施路径

详细开发次序、阶段交付物和退出条件以 [`docs/开发阶段规划.md`](开发阶段规划.md) 为执行基线。阶段 0 先完成运行组件联合兼容、资金状态机、跨服务事务语义、终端断线故障切换限额、门禁生命安全行为、目标负载和合规适用性确认；之后先建设平台与账户/风控，再建设交易、设备、终端断线故障切换与补传、门禁，最后接入支付、通知、清结算并开展系统级验收。每个业务阶段均包含自动化功能/集成测试、故障恢复验证和与目标负载相符的性能测试，不以服务启动或 Actuator 健康检查代替业务验收。


## 八、关键风险提示

若项目最终确认信创与等保三级要求均适用，最大的实施风险不是单一组件功能缺失，而是 **“适配链条断裂”** ——某个层级（如中间件）看似满足单项条件，但与上下层组件兼容性未经联合验证，上线后出现会话丢失、连接池异常或性能骤降。应对策略：

1. **坚持目标组合的联合适配报告**：已选用的 Nacos/RocketMQ 以及阶段 0 若决定采用的 Seata，与目标 JDK、OceanBase、OS 的联合验证，不接受各组件独立出具的兼容声明；
2. **实验室端到端压测**：高并发消费、批量清分、离线补传洪峰、门禁快照批量下发四类场景必须压测；
3. **版本列车对齐**：当前根 POM 的 Boot/Cloud/Alibaba 版本组合只作构建基线，按阶段 0 核验的官方矩阵与目标环境测试通过后才锁定生产版本；
4. **安全能力前置**：OceanBase 国密/审计/三权分立、终端 SM2 证书体系、快照签名链路在选型阶段确定，密评与等保同步规划；
5. **离线语义不可后补**：消费幂等键与门禁快照最大有效期是架构级约束，缺失后无法靠对账修复第一笔网络抖动带来的账实不平——评审时作为一票否决项检查。
