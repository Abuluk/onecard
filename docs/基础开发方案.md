# 一卡通平台基础开发方案（信创 + 等保三级）

**方案定位**：本方案面向需要同时满足**信息技术应用创新（信创）** 与**网络安全等级保护第三级（等保三级）** 的一卡通平台建设或改造项目。一卡通系统承载身份认证、消费交易、门禁通行、清分清算等核心业务，通常被归入“重要业务系统”，必须同时通过信创适配验证与等保三级测评。以下方案围绕**技术栈选型、安全架构设计、业务功能适配、迁移实施策略**四个维度展开。


## 一、总体架构原则

### 1.1 双合规驱动的架构基线

架构设计须同时满足两条刚性约束：

- **信创约束**：从芯片、操作系统、数据库、中间件到应用层，形成可验证的国产化链路，不接受“局部替换、核心仍依赖非信创组件”的组合。
- **等保三级约束**：遵循“一个中心、三重防护”框架——安全管理中心统一管控，安全通信网络、安全区域边界、安全计算环境三层纵深防御。

两条约束的交集在于：信创组件本身必须具备等保三级所需的安全能力（如数据库的审计与加密、操作系统的访问控制），而非“信创了再外挂安全”。

### 1.2 架构分层

建议采用**微服务 + 容器化**的架构风格，分为五层：

| 层级 | 信创选型方向 | 等保三级对应要求 |
|---|---|---|
| **硬件/芯片层** | 海光（C86）、鲲鹏（ARM）、龙芯（自主指令集）等已入信创名录的CPU | 物理环境安全、设备冗余 |
| **操作系统层** | 银河麒麟高级服务器 V10/V11、统信UOS服务器版 | 安全计算环境（主机加固、漏洞管理） |
| **数据层** | 达梦DM8 / 电科金仓KingbaseES V9 为核心关系库；Redis（信创适配版）为缓存 | 数据完整性、保密性、备份恢复 |
| **中间件层** | 东方通TongWeb / 宝兰德BES（应用服务器）；东方通TongLINK/Q或信创消息队列 | 安全通信、边界防护 |
| **应用层** | Spring Boot / Spring Cloud 微服务框架，适配国产JDK与中间件 | 身份鉴别、访问控制、安全审计 |


## 二、信创技术栈选型

### 2.1 推荐组合（已有多案例验证）

以下组合在2026年已有一卡通场景的规模化落地验证，可作为基础技术基线：

**组合A（教育/校园主流路线）** ：海光CPU + 银河麒麟高级服务器操作系统 + 达梦DM8 + 宝兰德/东方通中间件 + 新开普/新中新一卡通应用。达梦联合海光、麒麟、新华三、新开普发布的“五位一体”方案已完成全链路深度适配调优，覆盖高并发交易、消费支付、数据一致性与容灾备份等核心场景。

**组合B（城市级/高并发路线）** ：鲲鹏或海光 + 麒麟/统信 + 电科金仓KingbaseES + 东方通/宝兰德中间件。北京一卡通清结算系统已基于KingbaseES V9稳定运行近三年，支撑千万级日数据处理与夜间大规模清分结算，验证了国产数据库在城市级核心交易场景的承载能力。

### 2.2 关键组件的选型要点

**数据库**：一卡通的核心数据特征是“高并发短事务 + 批量清结算 + 强一致性”。选型时须重点验证三点：（1）**Oracle/MySQL语法兼容度**，以降低应用改造量；（2）**迁移工具链的完整性**，是否覆盖评估、转换、同步、校验全流程；（3）**等保三级内置能力**，包括SM2/SM3/SM4国密支持、细粒度审计、三权分立（系统管理员/安全管理员/审计管理员）等。

**中间件**：应用服务器中间件须与国产JDK和微服务框架完成兼容性验证。东方通TongWeb和宝兰德BES在金融、教育行业已有信创核心系统案例，需在选型阶段要求厂商提供与所选微服务框架、数据库的联合适配报告。

**CPU与操作系统**：优先选择已获得**安全可靠测评等级**的产品。银河麒麟高级服务器操作系统V11 SP1已获评安全可靠Ⅱ级，鲲鹏920、海光C86-4G、龙芯3C5000L等CPU均在信创名录内。选择时须确认目标版本与数据库、中间件的兼容矩阵，避免“在册但不兼容”的陷阱。


## 三、等保三级安全设计

### 3.1 安全通信网络

核心控制项：**冗余架构 + 传输加密 + 流量审计**。核心链路与关键设备须双机热备，避免单点故障；所有跨越不可信区域的通信须启用加密传输；全流量审计须覆盖IPv4与IPv6。

在一卡通场景中，**终端到平台**的通信安全尤为关键。刷卡终端、人脸识别设备、圈存机等分布在物理环境不可控的区域，建议：

- 终端与平台之间使用**国密SM4**对交易报文进行会话加密，每次交易使用不同会话密钥；
- 平台侧部署**双向认证**，终端证书基于SM2算法签发，防止伪终端接入；
- 对设备通信网关实施**白名单 + 协议深度解析**，阻断异常指令。

### 3.2 安全区域边界

一卡通平台应划分为**核心交易区、管理服务区、终端接入区、外联区**四个安全域，域间通过下一代防火墙实施访问控制，关键边界部署IPS与WAF。

针对一卡通的特有风险，边界防护须额外关注：

- **清分清算接口**：与银行、第三方支付、财务系统的对接接口是资金安全的关键节点，须实施**接口级鉴权 + 交易签名 + 重放攻击防护**；
- **终端接入边界**：大量物联网终端（门禁控制器、水控器、消费机）通过专网或VPN接入，边界处应部署**物联网协议深度检测**，而非仅做IP层过滤。

### 3.3 安全计算环境（应用安全）

这是等保三级控制项最密集、与一卡通业务耦合最深的部分。

**身份鉴别**：管理员和特权用户须采用**双因素认证**（口令 + 动态令牌或USB Key）。一卡通平台涉及资金操作，建议对财务清算岗位额外叠加**操作密码二次确认**。登录失败处理、会话超时自动退出、口令复杂度与定期更换策略必须落地。

**访问控制**：基于RBAC模型实施最小权限，**默认账号必须重命名或删除，默认口令必须强制修改**。一卡通系统中，消费扣款、余额调整、清分规则变更等敏感操作须与普通查询操作严格分离，实施**职责分离**（如制单与审核不能为同一人）。

**安全审计**：审计覆盖每个用户，记录用户标识、事件类型、时间、结果等关键要素，审计日志**留存不少于6个月**（部分行业实践要求180天以上）。一卡通场景中，以下事件必须进入审计范围：账户开户/销户、余额变动、消费撤销/冲正、清分规则修改、管理员登录与权限变更、终端设备注册/注销。审计记录须防止非授权删除和修改，建议写入**只追加的审计存储**或独立审计库。

### 3.4 数据安全与密码应用（密评衔接）

等保三级系统涉及敏感数据（身份信息、消费记录、行为轨迹），须实施加密、脱敏、备份与审计的完整链条。同时，**等保三级通常触发密评要求**，且密评与等保须同步规划、同步建设、同步运行。

国密算法在一卡通中的分工建议：

- **SM2（非对称）** ：终端证书签发、数字签名与验签、身份认证令牌；
- **SM3（杂凑）** ：交易流水完整性校验，为每笔消费生成“数字指纹”；
- **SM4（对称）** ：敏感字段加密存储（卡号、身份证号）、传输通道加密、会话密钥加密。

密评的量化口径通常要求**得分≥60且无高风险项**，等保三级及以上系统每年至少开展一次密评。方案设计阶段就应将密码应用纳入架构，而非测评前补救。

### 3.5 安全管理中心

部署**日志审计平台 + 堡垒机 + 态势感知**的集中管控组合。堡垒机管控所有运维操作并全程审计；日志平台汇聚网络设备、安全设备、主机、数据库、应用的全量日志，留存≥6个月；态势感知实现异常行为的实时告警与联动处置。一卡通系统的运维操作（尤其是数据库直连操作、清分脚本执行、配置变更）必须经过堡垒机，禁止绕过。


## 四、一卡通业务功能的核心适配要点

在通用技术架构之上，一卡通平台的以下业务特性需要在开发方案中专项设计：

**交易一致性**：消费扣款、余额更新、流水记录须在同一事务中完成，信创数据库的分布式事务能力（或基于消息队列的最终一致性方案）须在选型阶段完成压测验证。金仓在高校实测中峰值TPS达2,640，较原Oracle环境提升超四成，可作为性能基线的参考。

**清分清算的批处理能力**：夜间清分涉及大量聚合、对账、差错处理，对数据库的并行查询与批量写入能力要求高。选型时须验证数据库在**读写混合、资源消耗大的批处理场景**下的表现，并用消息队列做削峰填谷，避免清分查询直接冲击交易主库。

**双轨并行与平滑迁移**：存量一卡通系统迁移至信创栈时，推荐采用“**迁移前评估验证 → 迁移中增量同步 → 上线阶段双轨并行**”的实施路径。北京一卡通项目中，通过KFS+KDTS工具组合实现历史数据与增量数据的同步导入和一致性比对，迁移过程业务“零感知”，并在上线后保留原库并网运行作为风险兜底。高校场景中，“零回退、零重大故障”已被验证为可实现的迁移目标。


## 五、实施路径建议

**第一阶段：选型与实验室验证（1—2个月）** 。锁定CPU—OS—数据库—中间件—应用的具体版本组合，完成功能、性能、兼容、安全四类用例测试，要求厂商提供适配报告与压测数据。重点验证数据库的语法兼容度和迁移工具链的完整性。

**第二阶段：安全架构落地与等保差距分析（与第一阶段并行）** 。按照“一个中心、三重防护”逐项对照等保三级控制项，识别现有组件能力的差距（如数据库审计字段是否覆盖要求、操作系统是否支持双因素登录），在选型阶段就将安全能力纳入采购要求，而非后补。

**第三阶段：应用适配与联合调优（2—3个月）** 。完成一卡通核心模块（交易支付、清分清算、身份核验、设备接入）在信创栈上的适配改造，联合数据库/中间件厂商进行高并发交易与批处理场景的专项调优。此阶段应同步开展密评方案设计。

**第四阶段：双轨试运行与测评准备（2个月）** 。信创环境与原环境双轨并行，通过增量同步保持数据一致，验证业务连续性。试运行稳定后启动等保三级测评和密评，确保测评前所有技术控制项与管理控制项均已闭环。


**关键风险提示**：信创与等保三级双重约束下，最大的实施风险不是单一组件的功能缺失，而是 **“适配链条断裂”** ——某个层级（如中间件）看似在信创名录中，但与上下层组件的兼容性未经过联合验证，导致上线后出现会话丢失、连接池异常或性能骤降。应对策略是：在选型阶段坚持要求厂商提供**目标组合的联合适配报告**，并在实验室完成端到端压测，而非接受各组件独立出具的兼容性声明。
