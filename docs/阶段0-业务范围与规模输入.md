# 阶段 0：业务范围与规模输入

**状态**：进行中；首期范围、站点峰值和渠道规则已取得，合同/法律依据及门禁二期输入待补
**用途**：作为阶段 0 状态机、技术 PoC 和开发容量测试的输入  
**口径**：记录已由项目文档/用户确认的事实；未知值不推测

## 1. 已确认范围

| 领域 | 当前范围基线 | 来源/说明 |
|---|---|---|
| 消费 | 首期必选；主路径为先充值到校园卡账户、再刷卡消费；微信/支付宝等聚合渠道也可直接消费，四个站点正常在线由平台处理 | 用户确认；资金路径见 [ADR-0007](adr/0007-campus-stored-value-and-aggregator-boundary.md) 与[微服务划分](微服务划分.md) |
| 充值 | 首期必选；支持微信/支付宝/云闪付聚合充值入校园卡账户，补助及渠道额度规则按实际契约/配置确定 | 用户确认；渠道合同与具体支付/补助流程待核对 |
| 退款/冲正 | 首期必选；卡余额消费通过账户反向账务处理，聚合直付消费和充值退款按原渠道/合同规则处理；冲正时限 24 小时 | 用户确认；渠道合同与异常路径待核对 |
| 报表 | 首期必选；交易、对账和结算报表 | 用户确认；字段和日结窗口待核对 |
| 门禁与核验 | 二期扩展，不作为首期功能验收范围 | 用户确认；真实门型、控制器和生命安全输入待二期立项 |
| 断线支付 | 仅意外断线时终端有界故障切换；业务拒绝不触发离线；结果未知的在途交易保持待确认 | 用户确认及 [消费支付架构](微服务划分.md) |
| 卡务与账户 | 账户/卡状态、冻结解冻、余额和账户账本由账户服务负责 | [微服务划分](微服务划分.md) |
| 支付渠道 | 校园卡储值账户与微信、支付宝、云闪付聚合支付并存；聚合支付用于充值，也允许作为独立的直接消费方式；主消费路径为充值到账户后刷卡 | 用户确认；[ADR-0007](adr/0007-campus-stored-value-and-aggregator-boundary.md)；聚合渠道合同、商户号、回调与限额待核验 |
| 门禁 | 人员/门组/时段权限、控制器本地策略快照和通行审计 | [微服务划分](微服务划分.md) |
| 清结算 | 跨来源日终对账、商户清分、差错处理和结算报表 | [微服务划分](微服务划分.md) |
| 通知与风控 | 独立通知出口；在线交易前置风控，断线交易补传后复核 | [微服务划分](微服务划分.md) |
| 工程规模 | 八个业务服务、一个 Gateway、公共模块和八个 API 契约模块 | [项目说明](项目说明.md) |

业务场景按校园一卡通记录；2 个食堂、4 个消费站点及首期/二期范围已由用户确认。组织模型暂定为一个逻辑学校/租户，下设 2 个食堂、每个食堂聚合 2 个消费站点；首期数据库/API 保留 `tenant_id`，共享同一租户账户。实际合同主体、跨校区隔离要求仍待项目资料核实。详见[待确认事项与暂定方案](阶段0-待确认事项与暂定方案.md)。

## 2. 规模输入

项目文档不要求填写个人或部门责任方。容量数字记录统计时段和来源；没有数据时保留“待确认”，不据此设置生产 TPS 或容量结论。

| 输入项 | 当前值 | 状态/所需证据 |
|---|---:|---|
| 组织/租户数、实施站点数 | 暂定 1 个学校逻辑租户，下设 2 个食堂，每个食堂 2 个消费站点；共 4 个消费站点，按 8,000 人分散就餐的典型布局设计 | 食堂/站点/人数为用户确认；一个学校租户及共享账户为暂定模型，合同主体/跨校区隔离仍待资料核验 |
| 持卡用户数、有效卡数及增长率 | 发卡人数 8,000；有效卡口径、增长率及该数字对应的统计日期/规划阶段待确认 | 用户提供；待卡务台账核对并标注统计日期 |
| 消费终端数及型号/协议分布 | 数量待资产清单确认；首期消费机为标准 IC/CPU 双模联机/脱机消费机；离线 PoC 暂按 3 就餐日额度租约与恢复屏障设计 | 用户确认型号类别、容量目标；既有约 150 台规划估算尚无台账核实，具体厂商/协议和离线额度值待校方/设备确认 |
| 门禁控制器/门数及型号分布 | 数量待资产清单确认；属于二期 | 既有约 100 台规划估算尚无台账核实；门数、型号/协议待确认 |
| 日交易量 | 实际日量待台账或试点数据；旧约 16,000 笔/日输入已作废 | 不从新的设计压力目标推断历史业务量 |
| 业务高峰窗口的在线交易峰值 | 单站点 800 笔/分钟；4 个消费站点可同时达峰，全平台 3,200 笔/分钟（约 53.3 笔/秒） | 用户确认的新设计验收输入；午餐高峰有效满峰 30 分钟：单站点 24,000 笔、全平台 96,000 笔。属设计压力目标而非历史实测；2 个食堂作为业务聚合域，四站点均计入峰值 |
| 交易类型比例 | 消费 ≥90%；充值/补助 ≤8%；退款/冲正 <2% | 用户确认的验收输入；上线后用交易台账复核 |
| 在线拒绝/超时率及下游延迟 | 待确认 | 现有平台指标或试点采样；无现网时标为未知 |
| 最长计划/可接受断线时长 | 基本要求覆盖 3 个就餐日；离线单笔与日累计限额可配置 | 用户确认的设计约束；具体断线判定、额度数值和恢复屏障仍需设备联测 |
| 终端断线后的积压笔数与恢复时限 | 待确认 | 由最长断线时长和交易峰值推导，再经设备联测验证 |
| 每日门禁事件量、消息量和增长率 | 待确认 | 控制器/事件统计或一期目标估算 |
| 日结数据规模与允许完成窗口 | 待确认 | 结合清结算批次和结算约定确定 |
| 终端白名单与离线流水容量 | 白名单 ≥20,000 张；脱网记账 ≥100,000 条/终端；按每终端 800 笔/日估算约 125 天 | 用户确认的设计验收输入；厂商容量声明、掉电/WAL/恢复测试待核对 |
| 支付渠道限额、回调峰值、退款比例 | 聚合渠道用于充值和直接消费，主消费路径为充值后刷卡；T+1 自动对账，聚合直付/充值按原外部路径退款，校园卡余额消费以账户反向分录退款；冲正时限 24 小时；T+0/T+1 结算 | 用户确认的设计规则；渠道合同、商户后台、回调签名/重放和部分成功语义待核验 |
| 个人/消费/通行数据留存周期 | 交易流水在线 5 年，归档后再保留 10 年（设计总周期约 15 年）；门禁为二期待定 | 用户确认的设计规则；法定适用主体、起算点、归档可检索性和删除策略待法律/审计核验 |
