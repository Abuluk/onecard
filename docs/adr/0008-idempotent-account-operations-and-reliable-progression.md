# ADR-0008：账户操作幂等与跨服务可靠推进

**状态**：采用为开发基线；数据库实现与故障注入验证待完成  
**日期**：2026-11-04

## 背景

交易服务维护交易流程和终端流水，账户服务独占余额与账本写权限。网络超时可能发生在账户已经提交之后；若调用方换用新标识重试，可能重复扣款。通知和清结算属于后续流程，不应成为账户账务本地提交的同步一致性依赖。

## 决策

1. 一笔业务操作在首次发送前生成稳定的 `operation_id`，并绑定来源类型、来源标识和请求内容摘要；同一操作的所有重试和状态查询沿用该 ID。相同 ID 携带不同内容必须返回冲突，不能视为新交易。离线流水另使用终端身份与持久化本地序号形成稳定的来源键。
2. 账户服务在单一本地数据库事务内完成幂等操作结果、账户余额变化、不可变账本分录和待发布 outbox 事件。事务提交或回滚必须同时涵盖这些记录；不得先改余额再异步补写账本。
3. 交易服务在调用账户服务前持久化自己的操作状态；超时或连接中断时保持结果未知，通过同一 `operation_id` 查询/重试。收到确定结果后更新交易状态。账户服务对重复请求返回第一次提交结果。
4. Outbox 发布和消息消费按至少一次处理；消费者以稳定事件 ID 去重，重复投递不得产生第二次业务效果。通知只在资金操作提交后异步推进，不纳入扣款的分布式原子事务。
5. 不引入 Seata/XA 作为默认解法。余额与分录在账户服务本地原子提交，跨服务采用幂等命令、状态查询和 outbox 事件收敛；只有将来出现无法由此模型满足的跨服务原子不变量时，才单独评审分布式事务。
6. 账务功能不变量是：向调用方确认成功的账户操作，其余额变更、账本分录和幂等结果不可分离；服务进程重启后必须可查询原结果。阶段 0 还要求在选定数据库切换场景验证已确认账务 RPO=0，并以切换前后逐笔对账证明。该目标仅覆盖实际演练的故障类型，不替代其他主机/存储/灾备场景的独立 RPO/RTO 评估，也不预设特定集群拓扑。
7. 离线额度预留、复核、结清与补偿遵循 ADR-0003；余额更新、账本分录、预留结清和对应操作结果仍需在账户服务本地事务内保持一致。
8. 同一 `operation_id` 携带相同规范化请求摘要时返回首次操作的状态/结果；摘要不同则返回冲突（HTTP 409），绝不把同键不同内容解释为新操作。离线来源键为 `(tenant_id, terminal_id, local_seq_no)`，数据库唯一约束与账本引用共同阻止重放。
9. 幂等来源引用至少与其账务记录同生命周期保留；按项目当前在线 5 年、归档后再保留 10 年的策略，在约 15 年周期内保留可查询/拒重放的引用。法规适用性与归档可检索性另行评估，不由本 ADR 推定。
10. Outbox 首轮重试延迟暂定 1s、2s、5s、10s、30s，之后添加抖动并以 60s 为最高间隔持续重试；达到人工介入条件时进入告警/人工队列，记录不能删除或伪报成功。消息消费仍按至少一次和事件 ID 去重处理。

## 备选方案

- 交易服务直接写账户表或共享数据库事务：破坏服务写入权属；不采用。
- 每次超时生成新操作重试：无法区分首次提交和重试，可能产生重复账务效果；不采用。
- 用分布式事务包住扣款、交易状态和通知：扩大强同步故障域，且通知可异步；不作为默认方案。
- 账户本地原子操作 + 稳定幂等标识 + outbox/至少一次投递：采用为开发基线。

## 后果

- `operation_id` 唯一范围、请求摘要规范化、15 年项目策略下的归档/清理、并发竞争、outbox 重试参数和人工对账契约须在 API/数据库设计中冻结并测试。
- 该决策定义失败恢复方向，不等于现有代码已实现；当前 OceanBase PoC 尚未证明应用并发或数据库切换场景的 RPO=0。
- 业务 API 实现后必须测试并发重复请求、账户提交后响应丢失、服务重启、消息重复、outbox 重放和离线恢复屏障。

## 复审条件

目标数据库无法提供所需的本地事务/唯一约束；故障测试发现无法用幂等状态机和 outbox 收敛；或业务新增必须跨服务原子提交的资金不变量时复审。

## 依据

账户服务为余额/账本唯一写入方、交易服务维护自身状态、通知服务不拥有资金状态，来自现有 [`微服务划分`](../微服务划分.md) 与 [`跨服务责任矩阵`](../阶段0-跨服务责任矩阵.md)。消息按至少一次投递并由业务幂等实现单次效果的原则已记录于架构方案。本文不宣称“恰好一次传输”或现有实现已满足故障目标。
