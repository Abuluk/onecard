# ADR-0001：在线优先与终端断线故障切换

**状态**：方向已确认；PoC 阈值已暂定，生产参数与真实设备验证待完成
**日期**：2026-11-02  

## 背景

消费终端可在平台不可达时进入离线支付，但离线受理会带来余额过期、重复消费、补传和终端存储故障等资金风险。项目已确认：设备主要使用在线模式，只有意外断线时才通过终端设备故障切换到离线支付模式。

## 决策

- 在线支付是默认且正常模式；正常交易由平台校验并处理。
- 只有终端确认发生意外连接中断后，才允许后续新交易进入离线流程。PoC 默认在 5 秒窗口内连续 3 次传输层失败后进入 `DEGRADED`；此阈值可配置，不能计入业务拒绝、鉴权拒绝或明确风控拒绝，也不是厂商/行业标准。
- 业务拒绝（例如余额不足、卡冻结或风控拒绝）不属于断线，不得因此进入离线支付。
- 已发出但结果未知的在线交易保持待确认；不得把同一笔请求改记为本地成功。恢复后应使用原幂等标识查询或重试；只有之后的新交易可按有效预留额度离线受理。
- 离线支付必须使用账户服务事先签发并预留的有限额度。单笔、每卡日累计及每终端日累计额度均配置化；缺少有效签名策略或额度为零时失败关闭。PoC 使用隔离测试额度，不构成生产限额批准。
- 连接恢复后终端进入 `RECOVERING`：查询未决在线请求，按 `(tenant_id, terminal_id, local_seq_no)` 幂等补传离线流水，核对连续序号高水位及余额/预留额，刷新状态后才回到 `ONLINE`。恢复期间只允许在线受理；再次断线时离线仍关闭，直至屏障完成。

## 备选方案

- 全程强制在线、断线时完全拒绝消费：实现简单且无离线账务，但不满足项目已确认的意外断线故障切换要求。
- 任何在线失败（包括业务拒绝和结果未知）均允许离线受理：可能绕过余额/风控拒绝或重复使用未知交易对应额度，不符合已确认的故障切换边界。
- 在线优先，仅对确认的意外断线启用终端离线模式：采用此方向；待复核和预留资金语义由 ADR-0003 固定。

## 状态草案

```text
ONLINE
  ├─ 在线成功/业务拒绝 -> 返回确定结果，保持在线模式
  ├─ 意外断线已确认 -> FAILOVER
  └─ 已发送但结果未知 -> PENDING_CONFIRMATION；保留原幂等标识

FAILOVER
  └─ 后续新交易通过离线策略 -> 本地持久化并返回离线受理结果

PENDING_CONFIRMATION
  └─ 连接恢复后按原幂等标识查询/重试 -> 确认原交易结果

FAILOVER / PENDING_CONFIRMATION
  └─ 连接恢复 -> RECONCILING -> 满足恢复屏障 -> ONLINE
```

此图只表达已确认方向和现有架构约束；`PENDING_CONFIRMATION` 与后续离线消费之间必须由独立预留额度隔离，避免未知在途扣款与离线额度叠加造成超额消费。

## 待决问题与验收

1. PoC 默认值为传输层失败连续 3 次/5 秒；设备和食堂网络联测后确认失败分类、超时值、防抖和恢复观察期。
2. 离线额度按卡/终端/商户的范围、上限、最长离线时间，以及风险/冻结名单快照的有效期。
3. 未知在途交易对离线可用额度、账户余额和服务端保留额的影响，保证不会双重释放额度。
4. 终端本地序号持久化、时钟偏移、WAL 损坏/耗尽、设备丢失和恢复后的缺号/重复处理。
5. `NEED_REVIEW`、风控拒绝/不可用和退款/冲正的账本语义按 ADR-0003；支付渠道/商户合同对最终补偿归属的约束仍需纳入接口契约。
6. 暂定恢复屏障顺序：待确认在线交易、离线流水上传、幂等入账、序号连续高水位确认、余额/保留额同步、恢复在线受理；恢复期间在线可用但离线能力关闭。
7. 使用业务拒绝、已提交但响应丢失、断线抖动、重复补传、终端重启和余额恢复测试状态与账本不变量。

## 后果

- 交易主链路优先保障平台在线决策；离线能力只作为终端检测到意外断线后的受控故障切换。
- 终端软件与服务端必须区分“业务拒绝”“传输故障”和“结果未知”，不得仅凭通用超时响应切换模式。
- 白名单目标至少 20,000 张、终端离线流水至少 100,000 条；按每终端 800 笔/日，三个就餐日为 2,400 条（记录数容量的 2.4%）。该容量算术不替代终端持久化介质和掉电测试。
- 离线预留和复核资金策略已形成开发基线；在数值限额、终端安全存储和恢复屏障完成 PoC 前，不启用生产离线受理，也不把联测未通过的实现视为可发布。
