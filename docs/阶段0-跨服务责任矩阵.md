# 阶段 0：跨服务交易与清结算责任矩阵

**状态**：服务写入边界和可靠推进开发基线已暂定；渠道合同/沙箱、接口契约和测试未完成
**用途**：从现有服务划分提取读写权和调用方向，为任务 2、3 的 ADR 与 PoC 定范围

## 1. 业务数据与写入责任

| 服务 | 负责的数据/状态 | 写入边界 | 不负责 |
|---|---|---|---|
| `account-service` | 账户、卡状态、余额、账户账本 | 余额和账本分录只在账户服务本地事务内提交；对其他服务提供契约 | 跨来源日终对账、交易编排 |
| `transaction-service` | 交易状态、请求幂等、终端序号和补传进度 | 维护交易流水与幂等状态；通过账户契约请求入账 | 直接更新账户余额或共享账户表 |
| `risk-service` | 风控规则及判定结果 | 在线交易前置判定；离线流水补传时复核 | 账户余额写入；单独决定离线额度政策 |
| `payment-adapter-service` | 微信/支付宝/云闪付聚合充值及直接消费的请求、回调和标准化外部状态 | 外部渠道隔离、签名/回调验证与状态映射；确认的充值结果经账户契约幂等入账 | 校园卡刷卡消费和账户账本写入、清结算对账；具体聚合服务、商户合同和各通道能力仍待核验 |
| `clearing-service` | 渠道、在线/离线交易对账、清分批次和差错处理 | 清算结果通过账户契约幂等提交；不得直写账户库 | 实时消费扣款或维护权威账户余额 |
| `device-service` | 设备连接、命令投递、回传和设备影子 | 可靠接入和调度，按消费流水/门禁事件隔离队列 | 扣款、风控、门禁权限决策 |
| `access-service` | 门组策略快照、快照版本和通行审计 | 生成/签发访问策略，通过设备契约下发 | 人员主数据权威维护、资金处理、控制器长连接 |
| `notification-service` | 通知发送任务与结果 | 通过约定的通知契约消费业务请求/事件 | 资金状态或交易最终状态决策 |

本矩阵提取自 [`docs/微服务划分.md`](微服务划分.md) 与 [`docs/基础开发方案.md`](基础开发方案.md)，用于说明服务级写入和调用边界；项目文档不要求填写个人或部门责任方。

## 2. 关键调用与投递边界

| 流程 | 当前设计方向 | 尚待决策/验证 |
|---|---|---|
| 校园卡余额消费 | 主消费路径；交易服务编排、风险同步前置、账户服务本地原子扣款；同一幂等键/摘要重试返回原结果 | API 请求/响应契约、并发和提交后丢响应测试；结果未知用原键查询/重试 |
| 聚合渠道直接消费 | 用户确认属于首期可用资金路径；支付适配服务管理外部状态，成功后不增加校园卡余额 | 聚合产品/商户合同、授权和回调契约、幂等键以及结果未知时的查询/退款收敛 |
| 聚合渠道充值 | 支付适配服务确认渠道成功后，通过账户服务契约增加校园卡余额 | 防止重复回调/重试重复充值；充值退款规则和已消费余额限制按渠道及财务契约验证 |
| 断线离线消费 | 终端消费平台预留额度并持久化流水；服务端幂等接入；风控后由账户服务记账/结清预留 | 终端身份、序号、额度数值/时效、额度更新和补传失败恢复 |
| 交易与账户推进 | ADR-0008 采用账户本地原子事务、稳定幂等操作、交易状态先持久化和 outbox 至少一次推进；同键不同请求摘要返回冲突；幂等引用按项目账务保留周期保留；不默认使用分布式事务 | 并发/账户提交后响应丢失测试；具体摘要规范化、表结构与归档查询行为 |
| 支付渠道回调 | 聚合充值和聚合直付回调进入支付适配服务并标准化；校园卡余额消费走平台账户账本 | 外部入口位置、验签/重放规则、重复/乱序回调以及 HTTP 与持久化事件的选择；聚合服务合同/沙箱未知 |
| 退款/冲正 | 校园卡余额消费以账户反向分录退款；聚合直付和充值按原外部路径/合同退款；冲正请求目标时限 24 小时 | 渠道合同需确认可退规则、原路退款失败/部分成功、24 小时的起算与幂等语义 |
| 清结算 | 清结算归属跨来源对账、清分和差错分流；账户服务为账本权威方；设计目标为 T+1 自动对账，通道结算支持 T+0/T+1 | 渠道账单字段/时区、节假日、账期、结算幂等键和人工更正权限待合同/试点验证 |
| 通知 | 交易/支付等业务触发通知服务；至少一次消息按事件 ID 去重，通知不改变资金结果 | 事件版本契约、客户端集成、重试/人工队列和通知失败观测 |

## 3. 阶段 0 阻断决策

- 按 ADR-0003 保留 `NEED_REVIEW` 预留额度；通过后记账，拒绝后显式补偿/冲正；需对额度结清和渠道结算时序做故障验证。
- 按 ADR-0008 实现并验证交易状态与账户入账之间的可靠推进；测试账户已提交而调用方超时、服务重启、消息重复和重复请求。
- 对 outbox 暂定重试间隔（1/2/5/10/30 秒，随后带抖动最高每 60 秒）和人工告警/队列行为做故障验证；具体参数可在负载测试后调整。
- 已确认首期资金路径为聚合充值、校园卡余额刷卡消费（主路径）和聚合直付消费；仍需确认聚合服务提供方、商户合同、正式回调规范、验签和重放保护。
- 按 T+1 自动对账、T+0/T+1 结算、分路径退款和 24 小时冲正的目标补齐账单、失败/部分成功与资金收敛契约。
- 明确清结算批次、数据源、差错审批/冲正权限和结果回写契约。
- 按暂定业务操作 ID、事件 ID、幂等引用保留和重试规则设计接口/表；冻结事件版本及人工差错权限，并通过重复/乱序/死信测试。

在上述项完成前，不冻结支付/交易/清结算 API，也不因现有 Maven 模块依赖关系推断业务契约已确定。
