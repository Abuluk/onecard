# 阶段 0：跨服务交易与清结算责任矩阵

**状态**：边界草案；首期渠道和结算规则方向已确认，渠道合同、接口契约和可靠推进机制未冻结
**用途**：从现有服务划分提取读写权和调用方向，为任务 2、3 的 ADR 与 PoC 定范围

## 1. 业务数据与写入责任

| 服务 | 负责的数据/状态 | 写入边界 | 不负责 |
|---|---|---|---|
| `account-service` | 账户、卡状态、余额、账户账本 | 余额和账本分录只在账户服务本地事务内提交；对其他服务提供契约 | 跨来源日终对账、交易编排 |
| `transaction-service` | 交易状态、请求幂等、终端序号和补传进度 | 维护交易流水与幂等状态；通过账户契约请求入账 | 直接更新账户余额或共享账户表 |
| `risk-service` | 风控规则及判定结果 | 在线交易前置判定；离线流水补传时复核 | 账户余额写入；单独决定离线额度政策 |
| `payment-adapter-service` | 实体校园卡、微信/支付宝/云闪付聚合支付请求与回调的标准化状态 | 外部渠道隔离、签名/回调验证与状态映射 | 账户账本写入、清结算对账；具体聚合服务、商户合同和各通道能力仍待核验 |
| `clearing-service` | 渠道、在线/离线交易对账、清分批次和差错处理 | 清算结果通过账户契约幂等提交；不得直写账户库 | 实时消费扣款或维护权威账户余额 |
| `device-service` | 设备连接、命令投递、回传和设备影子 | 可靠接入和调度，按消费流水/门禁事件隔离队列 | 扣款、风控、门禁权限决策 |
| `access-service` | 门组策略快照、快照版本和通行审计 | 生成/签发访问策略，通过设备契约下发 | 人员主数据权威维护、资金处理、控制器长连接 |
| `notification-service` | 通知发送任务与结果 | 通过约定的通知契约消费业务请求/事件 | 资金状态或交易最终状态决策 |

本矩阵提取自 [`docs/微服务划分.md`](微服务划分.md) 与 [`docs/基础开发方案.md`](基础开发方案.md)，用于说明服务级写入和调用边界；项目文档不要求填写个人或部门责任方。

## 2. 关键调用与投递边界

| 流程 | 当前设计方向 | 尚待决策/验证 |
|---|---|---|
| 在线消费 | 交易服务编排；风险同步前置；账户服务原子扣款并返回确定结果 | 请求/响应契约、幂等保留期、风险超时与下游结果未知的状态收敛 |
| 断线离线消费 | 终端消费平台预留额度并持久化流水；服务端幂等接入；风控后由账户服务记账/结清预留 | 终端身份、序号、额度数值/时效、额度更新和补传失败恢复 |
| 交易与账户推进 | 账户账本只由账户服务写，交易服务持久化自己的交易状态 | 同步幂等命令、outbox/消息等候选方案的业务时序与故障恢复 PoC；不默认使用分布式事务 |
| 支付渠道回调 | 校园卡交易由平台处理；微信/支付宝/云闪付聚合支付回调进入支付适配服务并标准化 | 外部入口位置、验签/重放规则、重复/乱序回调以及 HTTP 与持久化事件的选择；聚合服务合同/沙箱未知 |
| 退款/冲正 | 首期采用原路退款；冲正请求目标时限 24 小时 | 渠道合同需确认可退规则、原路退款失败/部分成功、24 小时的起算与幂等语义 |
| 清结算 | 清结算归属跨来源对账、清分和差错分流；账户服务为账本权威方；设计目标为 T+1 自动对账，通道结算支持 T+0/T+1 | 渠道账单字段/时区、节假日、账期、结算幂等键和人工更正权限待合同/试点验证 |
| 通知 | 交易/支付等业务触发通知服务 | 消息版本、重试/死信、去重和通知失败是否影响业务结果 |

## 3. 阶段 0 阻断决策

- 按 ADR-0003 保留 `NEED_REVIEW` 预留额度；通过后记账，拒绝后显式补偿/冲正；需对额度结清和渠道结算时序做故障验证。
- 选择交易状态与账户入账之间的可靠推进机制，并验证账户已提交而调用方超时、服务重启、消息重复和重复请求。
- 已确认首期支付方式为实体校园卡、微信/支付宝/云闪付聚合支付；仍需确认聚合服务提供方、商户合同、正式回调规范、验签和重放保护。
- 按 T+1 自动对账、T+0/T+1 结算、原路退款和 24 小时冲正的目标补齐账单、失败/部分成功与资金收敛契约。
- 明确清结算批次、数据源、差错审批/冲正权限和结果回写契约。
- 固定跨服务业务 ID、事件版本、幂等键、保留期、重试/死信和复核工作流。

在上述项完成前，不冻结支付/交易/清结算 API，也不因现有 Maven 模块依赖关系推断业务契约已确定。
