# 独立制作一卡通系统阶段 0 阻断点重定义与推荐方案

**适用前提**：系统核心卡为学校自主制作、自主发行的校园一卡通（单用途预付卡性质），不涉及银联卡 BIN 管理，不接入银联收单网络，卡内资金封闭运行于校园场景。以下分析以此前提替换此前“银行卡支付”假设，对阶段 0 出口的八个阻断点逐一重新定性，并基于 2026 年 11 月可获取的公开资料给出推荐方案与证据要求。


## 一、先澄清一个根本性法律定性：独立一卡通不是“支付业务”

《非银行支付机构监督管理条例》明确规定，**单用途预付卡服务不属于该条例规定的支付业务**。非银行支付机构提供的支付服务限于“储值账户运营”和“支付交易处理”两类，均以接收收款人或付款人预付资金并转移货币资金为特征；校园一卡通在校内食堂、门禁、图书等封闭场景中循环使用，资金不向校外商户清算，属于典型的单用途预付卡。

这一法律定性直接消解了原阻断点中的**“支付渠道合同（银联收单）”** ：独立一卡通不需要银联收单资质，不需要接入银联商户入网平台，也不适用银联 2026 年 11 月的商户字段调整要求。原阻断点中涉及“收单机构准入”“商户号”“平台分账合规判定”的内容，对独立一卡通**整体不适用**。

**但替代性合规义务同时生成**：单用途预付卡虽不归央行支付业务监管，但校园一卡通的资金来源于师生预存，涉及消费者资金安全，教育主管部门和学校财务管理制度构成第一层约束；卡内资金若涉及财政性资金或代收费，还需遵守教育收费管理相关规定。合规重心从“支付牌照与收单准入”转向**教育行业数据与安全标准 + 学校资金管理制度 + 等保要求**。


## 二、逐项重定义：独立一卡通场景下的阻断点

### 阻断点 1：资金恢复屏障与幂等故障测试——保留，但基准要换

独立一卡通的资金恢复目标不应引用 DORA 或银联支付系统的 RTO 基准，而应以校园场景的实际可容忍中断时间为准。一卡通消费在食堂高峰期具有强时段性，早中晚三个窗口的中断容忍度远低于一般业务系统。行业实践中，一卡通核心数据库的可用性目标已明确为 **RPO=0、秒级 RTO**，共享存储集群或读写分离集群是高可用架构的主流选择。

**重定义后的关闭标准**：
- 在消费终端或数据库节点故障注入下，**已写入的消费流水零丢失（RPO=0）** ，恢复后余额与流水对账一致。
- 幂等验证不再以“同一笔银联回调重复 8 次”为模板，改为：同一终端在弱网下重复上送同一笔消费请求（模拟学生连续刷卡或终端重试），系统仅扣款一次；离线交易补传时不得产生重复入账。
- 证据形式：故障注入日志 + 消费流水与余额对账快照 + 离线补传幂等测试记录。


### 阻断点 2：原“支付渠道合同”——替换为“校内资金结算与商户接入制度”

独立一卡通不存在外部收单合同，但存在校内商户（食堂档口、超市、打印店等）的接入与结算关系。这里的合规风险不再是银联准入，而是**校内商户资金归集与结算的规范性**：商户结算周期、退款路径、手续费扣收是否有书面制度，是否存在学校账户与商户账户之间的资金混同。

**重定义后的关闭标准**：
- 产出一份**校内商户接入与资金结算管理办法**（或等效文件），明确结算周期、退款处理、对账机制、手续费规则。
- 如果涉及学校财务账户与一卡通备付金账户的分账，确认账户隔离与审批流程已落实。
- 证据：制度文件 + 至少一个商户的端到端结算对账样例。


### 阻断点 3：卡 BIN 主数据——**对独立一卡通不适用，移除**

独立制作的校园卡不使用银联 BIN 号段，卡内身份识别依赖学校自有的**人员主数据**（学号/工号）和卡内芯片序列号或应用标识。银联卡表文件接收链路、月度 BIN 同步验证等要求与独立一卡通无关，应当从阻断点清单中移除。

**替代项：人员主数据来源的权威性**。一卡通的人员账户必须以学校权威源系统为唯一真相源——本科生/研究生以学籍系统为准，教职工以人事系统为准。一卡通系统不应自行维护人员基础信息，而应通过同步接口从学籍/人事系统拉取，并建立**离校/离职状态变更触发账户冻结**的联动机制。行业实践中已有“入学时 HR/学籍资料触发账户生成，离校自动冻结权限”的成熟模式。

**关闭标准**：完成与学籍系统、人事系统的**人员状态同步接口**，并验证“入学开户—在校正常—离校冻结”全流程；不再要求银联卡表相关内容。


### 阻断点 4：正式 OIDC issuer / audience / 授权矩阵——保留，但 scope 模型不同

独立一卡通的身份认证服务于校内身份与消费权限，不需要 FAPI 2.0 的金融级客户端认证（private_key_jwt / mTLS），除非一卡通系统与校外银行或交通卡系统发生联合身份联邦。纯校内场景的 OIDC 基线应参照 **OAuth 2.0 / OIDC 标准实践**，重点在于：

- issuer 使用学校统一身份认证平台或一卡通自身认证服务的正式 HTTPS 域名；
- audience 区分**身份令牌**（用于门禁、图书借阅等身份场景）与**消费令牌**（用于电子钱包扣款），二者不应混用；
- 授权矩阵明确：哪些终端（食堂 POS、门禁读头、自助终端、移动端）→ 哪些 scope → 哪些操作。

**关闭标准**：完成 issuer 正式域名配置与 discovery 文档发布；产出一份授权矩阵表格（终端类型 × scope × 允许操作）；执行一次负向测试——消费场景令牌访问身份管理接口应被拒绝。


### 阻断点 5：数据库应用集成——保留，且对独立一卡通更为关键

独立一卡通的高并发特征集中在**开学季与就餐高峰**，而非全天均匀负载。数据库选型的核心矛盾是：高峰时段大量消费写入与实时余额校验并发，同时管理端报表查询不能拖慢交易响应。

**2026 年可参考的推荐路径**：
- **高可用架构**：优先采用**共享存储集群（RAC）或读写分离集群（RWC）**，RPO=0、秒级 RTO 作为底线目标。
- **信创兼容性**：如果学校有国产化要求，2026 年 7 月已有多家厂商联合发布教育行业全栈国产化一卡通方案，覆盖芯片、操作系统、数据库到应用层的全链路适配，可作为选型参照，但需注意这些方案处于早期落地阶段（首批标杆案例预计 2026 年第四季度落地）。
- **分布式事务**：消费扣款与流水落库需要强一致，跨服务场景（如消费同时更新余额、写入流水、触发通知）应使用 Seata 或等效分布式事务机制，而非仅依赖最终一致性。

**关闭标准**：完成数据库节点故障切换演练（RPO=0 验证）；完成高峰负载下余额校验与写入的延迟曲线记录；如使用国产数据库，提供迁移前后一致性对账报告。


### 阻断点 6：开发性能门槛——保留，基准需与校园场景对齐

你文档中的 **3,200 笔/分钟（约 53 TPS）** 作为设计压力目标，对独立一卡通而言处于合理量级，但需要补充**峰谷比**和**延迟分布**。校园一卡通的实际负载不是均匀的 53 TPS，而是集中在就餐时段的短时尖峰。行业参考中，20 万用户规模的系统高峰期可达到 **300 TPS**，日均交易量超过 50 万笔；另有 SpringBoot 方案以 **3,000 TPS** 作为高并发消费处理的目标。

**关闭标准**：
- 以 3,200 笔/分钟为**持续 30 分钟的平均负载**，另设**尖峰测试**：模拟 10 分钟内的就餐高峰，TPS 不低于 300（或按你实际终端数与并发刷卡率折算）。
- 性能报告必须包含**P99 消费响应时间**（离线交易行业参考 <200ms）和**错误率**。
- 将**数据库故障切换期间**的性能衰减与恢复后积压消化时间纳入门槛。


### 阻断点 7：留存法规适用性——需区分“交易流水”与“会计档案”

独立一卡通的交易记录留存不能简单套用《电子商务法》三年或支付机构五年。关键区分是：

- **消费流水**：作为持卡人余额变动的依据和校内商户结算的凭证，其留存期限首先服从**学校财务档案管理制度**。有来源提及食堂 IC 卡消费记录作为会计原始凭证的组成部分，可能参照 15 年甚至 30 年的保管期限，但该说法来自地方性会计核算办法的解读，**不能直接作为你系统的合规依据**。
- **身份信息与卡账户记录**：适用《个人信息保护法》的**最小必要与存储期限限制**原则；2025 年 4 月发布的教育行业标准 **JY/T 0643—2025《智慧教育平台 个人信息保护通用要求》** 对教育平台用户个人信息的处理活动提出了保护要求，一卡通系统作为智慧教育平台的组成部分，应将其纳入个人信息保护影响评估的参照框架。

**“保存期限主张尚未独立核实”的关闭方式**：不再停留于“主张”，而是产出一份**留存期限适用性判断表**，逐类列明数据（消费流水、余额快照、持卡人身份信息、终端日志）对应的**学校财务制度条文或教育行业标准条款**，由学校财务处或合规负责人书面确认。对于无法确定的事项，明确标注“待确认”并指定确认责任人与期限，而非笼统保留“未核实”状态。

**JY/T 0661—2025《教育数据分类分级指南》** （2025 年 12 月发布，2026 年 2 月实施）为教育数据的分类分级提供了直接依据，一卡通交易数据与身份数据的分级保护要求应据此映射。


### 阻断点 8：安全合规基线——从“支付安全”转向“等保 + 国密 + 教育数据保护”

独立一卡通不再以 PCI DSS 为基线（不处理银行卡号），但**等保要求是硬性的**。高校一卡通系统通常按**网络安全等级保护第三级**要求保护，需逐一落实物理环境、通信网络、区域边界、计算环境和安全管理中心的技术措施。

同时，校园卡芯片与交易链路应支持**国密算法**。行业实践中，国密一卡通改造已形成较成熟的路径：支持 **SM1/SM4** 的 PSAM 安全模块和加密终端，部分方案已覆盖 SM1/SM2/SM3/SM4 全算法，并适配麒麟、统信等国产操作系统。需要注意的是，有来源指出**超过 41% 的校园一卡通国密改造在布线阶段发现老旧线路不支持 SM4 加密信道**，因此在阶段 0 应完成一项**存量终端与线路的国密就绪度盘点**，而非直接假定改造可以平滑完成。

**关闭标准**：
- 等保三级差距分析或测评计划（如尚未测评）；
- 国密就绪度盘点报告，列明现有 CPU 卡、读卡器、PSAM 模块、消费终端是否支持 SM1/SM4，以及不支持设备的替换计划；
- 完成 JY/T 0643—2025 的个人信息保护条款逐项自查。


## 三、2026 年 11 月独立一卡通推荐方案（参考架构）

以下方案以“独立制作单用途校园卡 + 校内封闭支付 + 等保三级 + 可选信创”为约束条件：

| 层次 | 推荐选择 | 依据与说明 |
|---|---|---|
| **卡介质** | 非接触 CPU 卡，符合 ISO/IEC 14443-A，同时保留 M1 兼容过渡（如有存量） | 高校采购实践中 CPU 卡已是主流技术要求 |
| **卡内安全** | SM1/SM4 国密算法 + PSAM 安全模块 | 国密改造是 2025—2026 年一卡通安全升级的明确方向 |
| **应用架构** | Spring Cloud 微服务，至少拆分身份认证、支付/电子钱包、设备接入、数据中台等核心模块 | 20 万用户级方案已验证该路径可行 |
| **身份认证** | OAuth 2.0 / OIDC（校内 issuer），消费令牌与身份令牌分离 | 不强制 FAPI 2.0，但 audience 隔离必须做到 |
| **数据库** | 读写分离集群或共享存储集群，RPO=0 / 秒级 RTO；有信创要求时评估国产数据库（达梦、金仓等） | 高可用与信创双约束下的主流选择 |
| **分布式事务** | Seata 或等效机制，消费扣款 + 流水落库 + 通知强一致 | 避免仅靠最终一致性导致余额与流水偏差 |
| **终端通信** | 在线 HTTPS RESTful + 离线 ISO/IEC 14443 双通道；离线交易 <200ms | 兼顾食堂快速消费与门禁/图书实时验证 |
| **人员主数据** | 以学籍系统 + 人事系统为权威源，一卡通只存映射关系；离校状态变更触发冻结 | 消除一卡通自维护人员数据的孤岛风险 |
| **安全基线** | 等保三级 + JY/T 0643—2025 个人信息保护 + 国密就绪 | 教育行业合规的核心组合 |
| **数据分级** | 按 JY/T 0661—2025 对一卡通交易数据与身份数据分类分级 | 2026 年 2 月起实施的教育数据基础标准 |


## 四、数据来源真实性核查说明

本文涉及的外部依据中，**高置信度**的有：单用途预付卡不构成《非银行支付机构条例》支付业务的法律定性（来自港交所披露文件引述的条例原文，2025 年 11 月）；JY/T 0643—2025 和 JY/T 0661—2025 的标准编号、发布日期与实施日期（来自标准发布机构和教育部通知）；等保三级对校园一卡通系统的适用性（多篇 2025—2026 年期刊文献与行业文章一致指向三级）；国密算法在校园一卡通中的使用（多个厂商方案与改造案例交叉印证）。

**需要谨慎对待的有**：食堂 IC 卡消费记录“至少 15 年 / 30 年”的留存说法，来源为地方性会计核算办法的解读文章，**不能直接作为系统合规依据**，必须回到学校财务制度或省级教育财务主管部门的明确规定进行独立确认。20 万用户级架构文章中的 TPS 数据（300 TPS、500 TPS、3000 TPS）来自不同规模的方案描述，量级有参考价值，但不能直接等同于你系统的验收门槛。全栈国产化一卡通方案（2026 年 7 月发布）处于推广初期，首批标杆案例尚在落地中，选型时应要求厂商提供与你规模匹配的**可核验案例**，而非仅依据联合发布新闻。

**建议在你现有的 `阶段0-出口评审.md` 中为“留存法规”条目增加一行状态说明**：将“保存期限主张尚未独立核实”改为“保存期限适用性判断表编制中，财务确认责任人：___，目标关闭日期：___”，使该阻断点从模糊的主张状态进入可追踪的责任状态。
