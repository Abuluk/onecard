# 独立制作一卡通系统阶段 0 阻断点重定义与推荐方案

**复核状态**：本文是待核验的建议稿，不构成法规、标准或生产架构结论。用户已确认首期同时支持校园卡储值账户和微信、支付宝、云闪付聚合支付；主消费路径是聚合充值到账户后刷卡，聚合渠道也可以直接消费。本文原先“整个系统为校内封闭、无需外部收单合同”的前提不成立，以下八项按当前混合资金路径复核。本文列出的公开资料、行业数字和标准适用性尚无可追溯的一手出处，不得直接作为验收阈值或合规结论。


## 一、法规适用性需按实际资金路径判断

原建议稿援引《非银行支付机构监督管理条例》对单用途预付卡服务的定性，但未附法规原文链接、适用条款分析或法律意见。本项目同时包含外部聚合充值和聚合渠道直接消费，不能仅凭校园卡账户在校内使用，就推导整个系统或运营主体不属于某项监管范围。需要结合实际收款主体、资金归属、外部支付合同、消费商户及结算流向逐项核验。

校园卡不是银联银行卡 BIN 卡，因此不应把银联卡 BIN 主数据要求套到校园卡介质上。与此同时，微信、支付宝、云闪付聚合充值及直接消费仍依赖实际聚合产品、商户主体和合同约定；是否涉及特定收单、商户或结算义务，应以真实资金流和正式专业意见判断，不能在本文中作豁免结论。

学校财务制度、消费者资金保护、教育数据和网络安全要求都需要评估，但适用主体和具体义务须有正式依据。合规范围应覆盖校园卡储值账本、聚合渠道资金、直接消费、退款、商户结算及个人信息，不应预先限定为某一套行业标准。


## 二、逐项复核：本项目混合资金路径下的阻断点

### 阻断点 1：资金恢复屏障与幂等故障测试——保留，但基准要换

用户已指定数据库切换场景下验证已确认账务 RPO=0。验收仅覆盖实际选定并演练的切换场景，须核对已确认账户操作的余额、账本分录和幂等结果；其他主机/存储/灾备场景及恢复时间仍需单独评估，不从未核验的行业数字推导。

**重定义后的关闭标准**：
- 在选定数据库切换场景中验证已确认账务 RPO=0，切换后余额、账本分录和幂等结果逐笔一致；另行记录其他故障场景的数据恢复点与服务恢复时间。
- 对聚合充值、校园卡余额消费和聚合直付消费分别执行原请求加 8 次重复；对外部路径重放回调、对离线消费重复补传时均不得产生第二次资金效果。
- 证据形式：故障注入日志 + 消费流水与余额对账快照 + 离线补传幂等测试记录。


### 阻断点 2：聚合渠道合同与校内结算制度并行核对

本项目已确认聚合充值和聚合直接消费，因此不能移除外部聚合服务合同、商户配置、回调、退款和账单核对项。若学校还需向食堂档口等内部商户清分结算，则另需核实校内接入制度、结算周期、退款和财务审批，不能用内部制度替代外部渠道契约。

**重定义后的关闭标准**：
- 取得聚合服务合同/沙箱，核对实际商户主体、充值和直接消费产品、回调验签、退款、账单字段、T+1 自动对账及 T+0/T+1 结算能力。
- 若存在校内商户清分，另取得学校财务制度和结算样例，确认资金归属、审批、差错和退款处理。
- 证据：合同或正式产品文档、沙箱回调/退款/对账测试；校内清分样例按实际范围提供。


### 阻断点 3：银联卡 BIN 不适用；人员与校园卡主数据来源待定

校园卡不使用银联银行卡 BIN 号段，因此银联卡表同步不是本项目校园卡主数据要求。校园卡和账户仍需绑定人员标识、卡介质标识和状态；学校权威人员系统及接口现状尚未提供，不能预设必须由学籍/人事系统按某种机制同步。

**待确认项：人员主数据来源与生命周期**。应由项目确定学生、教职工及其他持卡人的权威源、同步方式、离校/离职账户处理与余额退款规则，并明确一卡通系统允许维护的本地字段。不得在接口和冻结策略未确认前假定上游系统或状态联动已存在。

**关闭标准**：明确人员与卡主数据来源/责任边界及状态变更规则；若阶段 1 依赖真实上游接口，则取得接口契约或明确模拟数据策略，并测试开户、变更、冻结和余额处置。


### 阻断点 4：正式 OIDC issuer / audience / 授权矩阵——保留，但 scope 模型不同

本项目已选择 OIDC；issuer、API audience、角色值和授权矩阵仍待正式配置。OIDC 身份令牌不能充当支付渠道的资金授权或支付凭证；支付渠道验签和交易状态需按渠道合同独立实现。当前材料不足以确定是否适用特定金融级客户端配置，需按实际客户端和威胁模型核验。重点包括：

- issuer 使用学校统一身份认证平台或一卡通自身认证服务的正式 HTTPS 域名；
- API audience 按具体资源服务器配置；不能将 PoC 默认的 `account` audience 当作已批准值，也不应把身份令牌解释为消费授权；
- 授权矩阵明确首期管理端、用户端、消费终端和服务身份可执行的操作。门禁/核验属于二期。

**关闭标准**：取得正式 issuer、API audience、用户/管理员角色值和授权矩阵；完成 discovery、签名/issuer/audience 校验及允许/拒绝访问测试。Issuer 尚为脱敏占位时只可保留模板，不可宣称生产身份冻结。


### 阻断点 5：数据库应用集成——保留

本项目的设计压力集中在四个消费站点午餐峰值。数据库选型需覆盖余额写入并发和报表/对账隔离，具体生产容量与拓扑待目标环境和实测决定。

**当前开发基线**：按 [ADR-0008](adr/0008-idempotent-account-operations-and-reliable-progression.md)，余额、账户账本、幂等结果和 outbox 在账户服务本地事务中提交；跨服务以稳定操作标识、查询/重试和至少一次消息推进，不默认引入 Seata/XA。数据库高可用拓扑、RPO/RTO 和信创要求须由目标环境、业务恢复需求及项目约束决定，不能从无出处的“行业主流”表述直接选 RAC/RWC 或承诺秒级恢复。

**关闭标准**：完成 OceanBase Spring 应用/连接池/迁移集成，验证余额与账本本地事务、并发扣款、服务/数据库重启及恢复；在选定数据库切换场景证明已确认账务 RPO=0，其他 RPO/RTO 和故障范围另行记录。


### 阻断点 6：开发性能门槛——保留，基准需与校园场景对齐

用户确认的开发压力输入为四站点同时达峰 3,200 笔/分钟，持续 30 分钟 96,000 笔；该数值是设计输入，不是历史业务量或生产容量证明。原稿中的 300 TPS、3,000 TPS 和日均 50 万笔未提供可核验来源，不能作为本项目容量目标。

**关闭标准**：
- 以四站点并发 3,200 笔/分钟运行 30 分钟，并根据终端并发/突发模型补充尖峰形状；终端数和请求分布取得后再冻结模型。
- 报告吞吐、P95/P99、错误率、资源和积压消化情况；本项目尚未批准固定延迟/错误率验收阈值。离线本地响应延迟与在线端到端延迟分开测量。
- 将**数据库故障切换期间**的性能衰减与恢复后积压消化时间纳入门槛。


### 阻断点 7：留存法规适用性——需区分“交易流水”与“会计档案”

用户已确认的项目留存策略为交易流水在线保留 5 年，归档后再保留 10 年，设计总周期约 15 年。该期限先作为项目策略记录，不表述为对所有数据类别或运营主体适用的法定期限。仍需区分：

- **消费流水**：作为余额变动、退款和校内清分凭证，应由学校财务/审计确认适用的档案类别、期限和起算点；不能直接套用未核验的地方解释。
- **身份信息与卡账户记录**：按适用的个人信息保护要求确定目的、范围、期限和删除/匿名化方式。本文列出的 JY/T 0643—2025 等标准编号、发布日期、效力和对本系统的适用性均须以主管部门正式文本核验。

**关闭方式**：产出一份留存期限适用性判断表，逐类列明数据（消费流水、余额快照、持卡人身份信息、终端日志）对应的正式制度或标准依据，并将尚未核实的类别和证据要求明确记录；已确认的在线 5 年、归档后再保留 10 年作为项目设计策略保留。

原稿所列 **JY/T 0661—2025** 标准编号、日期和适用范围尚无一手出处支持，暂不作为分类分级结论；取得正式标准文本后再评估是否适用。


### 阻断点 8：确认系统安全与数据保护适用性

是否涉及银行卡数据处理、适用何种网络安全等级保护级别及是否需要密码应用评估，应根据系统定级、实际数据流、运营主体和主管/专业机构意见确认。本文没有足够证据将等保三级或某种支付安全标准作为本项目的普遍硬性结论。

卡片、PSAM、终端链路是否必须支持特定国密算法及其认证要求，取决于正式安全要求、现有设备和采购约束。原稿提到的“41%”及算法/产品适配数字没有可核验来源，不作为项目事实；如适用，按真实设备清单和正式密码应用要求盘点。

**关闭标准**：
- 系统定级、等保/密评、产品认证和个人信息保护适用性判断及依据；
- 取得真实卡片、读卡器、PSAM、消费终端清单后，按已确认的安全要求核验兼容性；
- 对已核实适用的正式法律/标准逐项记录控制映射、责任主体与验证证据。


## 三、2026 年 11 月推荐方案（待核验）

以下仅列设计候选；适用性和选型须按本项目“校园卡储值 + 聚合充值 + 校园卡余额消费 + 聚合直接消费”的资金路径及已确认约束评估：

| 层次 | 推荐选择 | 依据与说明 |
|---|---|---|
| **卡介质** | 按现有卡片台账和终端 IC/CPU 双模兼容性确定；本轮未确认具体卡片型号 | 取得卡片和终端协议清单后验证读写、安全和离线能力 |
| **卡内安全** | 根据卡片、终端和正式安全要求选择算法/PSAM | 适用算法与认证要求需一手依据和设备盘点，不据行业文章定型 |
| **应用架构** | 沿用仓库已规划的服务边界，避免将支付适配、账户账本和交易编排合并为单一责任 | 现有服务划分见项目文档；不以未经核验的规模案例推断可承载能力 |
| **身份认证** | OIDC；issuer、API audience、角色和授权矩阵待正式配置 | 与支付渠道验签/支付状态分开；门禁和核验是二期 |
| **数据库** | OceanBase 开发基线；本地事务、连接池、故障恢复待应用验证 | HA 拓扑、RPO/RTO 与生产数据库在目标环境确定后评审 |
| **跨服务账务** | 账户本地原子事务 + 稳定幂等操作 + outbox/至少一次推进 | 已记录于 ADR-0008；不默认采用 Seata/XA |
| **终端通信** | 在线/离线双模式按厂商协议和设备能力确认 | 离线响应门槛、门禁/图书等二期要求未由本项目批准 |
| **人员主数据** | 按项目确认的权威源、卡账户生命周期和余额处置规则集成 | 当前主数据来源和上游接口待确认 |
| **安全基线** | 按系统定级、实际数据流和适用法规/标准形成安全基线 | 等保级别、密评和具体标准适用性待确认 |
| **数据分级** | 按已核实适用的教育/个人信息/网络安全规范形成分类分级 | 标准版本及对本系统的适用性须有正式文本和专业判断 |
