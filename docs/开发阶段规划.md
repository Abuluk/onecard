# 一卡通平台开发阶段规划

**版本**：1.0
**日期**：2026-11-02
**状态**：执行基线草案
**适用范围**：当前 Spring Cloud 后端骨架及八个业务服务

本文档将《微服务划分》中的服务边界转为有依赖顺序的开发阶段。每一阶段都必须交付可运行的业务切片，并完成自动化功能测试、集成/故障测试和与该阶段相关的性能验证，达到退出条件后才能进入依赖它的下一阶段。

## 1. 当前基线

- 根 Maven 工程聚合 `common`、`gateway`、八个 `apis/*-api` 和八个 `services/*-service` 模块。当前服务只提供 Spring Boot 与 Actuator 骨架，尚无领域 API、业务数据模型或资金流程。
- 本地 Compose 配置包含 Nacos 3.1.1、九个 `dev` 应用和监控组件；截至 2026-11-03 容器已停止，MySQL/Redis 只供 N9E 使用，不承载业务数据。OceanBase、Valkey 和 RocketMQ 只有隔离 PoC，未加入当前 Compose。阶段 0 兼容矩阵和阶段 1 本地平台验证记录分别说明覆盖范围。
- Gateway 已按开发态用户/管理角色矩阵实施 OIDC JWT 验证和默认拒绝，风控、设备及二期 access 路径已从公网路由移除，Actuator 使用独立管理端口。领域 API 仍未实现；生产启用前需完成精确 API 暴露矩阵、共享限流、真实 IdP 联测和服务身份隔离。
- `tests/performance/smoke.js` 当前为 1 VU、10 秒的 `/actuator/health` 检查。它只证明健康端点可访问，不代表业务吞吐、延迟或容量。
- 当前 Maven 版本组合见根 `pom.xml`。构建通过不等于 Nacos、数据库、消息、缓存及国产运行环境的运行时兼容已验证。

## 2. 审阅结论与先决决策

服务数量和目录结构一致：八个业务服务加一个网关，API 契约模块与服务模块一一对应。没有证据要求增加第九个业务服务，但以下边界和依赖必须在实现前确定。

1. **资金一致性**：账户余额与账户分录由账户服务本地事务原子提交；交易服务不共享账户表或数据库事务。阶段 0 必须选定交易状态与账户入账之间的可靠推进方式，并明确超时、重复、未知结果、服务重启后的状态恢复。
2. **离线风控状态**：终端已确认消费而服务端风控拒绝或不可用时，定义受理、入账、待复核、冲正/退款各状态的精确定义及其账户余额影响。`NEED_REVIEW` 不能含糊表示“已受理”或“已入账”。
3. **离线故障切换边界**：在线消费是默认模式；确定断线判定阈值、连续失败数、超时、恢复观察期和防抖，且明确余额不足、卡冻结、风控拒绝等业务拒绝不得触发离线支付。定义每卡/每终端离线额度、最长离线时长、卡状态缓存新鲜度、终端丢失/撤销策略、序号回退和本地存储损坏处理。
4. **未知结果与恢复屏障**：定义在线请求超时但服务端可能已扣款时的同键查询/重试行为，以及断线期间本地扣款后如何避免恢复联网时旧云端余额导致重复可用额度。普通在线模式只能在离线流水已同步且入账/保留额状态满足确认条件后恢复。
5. **人员与身份数据**：首期消费仍依赖人员/卡介质权威来源，需确定数据源、同步/撤销时限和接口契约；门禁服务不拥有人员主数据。门禁与核验列为二期扩展，刷脸/人证数据在二期范围确定后另行评审，不把生物特征数据默认写入通用设备日志。
6. **门禁生命安全**：门禁不属于首期。二期开发前，按实际控制器和门型验证快照过期、断电/断网、撤权、消防联动及紧急疏散行为；阶段 0/一期不臆定统一 fail-open 或 fail-closed 策略。
7. **目标组件与合规口径**：核验 Boot/Cloud/Alibaba BOM 官方兼容矩阵及指定 JDK、操作系统、数据库、缓存和消息产品的目标版本组合。确认系统定级、等保/密评适用性、产品认证和密码应用要求；方案文档不能代替有资质机构的意见或厂商联合适配报告。
8. **身份与网络边界**：定义用户登录的身份提供方、网关用户鉴权、服务间身份认证/授权、管理操作职责分离和数据库最小权限。网关鉴权不能替代服务间调用认证，也不能保护可被绕过网关直接访问的服务端口；风控与设备协议入口须明确为内部/设备专用边界，不应默认作为用户 API 暴露。
9. **对账与清结算责任**：账户服务维护权威账本并负责本地入账完整性；清结算服务负责跨来源/日终对账、差错分流和结算。清结算不得直接写账户账本；报表不得给在线交易库造成不可控负载。

上述决策应记录在 `docs/adr/`，并形成接口状态机、数据责任矩阵、部署拓扑、威胁模型和验收指标。资金状态、在线/故障切换状态机、恢复屏障、目标组件兼容、终端离线额度和门禁生命安全决策未完成前，不进入对应业务实现阶段。

## 3. 测试与性能门槛

### 每阶段必须完成

- 单元测试覆盖正常、边界、重复请求和失败路径；服务契约测试验证请求/响应兼容；关键跨层路径执行集成测试和 API 冒烟。
- 涉及数据库的变更要测试迁移、回滚/恢复策略、并发和事务边界；涉及消息的变更要测试重复、乱序、延迟、积压和重放。
- 每个阶段提交测试结果和性能报告，报告包含环境规格/配置、数据量、预热与运行时间、并发模型、吞吐、p50/p95/p99、失败/超时率、CPU/内存/GC、数据库连接池与慢查询、队列积压/恢复时间。
- 失败注入必须覆盖阶段实际依赖：下游超时、连接中断、进程重启、重复投递及依赖恢复后的自动收敛。资金链路还须验证账本不变量和无重复副作用。

### 容量指标的确定方式

阶段 0 已取得设计输入：8,000 名发卡用户、2 个食堂、4 个消费站点。约 150 台终端、其中门禁约 100 台是既有规划估算，尚无资产清单核实；门禁属二期。单站点压力目标为 800 笔/分钟，四站点可并发达峰，全平台为 3,200 笔/分钟；持续 30 分钟对应用户确认的 96,000 笔新设计压力目标。交易类型比例目标为消费 ≥90%、充值/补助 ≤8%、退款/冲正 <2%。旧约 16,000 笔/日输入已作废；96,000 笔不代表历史实测或生产容量达标。其余离线、渠道、留存设计输入见阶段 0 业务范围文档，合同/厂商能力和法规适用性仍需核实。当前先在本地机器和已盘点的 16 GB 开发服务器建立可复测的开发容量基线；真实业务规模和生产资源确定后，再批准生产逐服务吞吐、p95/p99、错误率、积压上限、恢复时间及资源上限。分钟峰值折算只能作为均匀流量参考，不代表生产 SLO，也不得将开发测试结果宣称为生产容量达标。

开发阶段性能场景逐步覆盖基准/稳态、阶段性并发、依赖故障和恢复补压。生产级峰值、突发、压力上限、长稳与离线积压清空目标待业务负载和生产服务器确定后执行。报告只对记录的硬件、版本、数据量和配置有效；服务器扩容或更换后需复测。

现有 k6 的 `http_req_failed < 1%`、关键接口 `p95 < 500ms`、`checks > 99%` 是脚手架模板值，不是已批准的开发 SLO 或生产容量承诺。业务接口上线后须按已记录的逐接口开发 SLO 设置 k6 阈值，并覆盖真实业务断言。不得用 Actuator 健康接口压测代替业务场景压测。

## 4. 分阶段实施

### 阶段 0：业务基线、架构决策与技术验证

**前置条件**：无。资金主链路和端侧实现不得绕过本阶段未决项。

**交付**：确认在线为默认、意外断线才故障切换的消费状态机；确定断线判定、防抖、业务拒绝分类、未知结果在途交易的待确认策略、同键查询/重试、离线额度和恢复屏障。确认人员与账户数据来源、各端责任、数据分类和合规适用性；冻结首批 API/事件契约草案、幂等键、状态码、故障语义和版本兼容规则，明确支付回调、结算入账和通知事件的调用方向/投递方式；核对当前工程软件版本并记录本地/16 GB 开发服务器基线。目标生产 OS/CPU/JDK 发行版适配、生产容量 SLO 与资源预算暂缓，目标生产环境和业务规模可用后复核；其余关键选择写为 ADR。

**验证**：先在当前本地环境构建、运行现有测试和可用的依赖 PoC；本地通过后再在 16 GB 开发服务器复测，并记录 Maven 实际 JDK、OS、CPU、内存和依赖版本。生产 OS/CPU/JDK 发行版联合适配延期。后续针对选定的 Nacos、数据库、缓存和消息执行配置/迁移/事务/并发/重复投递测试；对业务拒绝、网络延迟/丢包/断开、服务端已提交但响应丢失、链路抖动和恢复做状态机测试，验证断线故障切换和幂等行为。

**性能/压力**：按目前可获得的负载输入，先测本地环境，再测 16 GB 开发服务器；记录基准结果和资源消耗，不据此估算生产承载。真实业务峰值和生产服务器明确后再批准生产容量与压力测试退出阈值。

**退出条件**：先决决策 1-9 对开发基线范围均有结论记录；当前软件组合在本地/开发环境有可复测的构建与必要 PoC 结果；开发环境测试门槛已记录；私人仓库凭据事项按已确认范围豁免；生产 OS/CPU/JDK 发行版适配和生产容量 SLO 明确延期且有恢复条件。未通过开发基线时不进入阶段 1；通过也不代表生产适配、容量或合规验收通过。

阶段 0 与阶段 1 的任务边界独立。阶段 0 的详细任务和出口检查见 [`tasks/phase0-plan.md`](../tasks/phase0-plan.md)，执行状态记录在 [`tasks/phase0-todo.md`](../tasks/phase0-todo.md)。阶段 0 按 2026-11-04 临时开发基线出口通过，暂定决策、五类证据处置及阶段 1/生产启用门禁见 [`阶段0-出口评审.md`](阶段0-出口评审.md) 和 [`阶段0-待确认事项与暂定方案.md`](阶段0-待确认事项与暂定方案.md)。该结论允许受限开发，不代表真实渠道、生产容量、终端离线或合规验收。业务范围及规模输入见 [`阶段0-业务范围与规模输入.md`](阶段0-业务范围与规模输入.md)。

### 阶段 1：工程与运行平台

**依赖**：阶段 0。

**交付**：CI 构建与测试门禁；配置导入、服务注册/发现、网关外部路由白名单与鉴权、服务间认证、超时/限流/熔断；用户、管理、设备协议和内部接口分区；统一错误结构、traceId、审计日志和业务指标；按服务隔离数据库 schema/账号及 Flyway 迁移；本地与 CI 可重复启动的目标中间件环境；健康检查和告警落盘配置。

**验证**：全量 `.\mvnw.cmd --batch-mode --no-transfer-progress verify`；配置缺失/不可达、未授权/过期身份、越权服务调用、路由错误、超时和熔断的自动化测试；确认外部入口不能访问风控内部 API、设备协议端口和 Actuator 敏感端点；迁移从空库和上一版本升级测试；密钥不进仓库和日志；依赖、容器镜像及配置安全扫描。监控须能区分业务健康与进程存活。

**性能/压力**：先在本地、后在 16 GB 开发服务器测量网关单跳开销、服务间调用延迟和鉴权吞吐；对注册中心/配置刷新、连接池、日志和指标采集做阶段性并发及故障恢复测试；结果只作开发基线。生产服务器更换或业务规模确定后按新环境重测。

**退出条件**：CI 门禁可重复通过；认证、路由、配置、迁移和可观测性均有自动化证据；性能报告通过阶段 0 批准的开发环境门槛。该结果不是生产容量结论。

阶段 1 的具体任务、依赖、验证命令和检查点见 [`tasks/phase1-plan.md`](../tasks/phase1-plan.md)，执行状态记录在 [`tasks/phase1-todo.md`](../tasks/phase1-todo.md)。

### 阶段 2：账户、卡务与账本

**依赖**：阶段 1；资金分录和账户状态模型已由阶段 0 评审。

**交付**：账户/卡介质生命周期、余额查询、冻结/解冻、入账/扣款、不可变账务分录和审计；同一账户操作的并发控制、幂等接口、数据迁移与权限隔离。只有账户服务能写账户余额和账本。

**验证**：金额精度、余额不透支/不违反账户状态、借贷分录平衡、冻结卡拒绝交易；重复幂等键、并发扣款、事务回滚、数据库断连/重启及迁移升级集成测试；按账务规则做属性/对账测试。

**性能/压力**：分别测多账户均匀负载与单账户热点争用、扣款/充值混合、数据库连接池饱和和索引规模增长；报告吞吐、尾延迟、锁等待、CPU/IO 和错误率。不能只测余额查询。

**退出条件**：并发和异常测试不破坏账务不变量；迁移与恢复通过；扣款/入账性能达到批准的账户服务目标。

阶段 2 的任务、当前项目基线和验收方式见 [`tasks/phase2-plan.md`](../tasks/phase2-plan.md)，执行状态记录在 [`tasks/phase2-todo.md`](../tasks/phase2-todo.md)。阶段 2 依赖阶段 1 退出评审；当前阶段 1 检查点 A/B/C 与退出评审仍未完成。

### 阶段 3：实时风控

**依赖**：阶段 2 的账户/卡状态契约，阶段 1 平台。

**交付**：限额、频次、黑名单、规则版本和命中理由；规则可审计发布/回滚；在线交易的超时与拒绝语义，以及离线补传的复核规则接口。

**验证**：边界额度、跨日窗口、并发计数、规则更新竞态、重复请求、数据缺失和规则服务不可用；审计中能追溯规则版本和决定；对拒绝/降级结果做安全测试。

**性能/压力**：以阶段 0 的交易峰值回放规则评估；测规则命中与未命中、黑名单热点、规则刷新时延、缓存失效及下游慢响应下的吞吐和尾延迟。

**退出条件**：规则结果可重复解释、失败策略明确、关键交易目标负载下不超 SLO，风控不可用不触发静默放行。

### 阶段 4：在线交易编排

**依赖**：阶段 2、3；阶段 0 已确定交易状态机和账户写入推进机制。

**交付**：消费/充值交易状态机、业务流水、客户端幂等键、调用风控和账户服务的编排、未知结果查询、重试/补偿与审计；交易服务不直接写账户表。确认成功响应只能在账户写入结果可确定后返回。

**验证**：账户已提交而响应丢失、风控超时、交易进程在每个状态转换点重启、重复/乱序消息、重复客户端请求、重试到不同实例；证明同一业务效果只应用一次、未知结果在途交易保持待确认并可用原幂等键查询/重试、不被转成本地成功、失败不会伪报成功。余额不足、卡冻结、风控拒绝等业务拒绝必须原样返回，不得被终端解释为断线故障切换。跑完整交易 API 冒烟和账务对账。

**性能/压力**：消费高峰、账户热点、风控调用延迟分布、下游部分超时/限流下的端到端压力与持续测试；观测交易状态积压、线程池、连接池及账户锁等待。

**退出条件**：状态机无无法解释的终态；所有写请求可幂等恢复；资金不变量通过混沌/故障测试；在线交易性能达到批准目标。

### 阶段 5：设备接入与可靠投递

**依赖**：阶段 1、4 的事件/命令契约；设备协议和认证方案已确定。

**交付**：设备登记和身份校验、协议适配器、设备影子、命令版本/确认、断线重连与连接状态上报、按业务语义隔离的消费/核验/通行队列、死信与可见告警。明确哪些协议由本服务终止，哪些由设备厂商网关转发；终端支付故障切换由端侧执行，不依赖断线后仍可达的中心命令。

**验证**：无效签名、伪设备、重放、畸形/分片报文、重复/乱序/延迟、断连后重连、消息持久化、死信回放和限流；核验与通行日志不得挤占消费补传；设备影子版本冲突测试。

**性能/压力**：并发连接数、突发上报、消息峰值、断线重连风暴和下游不可用积压测试；验证消费队列优先级、反压生效和依赖恢复后排空时间。

**退出条件**：设备身份不可伪造，投递状态可追踪；审计事件不丢不并；队列隔离和恢复能力达到阶段 0 批准指标。

### 阶段 6：终端断线故障切换与补传

**依赖**：阶段 2、3、4、5；终端厂商/客户端兼容契约或测试设备可用。

**交付**：实现在线默认、意外断线达到批准阈值后才启用本地支付的端侧状态机；明确业务拒绝与链路故障分类、阈值/防抖/恢复观察期。交付终端持久化账本和 WAL、单调本地序号、离线额度/时长策略、补传 API、序号缺口与重复检测、受理/入账/待复核/冲正状态、恢复屏障、人工差错入口和可观测积压。每笔交易在首次尝试受理前生成并持久化幂等键；结果未知的在途交易保持待确认，用原键查询/重试，不得转成本地成功；故障切换后的后续新交易使用新的本地序号和幂等键。终端代码不在本后端仓库时，交付设备模拟器和真实硬件联测报告。

**验证**：正常在线消费与意外断网故障切换、连续失败阈值/抖动防切换、业务拒绝不切换、请求超时但服务端已提交时当前交易保持待确认并同键收敛、后续新交易正常走离线故障切换且不产生第二笔扣款、断网消费、重复补传、乱序/缺口、时钟漂移、序号回退、存储空间耗尽、进程/设备断电发生在落盘前后、账本损坏恢复、卡片冻结/撤销后的离线行为、风险拒绝/不可用、平台重复响应和人工复核；链路恢复后先同步并完成账务收敛，再解除恢复屏障。核对终端流水、交易状态与账户分录逐笔一致。

**性能/压力**：测量在线默认模式的吞吐与 p95/p99；模拟最长获批断线窗口形成的积压，在在线消费持续发生时恢复补传；验证故障检测与恢复抖动下的稳定性、幂等存储增长、按终端保序、公平性、限流和清空积压时限，确认补传洪峰不突破在线交易 SLO。

**退出条件**：在线为默认模式且业务拒绝不触发本地支付；只有批准的意外断线条件可进入故障切换；终端已确认的流水最终均可追踪到入账或明确差错终态；恢复屏障未解除前不按旧云端余额恢复普通在线扣款；无重复账务副作用，真实终端断电恢复和补传测试通过。

### 阶段 7：门禁权限与离线快照

**依赖**：阶段 1、5；阶段 0 已记录人员数据源、门型和生命安全策略。

**交付**：人员/门组/时间权限契约、快照版本与最大离线有效期、签发/验签/密钥轮换、设备下发确认、校时顺序、完整通行审计事件及过期后的设备行为。

**验证**：过期、撤权、旧版本重放、快照篡改、签名失败、设备时钟偏移、掉电/断网、密钥轮换和恢复同步；不同门型、消防联动和疏散场景在真实控制器上验证，不以模拟器单独验收生命安全行为。

**性能/压力**：全量人员/门组快照构建、批量设备下发、策略变更风暴和离线设备集中重连；检查设备确认率、快照生成/下发尾延迟与审计事件接收能力。

**退出条件**：超期/撤权按已验证策略执行；签名和密钥流程可轮换；安全审计完整；真实设备验收结果有记录。

### 阶段 8：支付渠道适配

**依赖**：阶段 2、4；渠道状态、签名规范、商户账户和清分规则已确认。

**交付**：渠道请求/响应防腐层、签名验签、nonce/重放保护、回调接收、支付状态查询、退款/冲正、渠道对账数据及与账户服务的幂等入账契约。渠道状态与账户入账状态分开记录。

**验证**：沙箱和虚拟渠道测试成功、拒绝、超时但渠道成功、重复/乱序回调、伪造签名、回调重放、渠道不可用和退款部分成功；未确认结果不得重复扣款或重复入账。

**性能/压力**：使用虚拟渠道或厂商许可的沙箱并发，不对真实支付渠道施加未授权压力；测各渠道响应分布、回调洪峰、连接隔离和限流下的交易恢复。

**退出条件**：所有渠道状态能收敛或进入可审计差错终态；签名/回调安全测试通过；性能在渠道配额和批准 SLO 内。

### 阶段 9：通知服务

**依赖**：阶段 1；消费回执、风险复核和支付通知事件已定义。

**交付**：短信/Push/模板消息适配、模板版本、用户偏好、敏感字段脱敏、事件幂等键、重试退避、限流、死信和发送结果查询。通知失败不回滚已完成资金交易。

**验证**：模板缺失/错误、供应商超时/限额、重复事件、乱序状态、退订、敏感信息日志检查、重试耗尽和人工重放；验证通知状态不会反向改变账务状态。

**性能/压力**：以通知峰值和渠道限额压测异步队列，测试大批量通知、供应商慢/停机、积压告警和恢复排空，不让通知消费线程占用交易关键线程池。

**退出条件**：事件至发送结果可追踪、隐私与限流策略通过、通知故障与交易主链路隔离。

### 阶段 10：清结算、跨来源对账与差错处理

**依赖**：阶段 2、4、6、8 的数据契约和业务 ID 稳定；交易与终端流水字段从产生之日起可追溯。

**交付**：日切规则、交易/账户/终端/渠道对账批次、重复/缺失/金额不一致分类、幂等更正/冲正、人工复核和双人审批、清分结算结果经账户契约提交、报表只读副本/数仓方案。所有输入和规则版本可重跑、可审计。

**验证**：基准交易、退款、离线补传、晚到回调、重复/缺失/错金额、跨日交易、批次中断重跑和人工调整；证明重跑不重复结算；抽样将终端流水、交易流水、账户账本和渠道单逐笔及汇总核对。

**性能/压力**：使用批准的最大日交易量及积压补传量运行完整批次；测全量读取、索引/分区、差异率、峰值内存、资源隔离及批次完成时间。并行运行报表负载，确认不拖慢交易和对账截止时间。

**退出条件**：所有输入可追溯、差错闭环、批次可安全重跑；在目标数据量下于批准窗口内完成，不对账户/交易在线库形成不可接受影响。

### 阶段 11：端到端验收、韧性与试点

**依赖**：阶段 1-10 全部通过；生产目标环境、设备和渠道沙箱可用。

**交付**：端到端业务验收、生产部署/回滚、容量与扩容策略、备份恢复和灾难恢复演练、运行手册、告警/值班路径、数据迁移计划、灰度/试点方案和试点回滚条件。

**验证**：在线消费/充值、意外断线故障切换与恢复补传、业务拒绝不触发本地支付、在线结果未知时同键收敛、门禁权限撤销和离线超期、支付成功与未知结果、退款、清结算差错的完整业务演练；执行权限/安全渗透、依赖和镜像漏洞、敏感日志、数据恢复、节点/数据库/消息故障注入。全链路审计和告警都须能定位业务 ID。

**性能/压力**：按目标生产拓扑执行基准、峰值、突发、压力上限和至少 24 小时长稳测试；执行数据库/消息故障期间的退化和恢复补压，测扩容前后吞吐、尾延迟、错误率、资源和积压清空时间。用实测结果确认逐服务 SLO 与容量余量，不引用厂商宣传值代替实测。

**退出条件**：所有业务与安全验收通过；无未处置的阻断级缺陷；备份恢复达到设定的 RTO/RPO；告警、回滚和运行流程演练有效；试点范围扩大的条件与证据已记录。

## 5. 阶段通用完成定义

- 需求、API/事件契约、状态机、数据迁移和运维说明已更新，新增架构决策有对应 ADR。
- 单测、契约测试、集成测试和核心 API 冒烟均进入 CI；没有跳过测试或放宽断言来通过门禁。
- 有关联业务 ID 的日志、指标、审计和告警；敏感数据按已批准规则脱敏/加密，配置与密钥不提交仓库。
- 性能报告可复现，阈值来自阶段 0 批准的负载和 SLO；每个阶段的性能/安全/故障门禁通过后才能依赖其结果。
- 资金和权限变化均有可追踪终态；故障恢复后可证明没有重复资金副作用、漏失审计事件或未授权放行。
