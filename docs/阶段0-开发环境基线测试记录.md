### Keycloak OIDC PoC 方法

使用随机生成、仅在 PowerShell 进程环境中使用的临时管理员和测试用户密码；不输出或保存密码/token。PoC 使用 loopback 端口 `18088`、独立网络和临时 realm：

1. 以 digest 固定的 `quay.io/keycloak/keycloak:26.8.1` 镜像运行 `start-dev`，设置 `KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD`，仅映射 `127.0.0.1:18088:8080`，内存上限 1 GiB。
2. 通过 `/realms/master/.well-known/openid-configuration` 等待 discovery ready；以临时管理员凭据从 master realm 的 OIDC token endpoint 获取管理 access token。
3. 通过 Admin REST API 创建临时 `phase0` realm、关闭 browser flow 的临时 public test client（启用 direct access grant，仅用于 PoC）、一个 realm role 和一个测试用户；为用户设置随机临时密码并分配该 realm role。
4. 通过 `/realms/phase0/protocol/openid-connect/token` 获取测试 access token；仅在本机解码 JWT payload，对照 phase0 discovery issuer 和 token `iss`，核对 `realm_access.roles` 为数组且含分配角色，并记录默认 `aud=account`、token type `Bearer`。此步骤验证 discovery/claim 结构，不替代签名验证、resource-server 验证或权限测试。
5. `finally` 清理临时 Keycloak 容器和 Docker 网络；临时密码与管理 token 变量清空。测试容器和网络已确认删除。

该 direct access grant 客户端只用于隔离 PoC，不能作为生产登录流程建议。正式 issuer、API audience、用户登录/client 类型、角色值和授权策略均未在此测试中确定。

历史账户服务启动与 Nacos PoC 使用旧 BOM；新 BOM 的 clean verify 和账户服务启动另在上表记录。旧 Nacos PoC 的运行时 `java` 为 Temurin JDK 25.0.5，Nacos 客户端实际版本为 3.1.1。两次历史 k6 检查请求的都只有 `/actuator/health`；吞吐约 1 请求/秒是脚本 `sleep(1)` 的结果，不代表服务容量，也没有覆盖业务接口。
