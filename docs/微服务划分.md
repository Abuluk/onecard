# 一卡通系统微服务架构设计文档

**版本**：1.0  
**日期**：2026-11-02  
**状态**：服务边界定稿；实现前置决策见《开发阶段规划》阶段 0
**适用范围**：食堂刷卡消费、门禁通行，含离线可用性要求


## 1. 设计目标与核心原则

### 1.1 目标

一卡通系统以在线交易为常态：终端正常连接平台时，由账户服务权威扣款。消费离线只作为终端遇到意外断线后的有界故障切换；恢复后完成流水同步和账务收敛再回到在线模式。门禁离线策略独立于消费支付切换。

### 1.2 三条不可妥协的设计原则

**原则一：在线资金的唯一权威源是账户服务。** 余额扣减的强一致性只能收敛在 `onecard-account-service` 的事务边界内。交易服务负责编排，不持有余额写权限。

**原则二：在线是默认支付模式，离线仅由意外断线触发。** 余额不足、卡冻结、风控拒绝等业务结果不是断线，不得触发本地支付绕过。断线期间只允许在已确认的缓存新鲜度、单卡/终端额度和最长离线时间内使用终端本地账本；联网后本地流水作为**待验证输入**进入平台入账与对账流程。账户服务负责账户账本及入账完整性；清结算服务负责跨来源、日终交易对账与差错分流。

**原则三：门禁离线与消费离线的事务语义根本不同，不得共用同一套补传重试机制。** 门禁离线是“放行缓存”——通行事件可乱序到达但必须完整留存；消费补传采用至少一次投递、服务端幂等去重，实现业务效果只入账一次，并按终端本地序号保序、让失败立即可见。网络本身不提供端到端恰好一次投递保证。


## 2. 服务清单与职责边界

共 8 个服务。`gateway/` 作为独立 API 入口不在业务服务计数内。

| 服务 | 职责 | 边界纪律 | 离线职责 |
|---|---|---|---|
| **`onecard-account-service`** | 账户与卡务：余额、状态、冻结/解冻、介质生命周期 | **在线资金唯一权威源**。余额变更及账户账本必须在此事务边界内完成 | 校验并执行已确认的离线入账；不承担跨来源日终对账 |
| **`onecard-transaction-service`** | 消费、充值入账的编排与流水记录 | 发起交易、**幂等受理离线补传**；不持有余额写权限 | 离线消费补传的幂等校验（幂等键：终端号+本地流水号），维护受理状态与序号进度 |
| **`onecard-payment-adapter-service`** | 首期支付渠道适配：微信、支付宝、云闪付聚合支付；路由、签名验签、回调 | 防腐层，隔离外部渠道变更；与 API 网关语义彻底区分；实体校园卡消费由交易/账户链路处理 | 无离线职责 |
| **`onecard-clearing-service`** | 清结算与对账：跨来源日终对账、商户清分、差错处理、结算报表 | **不参与实时链路**；内部按能力域拆分（见 §7），不直接写账户余额 | 离线终端流水与在线交易一并纳入对账输入 |
| **`onecard-notification-service`** | 短信、Push、微信模板消息统一出口 | 横向支撑，无资金逻辑 | 无离线职责 |
| **`onecard-risk-service`** | 限额、频次、黑名单、异常模式拦截 | **实时前置服务**，同步嵌入交易链路 | 离线补传交易同样经过风控检查，不因“离线”绕过 |
| **`onecard-access-service`** | 门禁：人员-门组-时段权限模型；**离线策略快照**生成与签发；通行审计 | 不处理人员主数据、不处理资金、不与控制器长连接 | 策略快照的签名、**最大离线有效期**管理；通行记录接收 |
| **`onecard-device-service`** | 多协议设备通道（TCP/HTTP/MQTT）、**设备影子**、在线状态感知、批量下发与回传调度 | **只负责可靠送到与可靠取回**，不参与权限或扣款决策 | 回传队列**按业务语义隔离**；消费流水队列优先级高于通行事件 |

**支付适配服务的命名说明**：原 `onecard-payment-gateway-service` 更名为 `onecard-payment-adapter-service`。名称中的“gateway”与 `gateway/` 模块的 API 网关语义重叠，更名消除歧义。它是支付上下文内的**渠道适配器**，不是入口组件。


## 3. 消费支付：在线优先 + 断线故障切换

### 3.1 权威点声明

正常情况下终端在线向平台发起消费，账户服务是余额权威源。只有终端检测到意外通信中断并达到阶段 0 确认的判定条件后，才使用账户服务预分配给卡/终端组合的有限离线预留额度；本地额度不是日常消费的第二权威源。

| 维度 | 在线模式（默认） | 断线故障切换 |
|---|---|---|
| 余额权威 | 账户服务实时余额 | 账户服务预留额度的终端侧受限副本 |
| 进入条件 | 服务可达且交易结果可确定 | 意外断线达到检测阈值；具体阈值和防抖由阶段 0 确定 |
| 业务拒绝 | 返回业务拒绝，不改支付模式 | 不适用；不得用离线模式绕过拒绝 |
| 对账时机 | 在线交易即时入账 | 恢复后按序补传并完成账务收敛 |
| 主要风险 | 网络超时后的交易结果未知 | 本地序号回退、账本损坏、缓存过期或额度耗尽 |

账户服务在线签发有限离线额度并从可用余额中预留；额度按卡/终端绑定，带版本、有效期和金额/笔数上限。终端只能消费已签发额度，不能以缓存余额自行扩额。故障切换需区分链路不可用、业务拒绝和请求结果未知；不能仅凭单次超时认定交易未处理。进入/退出阈值、连续失败数、恢复观察期和防抖策略由阶段 0 与端侧联测确定，避免抖动时反复切换。

### 3.2 幂等键

终端在首次尝试受理每笔交易前生成并持久化唯一幂等键；同一交易的查询、重试和补传始终沿用该键。进入故障切换后，每笔后续新交易分配新的本地序号和幂等键。键格式为：

```
{terminal_id}:{local_seq_no}
```

`local_seq_no` 是终端本地单调递增序号，不是时间戳。使用时间戳会在时钟回拨时产生碰撞键。同一笔离线交易无论重传多少次，`onecard-transaction-service` 以该键做唯一性检查；结合账户服务的入账幂等约束，保证业务效果只入账一次。终端按序重传，服务端对序号缺口和乱序作显式记录，不依赖时间戳决定幂等性。

### 3.3 关键纪律

**正常交易优先在线。** 在线模式从平台取得权威交易结果；本地余额和额度只用于符合策略的断线故障切换。

**只对断线切换。** 余额不足、卡状态拒绝、风控拒绝等确定的业务结果必须返回原结果，不得回退为本地支付。连接超时且结果未知时，先用原幂等键查询/重试；不能生成第二个支付键。

**结果未知的在途交易不转成本地成功。** 该笔交易保持待确认，并在恢复连接后用原幂等键查询或重试以收敛结果。终端进入断线故障切换后，后续新交易可按本地策略处理，并各自使用新的本地序号和幂等键。

**落盘先于离线受理提示。** 只有进入故障切换且本地预留额度、卡状态均满足条件时，才将交易写入本地持久化存储（SQLite/Realm/LevelDB + WAL）；落盘成功后提示“离线消费已受理，联网对账中”，不提示平台已完成记账。

**补传只写交易，不写主数据。** 离线补传的职责边界是交易流水。人员信息、账户状态、门禁权限等主数据不得通过消费补传通道回传，避免补传通道演变成第二条主数据写入路径。

**补传后必须经过风控。** 离线期间无法实时执行的限额、频次、超额检查，在补传时由 `onecard-risk-service` 执行。复核期间交易保持 `NEED_REVIEW`，对应预留额度继续占用且不返还可用余额；审核通过时账户服务在本地事务中正式记账并结清该笔预留。审核拒绝不得删除已受理流水，必须经可审计的补偿/冲正流程处理，资金结果未收敛前继续保留预留。风控暂不可用时持久化待处理并重试，不静默放行或丢弃。


## 4. 门禁离线：策略快照 + 有界自主

### 4.1 与消费离线的语义对比

| 维度 | 消费离线 | 门禁离线 |
|---|---|---|
| 事务语义 | 记账事件：余额变更 | 状态机事件：物理继电器动作 |
| 失败后果 | 资金差错 | 权限判断失败时按现场确认的安全策略处理，并保留紧急疏散行为 |
| 补传顺序 | **必须幂等并按序提交** | 可乱序到达，保留事件 ID 与设备时间用于审计 |
| 补传合并 | 不可合并 | 审计通行事件不得合并；仅设备状态快照允许按版本合并 |
| 风险窗口 | 透支、重复入账 | 权限撤销延迟生效 |

### 4.2 策略快照

`onecard-access-service` 在设备在线时生成并签名**策略快照**，经 `onecard-device-service` 下发至门禁控制器。快照内容包括：该门组授权人员标识列表、有效时段规则、快照版本号、签发时间、**最大离线有效期**。

快照的完整性与防篡改由国密体系保障：PSAM 安全模块与 SM2/SM3/SM4 算法用于签名和加密，设备端验签通过后才载入本地决策引擎。策略快照必须在设备本地完整缓存，不能依赖云端临时下发，否则断网瞬间决策即失效。

### 4.3 有界离线

**最大离线有效期**是门禁离线安全性的核心参数。超过有效期后，控制器必须执行经现场安全评审确认的 **fail-closed** 策略或仅允许应急凭证通行，不得无限期信任陈旧白名单。该策略不得阻断消防、紧急疏散等生命安全行为；不同门型的 fail-safe/fail-secure 行为须在真实控制器上验证。

恢复连接后的同步顺序是确定的：**先校准时钟，再拉取最新策略快照，最后按序补传通行记录**。时钟校准必须先于快照拉取，否则快照的有效期判断可能在错误时钟下失效。


## 5. 设备接入层：通道可统一，语义必须隔离

`onecard-device-service` 的职责边界是协议适配与可靠投递。它不参与“这个人能不能进门”或“这笔钱扣没扣”的业务决策。

### 5.1 回传队列的语义隔离

这是整个离线架构中最容易出错、后果最直接的设计点。三套队列不得共用同一 MQTT 主题与同一重试 backoff：

| 队列 | 载荷 | 重试策略 | 失败可见性 | 优先级 |
|---|---|---|---|---|
| **消费流水** | 金额、幂等键、本地流水号 | **必须幂等**，按终端保序 | 窗口立刻感知 | 最高 |
| **人证核验** | 会话、证摘要、比对分 | 可延迟 | 前台可改人工 | 中 |
| **通行事件** | 门、人员标识、决策结果 | 以事件 ID 去重并完整保留；允许乱序到达 | 权限审计可见 | 低 |

如果消费流水与核验结果、通行审计日志共用同一条 MQTT 主题和同一 backoff，食堂高峰的消费补传会被其他流量挤成超时，窗口端的扣款确认延迟直接引发纠纷。通道层面可以统一接入，但**持久化保证、审计留存和重试优先级必须按队列隔离**；通行日志即使乱序到达，也必须通过事件 ID 去重并完整保留。

### 5.2 设备影子

设备影子保存期望状态与上报状态之间的差异，解决的是**状态同步**而不是在线状态展示。应用层无论设备是否联网，都可以从影子读取当前状态或下达指令，指令在设备上线后自动执行。但策略快照本身不走影子机制——快照必须完整缓存在端侧，影子只保存差异，不能替代端侧的离线决策数据。


## 6. 关键时序

### 6.1 在线消费 → 断线故障切换 → 联网补传

```
在线常态：
  识别用户 → 分配 terminal_id:local_seq_no 幂等键 → 在线请求交易
  → risk-service 校验 → account-service 扣款 → 返回确定状态

意外断线：
  本地链路检测达到批准阈值 → 检查当前请求是否已有云端结果
  ├─ 已处理/业务拒绝：返回原交易状态，不再本地扣款
  ├─ 结果未知：当前交易保持待确认，保留原幂等键，恢复后查询或重试
  └─ 断线状态已确认：后续新交易校验已签发预留额度和卡状态
       → 分配新的本地序号/幂等键 → 额度消费记录 WAL 落盘（OFFLINE_ACCEPTED）
       → 提示“离线消费已受理，联网对账中”

链路恢复：
  验证服务稳定 → 按终端序号补传，沿用原幂等键
  → risk-service 校验
       ├─ 通过：account-service 幂等记账并结清对应预留
       └─ 需复核/暂不可用：NEED_REVIEW，预留继续占用
  → 对账并更新本地剩余额度/服务端预留额
  → 满足恢复屏障后才恢复普通在线扣款模式
```

`NEED_REVIEW` 按 [ADR-0003](adr/0003-offline-payment-reserve-and-review.md) 处理：平台记录不可变的待复核交易，保留已预留金额，不向可用余额返还；通过后原子记账并结清预留，拒绝后走显式补偿/冲正。终端已受理的消费不得因风控超时或平台重试而静默丢失。恢复屏障按同一 ADR 收敛在线未知交易、离线流水和预留额度。

项目已确认在线优先、仅意外断线触发终端故障切换的方向；额度预留和复核资金策略见阶段 0 的 [ADR-0003](adr/0003-offline-payment-reserve-and-review.md)，数值阈值、有效期和设备级恢复行为须经联测确定。

### 6.2 门禁策略快照下发与离线决策

```
在线时：
  access-service 生成快照（版本号、有效期、人员-门组-时段规则）
  → 用 PSAM/SM2 签名 → 经 device-service 下发
  → 控制器验签 → 载入本地决策引擎

离线时：
  刷卡/刷脸 → 本地决策引擎比对快照 → 继电器动作
  → 写本地通行审计日志（可乱序补传，但不得丢弃或合并独立事件）

恢复连接：
  校时 → 拉取最新快照（验签） → 补传通行审计事件（事件 ID 幂等去重，完整留存）
```


## 7. 清结算服务的内部粒度

`onecard-clearing-service` 保持为清结算业务域的归属单元，但内部不得建设为“什么都在做的批处理单体”。跨来源交易对账、清分与结算由此服务负责；账户服务维护权威账本并提供查询/入账接口。按业务能力域组织为三个职责单一的组件或子部署单元：

| 子能力 | 职责 | 幂等/一致性约束 |
|---|---|---|
| **轧差/清算** | 按清算对象汇总交易、计算应收应付净额 | 输入为已确认的交易流水，不直接读写账户余额 |
| **交易一致性校验/对账** | 将离线终端流水、在线交易、渠道回调三者交叉核对；账户账本作为权威核对来源 | 差异分类：重复、缺失、金额不符，分别进入可审计的更正或人工队列 |
| **幂等结算结果提交** | 将清算结果通过账户服务契约提交入账，清结算服务不直接写账户账本 | 幂等键基于 `business_id + seq_no`，幂等窗口覆盖最长对账周期 |

**报表与分析类查询不得跑在清结算联机库上。** 只读副本或数仓是报表的唯一承载位置。账户服务不重复运行同一批跨来源对账任务，避免差异处理和冲正职责分裂。


## 8. 风险矩阵

| 风险 | 触发条件 | 影响 | 缓解措施 | 责任服务 |
|---|---|---|---|---|
| 离线消费重复入账 | 补传重试、网络抖动 | 资金多扣/多入 | 终端生成幂等键；服务端唯一约束 | transaction-service |
| 离线消费漏传 | 终端存储损坏、队列丢失 | 账实不平 | 本地 WAL；交易服务记录补传进度，清结算服务日终对账并分流差错 | transaction-service / clearing-service |
| 终端序号回退或时钟漂移 | 本地计数器/时钟异常 | 幂等键冲突或事件时间失真 | 本地序号持久化；单独检测时钟漂移、重复与序号缺口 | transaction-service / device-service |
| 门禁快照过期后仍放行 | 终端未执行 fail-closed | 权限撤销失效 | 强制最大离线有效期；超期 fail-closed | access-service |
| 消费补传被通行日志挤占 | 共用 MQTT 主题/backoff | 窗口扣款确认延迟 | 回传队列按语义隔离，消费优先 | device-service |
| 清结算报表拖垮联机库 | 报表查询直连联机库 | 对账任务超时、影响日终 | 报表走只读副本或数仓 | clearing-service |


## 9. 落地路线图

**第一阶段：主链路（账户 + 交易 + 风控 + 设备 + 门禁）**

`account-service` 与 `transaction-service` 分别拥有各自的数据与写入边界：账户余额及账本分录在账户服务本地事务内完成，交易服务通过契约编排并持久化交易状态，不跨服务共享表或数据库事务。跨服务的可靠执行机制（例如持久化消息/outbox 或明确的幂等状态机）须在阶段 0 决策并验证。`risk-service` 以独立服务部署，`device-service` 与 `access-service` 随场景就位。**离线消费的幂等键必须在接口设计的第一天落定**。

**第二阶段：支付适配与通知**

`payment-adapter-service` 更名并独立部署；`notification-service` 轻量上线。这两个服务不参与离线主链路，可以在主链路稳定后并行推进。

**第三阶段：清结算内部拆分**

`clearing-service` 在账户、交易、支付及终端数据契约稳定后实现跨来源对账、清分和结算。交易与设备阶段必须从第一天生成稳定业务 ID、保留原始终端流水与入账状态，使后续对账有完整输入；阶段 10 再实现并压测对账批次。


## 10. 附：与 `project-root` 目录的对应关系

| 服务 | `services/` 目录 | `apis/` 契约模块 |
|---|---|---|
| 账户 | `services/onecard-account-service` | `apis/onecard-account-api` |
| 交易 | `services/onecard-transaction-service` | `apis/onecard-transaction-api` |
| 支付适配 | `services/onecard-payment-adapter-service` | `apis/onecard-payment-adapter-api` |
| 清结算 | `services/onecard-clearing-service` | `apis/onecard-clearing-api` |
| 通知 | `services/onecard-notification-service` | `apis/onecard-notification-api` |
| 风控 | `services/onecard-risk-service` | `apis/onecard-risk-api` |
| 门禁 | `services/onecard-access-service` | `apis/onecard-access-api` |
| 设备接入 | `services/onecard-device-service` | `apis/onecard-device-api`（仅内部命令/事件契约） |

`gateway/` 是用户/管理 API 入口，只做鉴权、全局限流和路由，**不得出现直连账户/交易数据库的 `mapper/` 与 `entity/`**。消费与门禁管理请求经网关路由至对应服务；控制器协议接入由 `device-service` 在隔离的设备网络边界处理。风控内部 API 和设备协议入口不得默认暴露为普通用户路由，必须有身份、授权和网络边界测试。


**文档结论**：八个服务的主体边界已经收敛。离线消费的幂等键、门禁快照最大有效期、消费补传的资金状态映射和设备安全策略必须在接口设计前明确，并在分阶段开发中以故障、恢复和对账测试验证。
