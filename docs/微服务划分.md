# 一卡通系统微服务架构设计文档

**版本**：1.0  
**日期**：2026-11-02  
**状态**：设计定稿  
**适用范围**：食堂刷卡消费、门禁通行，含离线可用性要求


## 1. 设计目标与核心原则

### 1.1 目标

一卡通系统在食堂与门禁两个场景下，必须同时满足两条看似冲突的要求：**在线时资金强一致，离线时业务不中断**。本文档定义的微服务边界与离线机制，以“在线收敛、离线有界”为总体原则，确保任何一笔消费或一次通行，在断网与恢复前后都不会产生资金差错或权限失控。

### 1.2 三条不可妥协的设计原则

**原则一：在线资金的唯一权威源是账户服务。** 余额扣减的强一致性只能收敛在 `onecard-account-service` 的事务边界内。交易服务负责编排，不持有余额写权限。

**原则二：离线余额的权威明确下放至终端，但“本地权威”不等于“本地免责”。** 断网期间终端本地记账是扣款成功与否的唯一依据；联网后终端流水作为**待验证输入**进入账户服务的对账链路，而不是被默认信任。账户服务的日终对账必须把离线终端流水与在线交易一并核对，差错进入人工处理。

**原则三：门禁离线与消费离线的事务语义根本不同，不得共用同一套补传重试机制。** 门禁离线是“放行缓存”——通行日志可以乱序、可以合并；消费离线是“记账恰好一次”——流水必须幂等、必须保序、失败立即可见。


## 2. 服务清单与职责边界

共 8 个服务。`gateway/` 作为独立 API 入口不在业务服务计数内。

| 服务 | 职责 | 边界纪律 | 离线职责 |
|---|---|---|---|
| **`onecard-account-service`** | 账户与卡务：余额、状态、冻结/解冻、介质生命周期 | **在线资金唯一权威源**。余额变更只能在此事务边界内发生 | 离线补传流水的**最终入账与日终对账**；不假设终端数据天然可信 |
| **`onecard-transaction-service`** | 消费、充值入账的编排与流水记录 | 发起交易、**幂等受理离线补传**；不持有余额写权限 | 离线消费补传的幂等校验（幂等键：终端号+本地流水号） |
| **`onecard-payment-adapter-service`** | 支付渠道适配：微信、支付宝、银联、NFC 圈存；路由、签名验签、回调 | 防腐层，隔离外部渠道变更；与 API 网关语义彻底区分 | 无离线职责 |
| **`onecard-clearing-service`** | 清结算与对账：日终对账、商户清分、差错处理、结算报表 | **不参与实时链路**；内部按能力域拆分（见 §7） | 离线终端流水与在线交易一并纳入对账输入 |
| **`onecard-notification-service`** | 短信、Push、微信模板消息统一出口 | 横向支撑，无资金逻辑 | 无离线职责 |
| **`onecard-risk-service`** | 限额、频次、黑名单、异常模式拦截 | **实时前置服务**，同步嵌入交易链路 | 离线补传交易同样经过风控检查，不因“离线”绕过 |
| **`onecard-access-service`** | 门禁：人员-门组-时段权限模型；**离线策略快照**生成与签发；通行审计 | 不处理人员主数据、不处理资金、不与控制器长连接 | 策略快照的签名、**最大离线有效期**管理；通行记录接收 |
| **`onecard-device-service`** | 多协议设备通道（TCP/HTTP/MQTT）、**设备影子**、在线状态感知、批量下发与回传调度 | **只负责可靠送到与可靠取回**，不参与权限或扣款决策 | 回传队列**按业务语义隔离**；消费流水队列优先级高于通行事件 |

**支付适配服务的命名说明**：原 `onecard-payment-gateway-service` 更名为 `onecard-payment-adapter-service`。名称中的“gateway”与 `gateway/` 模块的 API 网关语义重叠，更名消除歧义。它是支付上下文内的**渠道适配器**，不是入口组件。


## 3. 消费离线：本地权威 + 幂等补传

### 3.1 权威点声明

离线期间，消费的余额权威是终端本地。这一决策写入架构基线，不作为部署期可选项。

| 维度 | 本机余额（已采纳） | 平台余额（未采纳） |
|---|---|---|
| 断网可扣 | 是 | 否，网络抖动即窗口停摆 |
| 对账时机 | 联网后 | 实时 |
| 主要风险 | 时钟回拨、余额文件损坏 | 不可用风险高于差错风险 |

本机余额需要防范两类终端侧故障：**时钟回拨**导致补传顺序错乱和幂等键冲突；**余额文件损坏**导致透支或负余额。这两类风险由终端本地账本的 WAL 机制和补传时的服务端风控兜底，不能假设终端永不故障。

### 3.2 幂等键

幂等键由终端在本地落库时生成，格式为：

```
{terminal_id}:{local_seq_no}
```

`local_seq_no` 是终端本地单调递增序号，不是时间戳。使用时间戳会在时钟回拨时产生碰撞键。同一笔离线交易无论重传多少次，`onecard-transaction-service` 以该键做唯一性检查，保证云端只入账一次。

### 3.3 关键纪律

**落盘先于提示。** 终端识别成功不等于记账成功。必须先将交易写入本地持久化存储（SQLite/Realm/LevelDB + WAL），落盘成功后才向用户显示“扣款成功”。提示先于落盘是窗口纠纷的常见根因。

**补传只写交易，不写主数据。** 离线补传的职责边界是交易流水。人员信息、账户状态、门禁权限等主数据不得通过消费补传通道回传，避免补传通道演变成第二条主数据写入路径。

**补传后必须经过风控。** 离线期间无法实时执行的限额、频次、超额检查，在补传时由 `onecard-risk-service` 同步执行。风控不通过不阻断补传受理，但将交易标记为 `NEED_REVIEW`，进入人工复核队列，而不是静默入账。


## 4. 门禁离线：策略快照 + 有界自主

### 4.1 与消费离线的语义对比

| 维度 | 消费离线 | 门禁离线 |
|---|---|---|
| 事务语义 | 记账事件：余额变更 | 状态机事件：物理继电器动作 |
| 失败后果 | 资金差错 | 拒绝通过，门保持锁定 |
| 补传顺序 | **必须幂等、建议保序** | **可乱序**，按时间戳排序即可 |
| 补传合并 | 不可合并 | 可合并相同门状态的重复事件 |
| 风险窗口 | 透支、重复入账 | 权限撤销延迟生效 |

### 4.2 策略快照

`onecard-access-service` 在设备在线时生成并签名**策略快照**，经 `onecard-device-service` 下发至门禁控制器。快照内容包括：该门组授权人员标识列表、有效时段规则、快照版本号、签发时间、**最大离线有效期**。

快照的完整性与防篡改由国密体系保障：PSAM 安全模块与 SM2/SM3/SM4 算法用于签名和加密，设备端验签通过后才载入本地决策引擎。策略快照必须在设备本地完整缓存，不能依赖云端临时下发，否则断网瞬间决策即失效。

### 4.3 有界离线

**最大离线有效期**是门禁离线安全性的核心参数。超过有效期后，控制器必须执行 **fail-closed**（拒绝所有常规凭证）或仅允许应急凭证通行，不得无限期信任陈旧白名单。离线自治的前提是时间窗口可控；无限期信任本地快照意味着一次长期的权限撤销可能在断网设备上完全失效。

恢复连接后的同步顺序是确定的：**先校准时钟，再拉取最新策略快照，最后按序补传通行记录**。时钟校准必须先于快照拉取，否则快照的有效期判断可能在错误时钟下失效。


## 5. 设备接入层：通道可统一，语义必须隔离

`onecard-device-service` 的职责边界是协议适配与可靠投递。它不参与“这个人能不能进门”或“这笔钱扣没扣”的业务决策。

### 5.1 回传队列的语义隔离

这是整个离线架构中最容易出错、后果最直接的设计点。三套队列不得共用同一 MQTT 主题与同一重试 backoff：

| 队列 | 载荷 | 重试策略 | 失败可见性 | 优先级 |
|---|---|---|---|---|
| **消费流水** | 金额、幂等键、本地流水号 | **必须幂等**，按终端保序 | 窗口立刻感知 | 最高 |
| **人证核验** | 会话、证摘要、比对分 | 可延迟 | 前台可改人工 | 中 |
| **通行事件** | 门、人、结果 | 可合并相同门状态 | 闸机口排队感知较低 | 低 |

如果消费流水与人证核验、通行日志共用同一条 MQTT 主题和同一 backoff，食堂高峰的消费补传会被人证和通行流量挤成超时，窗口端的扣款确认延迟直接引发纠纷。通道层面可以统一接入，但**持久化保证和重试优先级必须按队列隔离**。

### 5.2 设备影子

设备影子保存期望状态与上报状态之间的差异，解决的是**状态同步**而不是在线状态展示。应用层无论设备是否联网，都可以从影子读取当前状态或下达指令，指令在设备上线后自动执行。但策略快照本身不走影子机制——快照必须完整缓存在端侧，影子只保存差异，不能替代端侧的离线决策数据。


## 6. 关键时序

### 6.1 离线消费 → 联网补传

```
终端离线：
  识别用户 → 读取本地余额 → 判定是否可扣
  → 写本地账本（WAL，状态 OFFLINE_CONFIRMED）→ 落盘成功
  → 显示“扣款成功”

终端联网：
  按本地流水号升序补传 → POST /offline-transactions（幂等键：terminal_id:local_seq_no）
  → transaction-service 幂等检查
    ├─ 已存在：返回已入账，不重复处理
    └─ 新交易：调用 risk-service 补传风控
         ├─ 通过 → 调用 account-service 入账 → 状态 SUCCESS
         └─ 不通过 → 状态 NEED_REVIEW，进入人工复核队列
```

### 6.2 门禁策略快照下发与离线决策

```
在线时：
  access-service 生成快照（版本号、有效期、人员-门组-时段规则）
  → 用 PSAM/SM2 签名 → 经 device-service 下发
  → 控制器验签 → 载入本地决策引擎

离线时：
  刷卡/刷脸 → 本地决策引擎比对快照 → 继电器动作
  → 写本地通行日志（可乱序、可合并）

恢复连接：
  校时 → 拉取最新快照（验签） → 补传通行日志（按时间戳排序，不要求幂等）
```


## 7. 清结算服务的内部粒度

`onecard-clearing-service` 保持为清结算业务域的归属单元，但内部不得建设为“什么都在做的批处理单体”。参照 2026 年银行清结算引擎的拆分实践，按业务能力域组织为三个职责单一的组件或子部署单元：

| 子能力 | 职责 | 幂等/一致性约束 |
|---|---|---|
| **轧差/清算** | 按清算对象汇总交易、计算应收应付净额 | 输入为已确认的交易流水，不直接读写账户余额 |
| **余额一致性校验/对账** | 将离线终端流水、在线交易、渠道回调三者交叉核对 | 差异分类：重复、缺失、金额不符，分别进入自动冲正或人工队列 |
| **幂等账务落库** | 将清算结果以幂等方式写入账务 | 幂等键基于 `business_id + seq_no`，幂等窗口覆盖最长对账周期 |

**报表与分析类查询不得跑在清结算联机库上。** 只读副本或数仓是报表的唯一承载位置。


## 8. 风险矩阵

| 风险 | 触发条件 | 影响 | 缓解措施 | 责任服务 |
|---|---|---|---|---|
| 离线消费重复入账 | 补传重试、网络抖动 | 资金多扣/多入 | 终端生成幂等键；服务端唯一约束 | transaction-service |
| 离线消费漏传 | 终端存储损坏、队列丢失 | 账实不平 | 本地 WAL；日终对账将“终端已扣但云端无记录”列为差错 | account-service / clearing-service |
| 时钟回拨导致幂等键冲突 | 终端时钟被篡改或漂移 | 两笔交易被视为同一笔 | 本地序号而非时间戳；补传时校验时间单调性 | transaction-service |
| 门禁快照过期后仍放行 | 终端未执行 fail-closed | 权限撤销失效 | 强制最大离线有效期；超期 fail-closed | access-service |
| 消费补传被通行日志挤占 | 共用 MQTT 主题/backoff | 窗口扣款确认延迟 | 回传队列按语义隔离，消费优先 | device-service |
| 清结算报表拖垮联机库 | 报表查询直连联机库 | 对账任务超时、影响日终 | 报表走只读副本或数仓 | clearing-service |


## 9. 落地路线图

**第一阶段：主链路（账户 + 交易 + 风控 + 设备 + 门禁）**

`account-service` 与 `transaction-service` 同库同事务部署，`risk-service` 以独立进程轻量启动，`device-service` 与 `access-service` 随门禁场景一并就位。**离线消费的幂等键必须在接口设计的第一天落定**——补传幂等的缺失会在第一笔网络抖动重试时暴露为账实不平，无法靠后期对账修补。

**第二阶段：支付适配与通知**

`payment-adapter-service` 更名并独立部署；`notification-service` 轻量上线。这两个服务不参与离线主链路，可以在主链路稳定后并行推进。

**第三阶段：清结算内部拆分**

`clearing-service` 在交易量积累后按 §7 的三项子能力逐步拆分部署单元，不急于在第一阶段铺开。日终对账本身可以在第一阶段以批处理任务的形式先行运行，但**对账输入必须从第一天起就包含离线补传流水**。


## 10. 附：与 `project-root` 目录的对应关系

| 服务 | `services/` 目录 | `apis/` 契约模块 |
|---|---|---|
| 账户 | `services/onecard-account-service` | `apis/onecard-account-api` |
| 交易 | `services/onecard-transaction-service` | `apis/onecard-transaction-api` |
| 支付适配 | `services/onecard-payment-adapter-service` | `apis/onecard-payment-adapter-api` |
| 清结算 | `services/onecard-clearing-service` | `apis/onecard-clearing-api` |
| 通知 | `services/onecard-notification-service` | `apis/onecard-notification-api` |
| 风控 | `services/onecard-risk-service` | `apis/onecard-risk-api` |
| 门禁 | `services/onecard-access-service` | `apis/onecard-access-api` |
| 设备接入 | `services/onecard-device-service` | `apis/onecard-device-api`（仅内部命令/事件契约） |

`gateway/` 保持单 API 入口地位，只做统一鉴权、全局限流和基础路由，**不得出现直连账户/交易数据库的 `mapper/` 与 `entity/`**。所有资金与门禁业务请求经 `gateway/` 路由至对应 `services/` 服务。


**文档结论**：八个服务的主体边界已经收敛。设计的核心不在“再拆什么”，而在两个已经确定的离线约束——消费的**幂等键由终端生成**、门禁的**策略快照有最大有效期**——能否在接口设计的第一天被钉死在各自的服务边界内。这两条约束一旦缺失，后期的对账修复无法弥补第一笔网络抖动带来的账实不平。
