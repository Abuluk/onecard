# 阶段 0：业务基线、架构决策与技术验证详细方案

**状态**：待执行；当前优先阶段
**目标**：把业务边界、架构决策、目标技术组合、容量和安全要求变为有负责人、有证据、可执行的基线
**范围**：调研、ADR、模型/契约草案、目标组合 PoC、故障与性能基准
**不含**：账户/交易/门禁等生产业务功能实现

本方案细化 `docs/开发阶段规划.md` 中的阶段 0。阶段 0 和阶段 1 是两个独立、顺序执行的阶段：阶段 0 产出决策与验证证据；阶段 1 才建设工程与运行平台。阶段 0 未通过前，不开始阶段 1 中依赖未决身份、组件、数据或 SLO 的实现。

## 1. 成功标准

- 一卡通业务流程、数据权属、资金状态机、在线优先/断线故障切换语义和异常终态均有业务负责人书面确认。
- 每项架构选择都有 ADR，包含候选方案、依据、代价、失败策略、验证结果、决策人和复审条件；未决项明确标记阻断范围。
- 指定运行环境的 JDK、OS、Spring/Alibaba、Nacos、数据库、缓存、消息和监控组合经过官方资料核对与目标环境联合 PoC，不以单个组件声明或 Maven 构建代替。
- 容量模型来自实际业务数量和峰值窗口；逐服务 SLO、离线补传恢复时间、资源上限和容灾目标经业务与运维负责人批准，不编造 TPS 或通用延迟数字。
- 威胁模型、数据分类、身份/网络边界、合规适用性和门禁生命安全行为有责任人及验证证据。
- 阶段 0 验收包足以让阶段 1 按固定基线实施，不需要在阶段 1 临时猜测关键架构决定。

## 2. 当前基线与已知风险

- 当前 Maven 基线为 JDK 25、Spring Boot 4.1.2、Spring Cloud 2025.1.4、Spring Cloud Alibaba 2025.1.0.0；目标运行兼容性和生产适用性仍待核实。
- Nacos、OceanBase、Valkey、RocketMQ 等目标组件尚未组成业务运行栈。本地 MySQL/Redis 仅用于 N9E，不能代表业务数据库/缓存验证结果。
- 在线交易是默认模式；仅意外断线触发终端有界故障切换。余额不足、卡冻结、风控拒绝等业务拒绝不得触发离线支付。已发出但结果未知的在途交易保持待确认，不转成本地成功；恢复后用同一幂等键查询/重试；后续新交易才可在故障切换状态下使用新序号进入离线流程。
- 账户账本归账户服务；交易服务负责编排；跨来源和日终对账归清结算服务。终端已确认、平台风控拒绝或不可用时的资金处理尚需明确。
- 当前 Gateway 默认配置了八个服务路径，设备和风控入口的实际信任边界仍需用暴露矩阵和网络图确定。
- 仓库部署 workflow 含已暴露的镜像仓库凭据，且发布目标配置与现有目录不一致。该凭据应按已泄露处理，先吊销/轮换，再处理远端历史并停用未批准的自动发布。

## 3. 决策范围与顺序

| 顺序 | 决策域 | 必须回答的问题 | 主要产物 |
|---|---|---|---|
| 0 | 凭据与发布风险 | 暴露凭据是否仍有效、哪些远端/历史副本包含它、如何限制发布权限 | 凭据处置记录、发布边界 |
| 1 | 业务范围与规模 | 有哪些用户、卡、终端、控制器、渠道、场景、峰值和日结要求 | 需求/容量输入表、系统上下文图 |
| 2 | 资金与离线状态 | 在线结果、断线、结果未知、风险拒绝、补传、入账、待复核和冲正如何转换 | 交易状态机、账务影响表、资金 ADR |
| 3 | 人员、门禁与身份 | 主数据源、撤销时限、身份源、设备认证、门型与消防行为如何定义 | 数据权属矩阵、身份/门禁 ADR |
| 4 | 安全与合规范围 | 系统边界、数据类别、威胁、审计/留存、合规适用范围是什么 | 数据分类、威胁模型、适用性结论 |
| 5 | 技术兼容与运行拓扑 | 目标版本/产品、网络、配置、密钥、存储与部署如何组合 | 兼容矩阵、部署图、组件 ADR |
| 6 | 容量、可靠性与恢复 | 吞吐、延迟、积压、恢复、RTO/RPO 和资源目标是多少 | 负载模型、SLO、备份/恢复目标 |
| 7 | 联合 PoC 与复核 | 目标组合是否满足功能、安全、兼容和容量底线 | PoC、故障/性能报告、阶段退出评审 |

顺序 1-6 可在不同负责人并行调研，但决策依赖要显式记录；资金状态、人员数据责任、身份边界、目标技术组合和容量输入未定时，不得宣称阶段 0 完成。

## 4. 详细任务

### 任务 0：凭据事件处置与发布边界止血

**目标**：先消除当前已暴露仓库凭据继续被使用的风险。

**验收条件**：

- [ ] 镜像仓库管理员已吊销/轮换该凭据，并确认新凭据的最小权限、使用范围和审计记录。
- [ ] 仓库管理员按托管平台流程清理远端可达历史中的凭据；清理前确认协作者、分支和镜像备份的协调步骤，避免无意覆盖其他未发布工作。
- [ ] 普通 push、PR 和本地测试不触发镜像发布；发布目标、镜像上下文和审批环境在仓库/镜像仓库归属确认前保持禁用。
- [ ] Secret scanner 检查工作树和远端历史；处置报告不把真实凭据复制进 issue、日志、ADR 或测试样例。

**验证**：在提供商处核验旧凭据失效；扫描工作树与清理后的远端历史；审查 Actions 触发规则、环境保护和权限。旋转与历史改写由有权限的仓库管理员执行。

**依赖**：无；必须在任何发布/推送前完成。
**产物**：凭据处置记录、发布权限清单。
**规模**：小；含外部管理员操作。

### 任务 1：业务范围、用户和规模输入

**目标**：获得建模和容量估算所需的真实业务输入，并明确决策责任人。

**验收条件**：

- [ ] 列出用户/管理员/财务/运维/设备厂商等参与方及决策责任人，梳理消费、充值、退款/冲正、门禁、核验、清分和报表的目标/非目标。
- [ ] 收集当前与规划用户数、卡数、终端/控制器数量、食堂峰值时段、在线交易峰值、支付渠道限额、消息事件量、日结数据量、留存期和业务增长假设；未知数据标注负责人和截止日期。
- [ ] 绘制系统上下文和外部依赖图，标明用户 API、管理 API、支付回调、设备协议、人员主数据、资金/清算系统和运维入口。
- [ ] 区分已确认事实、业务假设、厂商能力声明和待验证数据，后续容量/合规结论引用对应证据。

**验证**：由业务、财务、运维和设备负责人评审流程及数量来源；从现有流水/设备台账抽样复核峰值估算，记录数据时间范围及缺口。

**依赖**：任务 0 可并行。
**产物**：业务范围说明、用户/设备清单、容量输入表、上下文图、责任人表。
**规模**：中。

### 任务 2：资金模型、交易状态机与终端故障切换决策

**目标**：冻结在线交易和终端断线故障切换的资金语义，避免交易、账户和终端各自实现不同规则。

**验收条件**：

- [ ] 明确账户服务本地事务内的余额与账本不变量、交易服务状态机、账户写入可靠推进机制、超时/重复/服务重启/未知结果查询与幂等保留期限；在 outbox、幂等状态机等候选中作出有证据的选择。
- [ ] 写清在线默认、意外断线判定阈值/连续失败数/恢复观察期/防抖；余额不足、卡冻结、风控拒绝等业务响应不得触发本地支付；当前未知在途交易待确认，后续新交易才能进入离线故障切换。
- [ ] 决定每卡/每终端离线额度、最长断线时间、状态缓存新鲜度、终端撤销/丢失、序号回退、时钟偏移、WAL 损坏/存储耗尽的行为及负责方。
- [ ] 明确 `NEED_REVIEW` 是仅受理、账本已记账还是资金保留；定义其可用余额影响、风控拒绝/不可用时处置、人工审批、退款/冲正和对账终态。
- [ ] 定义恢复屏障：本地流水同步、幂等确认、账户入账/保留额、余额刷新和终端恢复普通在线模式的顺序与确认条件，证明不会重复开放余额。
- [ ] 固定 `terminal_id + local_seq_no` 等幂等键组成、唯一范围、序号持久化、重复/缺口/乱序处理及离线流水重放策略。

**验证**：用状态转移表和可执行状态机/模拟器覆盖业务拒绝、请求未发送、服务端已提交但响应丢失、服务端拒绝但响应丢失、断线抖动、后续新交易离线受理、重复补传、风控不可用、恢复同步和重复请求；对每条路径核对交易状态、账户分录、终端提示与客户资金影响。

**依赖**：任务 1。
**产物**：资金/离线状态机图、账务影响矩阵、幂等契约、恢复屏障 ADR、失败场景测试报告。
**规模**：大；按在线状态机、离线状态机、恢复屏障三个评审切片完成。

### 任务 3：支付渠道、清结算与跨服务责任

**目标**：确认外部渠道状态如何进入交易/账本，并保持服务数据权属一致。

**验收条件**：

- [ ] 确定支付渠道请求、回调验签/重放保护、超时查询、部分成功、退款/撤销、渠道对账数据和账户入账之间的状态与幂等关系。
- [ ] 明确账户账本、交易流水、终端本地流水、支付渠道账单和清结算结果分别由谁写入；清结算只经账户服务契约提交结果，不直接改账户余额。
- [ ] 明确交易、账户、支付适配和通知之间调用/事件边界，选择可靠消息/outbox/查询补偿等推进方式，并定义至少一次投递、去重与重放行为。
- [ ] 明确跨服务业务 ID、幂等键、事件版本、状态保留期、重试/死信/人工差错流程及责任人。

**验证**：以表格逐项模拟渠道成功/拒绝/超时、重复/乱序回调、退款部分成功、账户已提交而调用方超时、消息重复和日终对账；验证所有路径有收敛状态和账务责任方。

**依赖**：任务 1、2。
**产物**：数据责任矩阵、跨服务调用/事件图、渠道与清结算状态表、ADR。
**规模**：中。

### 任务 4：人员主数据、身份、安全、隐私与门禁生命安全

**目标**：定义谁能访问哪些入口、设备如何被信任、个人信息如何被处理，以及离线门禁的安全边界。

**验收条件**：

- [ ] 指定人员/卡介质主数据权威源、同步方向、撤权时限、离线数据范围、冲突处理和责任团队；门禁服务不成为未授权主数据源。
- [ ] 明确用户、管理员、服务和设备的身份提供方、凭证/证书生命周期、认证/授权模型、职责分离、服务间最小权限、密钥保管和轮换。
- [ ] 形成外部路由暴露矩阵，区分用户/管理、支付回调、设备协议、内部服务调用和运维管理；定出直连服务端口、网络分区、Nacos 管理面和 Actuator 的访问规则。
- [ ] 完成数据分类分级和数据流图；明确个人/生物特征/消费/通行数据的采集目的、最小化、日志脱敏、访问审计、留存/删除和备份策略，不默认采集或记录生物模板。
- [ ] 对系统定级、等保/密评、商用密码和产品认证作适用性分析，结论标注依据、责任机构和待确认事项，不把工程方案文字视为正式测评结论。
- [ ] 按门型确认控制器断电/断网/快照过期/撤权/时钟错误/消防联动/紧急疏散时的动作；由场地安全负责人和设备方签署实测方案。
- [ ] 对支付回调、用户入口、服务间调用、设备命令、Nacos/数据库/消息和日志构建威胁模型及滥用场景。

**验证**：安全、隐私、运维、场地安全和设备负责人联合评审；在真实门型/控制器上验证消防及疏散行为计划，不以通用模拟器替代生命安全验证；抽样演练凭据撤销和人员撤权。

**依赖**：任务 1；与任务 2、3 并行。
**产物**：身份/网络边界 ADR、路由矩阵、威胁模型、数据分类/权属表、合规适用性记录、门禁安全验收方案。
**规模**：大；身份、隐私/合规、现场门禁分开评审后汇总。

### 任务 5：目标组件兼容矩阵与部署拓扑

**目标**：从候选技术栈中冻结可复现的目标组合，并把实验环境、安全配置和发布方式定下来。

**验收条件**：

- [ ] 对 JDK 发行版/版本、OS/CPU、Spring Boot/Cloud/Alibaba BOM、Nacos、Gateway、OpenFeign、Sentinel、Seata、数据库、JDBC、Flyway、缓存、消息、监控和容器镜像逐项记录候选版本、官方支持范围、许可证/供应支持、信创/安全适用性和证据链接。
- [ ] 核对当前 POM 组合与官方版本矩阵；发生不兼容或缺少支持证据时给出升级/降级/替代方案和复测要求，不以依赖下载成功作为通过。
- [ ] 比较 OceanBase 目标模式/兼容语法、隔离级别、事务/并发、迁移工具、备份恢复、加密审计及 Seata 是否需要；不预设必须引入分布式事务。
- [ ] 冻结 Nacos `spring.config.import` 的 namespace/group/dataId、必需/可选导入、配置刷新、密钥注入、服务发现和故障行为；密钥不放仓库或普通配置项。
- [ ] 绘制 dev/test/staging/prod 拓扑、外部/内部/设备/管理/监控网络区、入口、服务副本、存储、消息、注册配置、镜像仓库和 Secret 管理边界。
- [ ] 明确日志/指标/审计告警、备份、恢复演练、RTO/RPO、证书轮换、滚动升级和回滚的技术方案及责任人。

**验证**：以官方产品/框架文档、兼容矩阵、厂商书面材料和目标 OS/JDK 运行结果交叉确认；所有版本可锁定到具体版本/摘要，禁止用 `latest` 作为验收基线。

**依赖**：任务 1、4。
**产物**：版本兼容矩阵、选型 ADR、配置矩阵、部署/信任边界拓扑、密钥与备份恢复方案。
**规模**：大；运行时、数据层和运营拓扑分批决策。

### 任务 6：负载模型、逐服务 SLO 和资源预算

**目标**：用真实使用场景形成可以复测的容量目标。

**验收条件**：

- [ ] 将任务 1 的用户/设备/渠道数据转为请求类型、日均量、峰值时段、突发系数、热点比例、读写比例、消息产生/消费量、数据保留和增长曲线。
- [ ] 分别定义 Gateway、交易、账户、风控、设备、支付回调、通知、门禁同步、清结算的吞吐、p95/p99、错误率、超时率、连接/线程/内存/CPU上限。
- [ ] 为最长批准离线窗口和最大恢复积压建立模型；明确补传清空时间、在线消费保护阈值、公平性、超额度行为和积压告警阈值。
- [ ] 定义数据库容量/连接池、消息分区/保留、缓存命中与失效、监控基数/采样和日结批次时间的验收边界。
- [ ] 约定基准/稳态/峰值/突发/压力上限/长稳/故障降级/恢复补压的环境、数据、并发和报告格式；每个数值有来源和批准人。
- [ ] 确认测试环境与生产目标的硬件、OS、JDK、数据库、网络、数据规模差异；差异未经量化时结果不能外推到生产。

**验证**：业务、财务、运维共同签字确认 SLO；对峰值交易、支付渠道限额、终端断线窗口和日结期限做边界核算；检查负载模型能被压测脚本或数据生成器表达。

**依赖**：任务 1、5。
**产物**：按服务的负载模型/SLO/资源预算表、测试矩阵、批准记录。
**规模**：中。

### 任务 7：目标环境联合 PoC、故障与性能验证

**目标**：证明选定组合可运行且满足阶段 0 的最低功能、安全和性能要求。

**验收条件**：

- [ ] 在目标 OS/JDK 和容器运行环境中完成 Maven 构建与最小 Spring/Cloud/Nacos 启动；配置导入、服务注册/发现、密钥加载、健康/指标抓取均可复现。
- [ ] 用目标数据库验证 JDBC/ORM 方言、事务隔离、并发更新、迁移/恢复、审计/加密和连接池；用目标缓存验证一致性、过期、并发和节点故障；用目标消息验证 TLS、至少一次、重复/乱序、重放、积压和消费恢复。
- [ ] 对账户写入和交易推进候选方案做可丢响应、服务重启、重复幂等请求、消息重复及依赖故障试验；账务不变量保持成立。
- [ ] 对端侧状态机模拟网络延迟、丢包、意外断线、请求未知、业务拒绝、链路抖动、终端重启、恢复屏障和积压补传；证明业务拒绝不会触发本地支付，未知在途交易不被转成本地成功。
- [ ] 执行已批准的基准、峰值、突发、压力上限、持续运行和故障恢复补压；报告 p50/p95/p99、吞吐、错误/超时、CPU/内存/GC、连接池/锁/慢查询、队列积压和清空时间。
- [ ] 进行配置/权限/网络/密钥/镜像/依赖基础安全检查；门禁真实设备的生命安全验证方案得到场地负责人确认。

**验证**：每个 PoC 包含版本清单、启动/测试命令、环境资源、输入数据、原始结果、日志和结论；失败需记录原因、责任人、方案和复测，不允许以改低 SLO 或关闭检查换取通过。

**依赖**：任务 2-6 的决策已冻结到可测试状态；任务 0 凭据处置通过。
**产物**：目标组合 PoC、兼容/故障/安全/性能报告、遗留风险清单。
**规模**：大；按框架注册配置、数据组件、消息/缓存、资金状态机四类实验独立报告。

### 任务 8：ADR 汇总、跨文档核对与阶段出口评审

**目标**：检查决策之间没有冲突，并正式决定是否允许进入阶段 1。

**验收条件**：

- [ ] 重要决策按 `docs/adr/README.md` 格式形成带序号 ADR，包含状态、背景、选择、替代方案、后果、验证证据、负责人和复审条件。
- [ ] 核对 `docs/项目说明.md`、`docs/微服务划分.md`、`docs/基础开发方案.md`、`docs/architecture.md`、本阶段方案和配置矩阵语义一致。
- [ ] 所有阻断级风险已有处理结果或明确不进入阶段 1；剩余风险有负责人、期限、影响、缓解和接受人。
- [ ] 业务、财务、设备/场地安全、信息安全、运维/基础设施负责人完成阶段退出评审并签字。

**验证**：按检查点 A-D 逐项回放证据；任何缺少负责人、缺少测试结果或依赖关系冲突的决策均保持未通过，并返回对应任务修订。

**依赖**：任务 0-7。
**产物**：阶段 0 决策包、ADR 索引、批准后的阶段 1 输入基线。
**规模**：中。

## 5. 检查点与阶段退出

### 检查点 A：业务、资金和数据责任（任务 1-3）

- [ ] 用户/设备/渠道范围和关键规模输入有来源及责任人。
- [ ] 在线交易、未知结果、断线故障切换、离线复核、入账和恢复屏障状态机通过业务/财务评审。
- [ ] 账户、交易、终端、渠道和清结算的数据/写入责任无冲突。

### 检查点 B：身份、安全和合规边界（任务 4）

- [ ] 用户/管理员/服务/设备身份和网络分区明确；路由暴露矩阵默认拒绝未批准入口。
- [ ] 数据分类、日志脱敏、审计/留存和隐私范围有责任方结论。
- [ ] 门禁消防/疏散及断网、断电、过期行为有真实设备验证计划和签署人。
- [ ] 等保/密评/产品认证适用性记录证据来源及专业机构确认路径。

### 检查点 C：技术、拓扑和容量（任务 5-6）

- [ ] 目标组件版本及组合兼容结果可查；未验证组件仍标记为阻断，不写成生产已选型。
- [ ] 部署、网络、配置/密钥、监控、备份与恢复拓扑经基础设施负责人评审。
- [ ] 每服务 SLO、负载模型、离线恢复积压目标和硬件配置已批准。

### 检查点 D：联合验证与签署（任务 7-8）

- [ ] 功能、兼容、故障、安全和性能报告可复现，失败项已关闭或正式阻断。
- [ ] ADR 与各项方案文档口径一致，阶段责任人完成评审。

**阶段 0 退出条件**：A-D 全部通过；9 项架构审阅结论均有负责人和书面结果；目标组件组合有目标环境的兼容、安全和性能证据；阶段 1 所需身份、配置、网络、数据库、测试环境、SLO 和安全门槛已冻结。否则保持阶段 0，不进入阶段 1 的依赖性实现。

## 6. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 把候选组件当作已批准生产栈 | 版本/信创/安全不兼容，造成后续返工 | 官方资料与目标环境联合验证后才进入兼容矩阵的“通过”列 |
| 需求规模数据缺失 | SLO 和成本随意设定 | 标记缺口、负责人和截止时间；未批准数字不得作为退出依据 |
| 资金异常状态定义不清 | 重复扣款、账实不平或线下纠纷 | 状态转移和账户影响逐项评审并故障注入 |
| 门禁通用 fail-closed 决策 | 影响消防与紧急疏散 | 按门型和现场消防联动实测，由场地安全负责人批准 |
| 合规结论超出证据 | 方案误导采购/测评 | 记录适用性与证据来源，正式结论由责任方/专业机构确认 |
| 凭据泄露与自动发布未隔离 | 未授权仓库访问或镜像发布 | 先轮换，处理远端历史，禁用未批准发布触发器并限制 Secret 权限 |
| PoC 只验证单组件 | 联合运行仍失败 | 对锁定版本、OS/JDK、数据库/缓存/消息执行端到端组合验证 |
